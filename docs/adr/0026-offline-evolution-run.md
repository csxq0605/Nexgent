# ADR 0026：第 3 层离线进化——一次运行怎样搜索、停止和下结论

- **状态**：已接受（只定流程与文件格式；v1 只在脚本化模型与评测器下跑过，真实运行等用户开口）
- **日期**：2026-10-19
- **依据**：
  - 资料库 `docs/handoff/evolution-layer2-3-design.md` §3（对照读过的 GEPA、DSPy、ADAS、DGM、HGM、MASS 源码，见 `evolution-layer2-3-notes/`）；
  - ADR 0018 第 6、9、10 条，ADR 0019 第 4 条；用户 2026-10-19 回复“都做”。
- **替代**：无。本 ADR 补充 ADR 0018 第 6 条的实现细节；评价器纪元不变（规则 id 仍是 `adr-0019`）。

## 决策

1. **v1 可学习的部件只有两个。**
   - **执行指引**：给根任务的一段做法文字（≤4000 字符），装载时作为能力版本的 `context-policy` 文字。
   - **检索参数**：手册每个任务给几条（1–8）、相关性门槛的覆盖率（0.05–0.5）与共享词数（1–4）、每个任务抽几个启用的技能（0–3）。
   - 改进器的可学习段落先不进搜索：评它们要跑下游学习，费用高一个量级，等 ADR 0019 第 5 条的下游比较实现以后再加。系统提示、工具说明、默认工作流等「kernel 维护」把它们数据化以后再加。
   - 冻结字段：`permissions`、`approvals`、`sandbox`、`costCaps`、`budget`、`learning`、`evaluator`、`rubric`、`practice`、`model`。候选里出现任何一个就拒绝（`offlineCandidateProblems`），评测器只拿到候选和题目 id。
2. **计划不花钱。**
   - 用固定种子从练习题集切出四份：小批量池（`train`）、选择集（`selection`，至多 12 题）、留出集（`holdout`，至多 20 题）、通用题（`guard`）。前两份学习方可见，后两份只在最后一关用。
   - 预计花费按最坏情况算：种子评一次选择集，每一轮“父代与子代各跑 3 道小批量题 + 子代跑全部选择集 + 一次提案”，最后两边各跑一次留出集与通用题。上限默认是预计的 1.5 倍。
   - 计划连同哈希写进 `run.json`，状态 `awaiting-approval`。
3. **用户批准的上限必须与计划一致才跑。** 运行在每个阶段开始前检查“已花 + 这一阶段的预计”，会超过上限就停在 `stopped`（`budget`）。要更高的上限就重新计划。
4. **搜索。**
   - **选父代**：在选择集上取每道题得分最高的那些版本，去掉被别的前沿成员支配的，按出现在几道题的前沿上计权，再除以 `1 + 已有子代数`（GEPA 的 Pareto 频次 × DGM 的子代降权）。
   - **选部件**：同一个父代上轮流选。
   - **提案**：一次请求，只改一个部件。输入是父代在小批量题上的“任务、运行结果、评测反馈”，以及这个部件最近被拒的改动和理由（DSPy 的指令历史、ADAS 的失败回传），并列出冻结字段。回答与父代相同、超界、改了别的部件或冻结字段，都算被拒。
   - **接受**：子代在同一组小批量题上的总分严格高于父代，并且至多在 1 道题上变差（比 GEPA 的“总分更高”多一道防噪声的限制）。接受的子代跑全部选择集进入档案，否则记入被拒历史。
   - **停止**：最大轮数（默认 10）、连续 4 轮没有接受、停止文件、取消、或下一阶段会超上限。
5. **最后一关。**
   - 选择集均分最高、且高于种子的版本，与种子在留出集和通用题上各跑（默认 1 次，可配置）。
   - 留出集上按题配对的差，用两层自助法（先抽题，再在题内抽重复）求 95% 区间，下限大于 0，并且通用题平均不差于 −0.05，结论才是 `recommended`；否则是 `no-better`。没有版本在选择集上胜过种子时，直接 `no-better`，不花留出集的钱。
   - 状态 `awaiting-user`。`recommended` 只是推荐，要用户在能力页批准才写成能力版本生效（ADR 0018 第 9 条；界面和应用接口另做）。
6. **续跑。** 每个阶段结束原子写一次 `run.json`，随机数状态一起保存。中断的那一轮作废重做。计划哈希对不上就拒绝续跑。续跑时清掉上次的停止文件。
7. **评测器是接口。** `PracticeEvaluator` 收候选与题目 id，回每题 0–1 分和反馈；没跑完或打不了分记 0（未知结果不算成功）。`ReplayPracticeEvaluator` 是产品形态：每道题在它输入快照的一次性副本里、带着候选跑，跑完从副本打分。准备副本、运行、打分三步作为参数传入，以便接上门控的副本、`TrialRunner`、确定性检查与外部评审。
8. **花费记账。** 提案请求记 `purpose: "auxiliary"`、`taskId: "offline:<runId>"`，不带 `learningPhase`，所以不占第 1、2 层的学习预算；运行自己的 `spentUsd` 加总提案和每道题的花费，对照批准的上限。

## 后果

- 离线流程在脚本化模型与评测器下能完整跑通（计划、批准、种子、迭代、留出、推荐、超限停止、停止文件、续跑、拒绝被改过的计划）。
- 还没接上的：把候选的执行指引与检索参数装进重放副本（要生成一个带 `context-policy` 组件的能力版本，产品现在也还不从配置读检索参数）、外部评审打分、能力页上的批准与应用、SDK 入口。
- 第 3 层是否带来收益，要按 ADR 0019 第 8 条测量；真实运行花钱，等用户开口。
