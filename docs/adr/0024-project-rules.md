# ADR 0024：用户说过的项目规则单独存、每次都给

- **状态**：已接受
- **日期**：2026-10-18
- **依据**：
  - 本机编程实验（2026-10-18）：带经验与不带经验两边考试同分（28/40），失分全在两条只在反馈里说过的项目约定上；
  - 用户 2026-10-18 同意“规则从任务指令和反馈里来、按用户说的范围记、拿不准的待确认”。
- **替代**：
  - ADR 0018 第 4 条中“条目一律抽象、不含具体值”对用户明确说出的项目约定不再适用；
  - ADR 0023 第 3 条的随机注入与按证据启用 / 下线，不适用于项目规则。

## 背景

实验里用户在反馈中说了两条约定：金额一律返回整数分；每个新函数要有自己的测试文件，按函数名命名。每题当场能改对，下一题照样再犯。查经验条目发现三处原因：

1. 反思把约定提炼成“先查项目约定，README 没写就不要假设”，具体的单位和命名丢了；
2. 条目只在任务文字含它的关键词时才给，“实现某个函数”这样的任务对不上“金额”“测试文件”；
3. 即使检索到，试用条目也只按 0.5 的概率给。

成熟的工具把“项目规则”和“学到的做法”分开处理：

- Claude Code 的 CLAUDE.md：每次会话都加载，子目录里的文件只在处理该目录时加载；
- Cursor rules：按 glob 自动附加，或始终生效；后台自动生成的 memories 要用户批准才生效；
- Codex 的 AGENTS.md：作用于所在目录树，越近的越优先，用户在对话里的直接指令优先于它。

## 决策

1. **条目分两种。** `kind` 缺省为做法（practice），照旧按 ADR 0018、0023 处理。`kind: "rule"` 是项目规则：
   - 用户在任务消息或反馈里说成“以后都这样”的约定才算；
   - 只记在项目级；
   - 保留具体的单位、格式、命名和数值，但要用自己的话重述，不照抄原句。
2. **范围按用户的话记。** `appliesTo` 写用户说的范围：整个项目，或某个目录、模块、某类文件。没说范围时，记为这次任务改到的那部分。范围由执行模型按文字判断是否适用，宿主不做路径匹配。
3. **每次都给，不抽签。** 本项目每个根任务的第一轮，在手册注入的最前面给出全部生效的规则。规则作用于整个工作区（含所有子目录），除非规则自己写了更窄的范围。规则压过项目里旧文件（README、注释、示例）的说法；只有本任务自己的消息明确提出的要求能压过规则（与 Codex AGENTS.md 的优先级一致）。规则不参加随机注入对照，也不因没人用而下线；只有用户停用，或被新规则通过 `supersedes` 取代时才退休。
4. **拿不准的等用户确认。** 反思判断不了某句话是不是长期规则时，写成 `pending`。待确认的规则不注入，在“能力”页列在最前，用户点“确认”生效，点“不要”停用。只针对这一次结果的要求（“这次”“这里”、对某个成果的口味）不算规则，照旧不学。
5. **把关。**
   - 规则只能带用户亲口给出的数值，任务数据或回答里的其他数值照样拒绝；
   - 与用户原话共享 24 个以上连续字符的拒绝；
   - 与已有规则相似且没声明取代的视为重复；
   - 一次反思新增条数的上限（3 条）包含规则。

6. **打分和反思都按规则来。** 自评生成评分标准和打分时，看到这次任务拿到的规则，并按上面的优先级把规则当成任务要求的一部分。反思不给规则投票、不改写规则：规则不因运行结果、项目文件或评价与它不一致而被判错，只有用户后来的话（一条声明 `supersedes` 的新规则）能改它；违反的操作以 `rule-locked` 拒绝。

   实验 v3（2026-10-18）里，规则范围被写成“整个项目（题1 项目根目录）”，执行模型据此认为规则不管后面的题，又把 README 里写的“元”当成任务要求；自评看不到规则，按 README 判，反思随后三次给规则投了反对票。本条与第 3 条的优先级就是为此补上的。

## 后果

- 用户明确说过的约定从下一个任务起就生效，不需要攒证据。
- 规则是否有用不再由对照判断，所以写错的规则只能靠用户停用。这正是要用户确认拿不准那一类的原因。
- 反思提示升到 `v3`。
