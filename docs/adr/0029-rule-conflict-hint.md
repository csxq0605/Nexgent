# ADR 0029：项目规则与现状冲突时，在任务里问用户一句

- **状态**：已接受
- **日期**：2026-10-19
- **依据**：
  - 本机试用（2026-10-19）：一条项目规则生效后，项目里 3 个旧测试与它不符。这次是模型自己察觉后来问的，系统没有提醒。
  - 用户 2026-10-19 回复“都要做”（其中一件就是这条）。
- **替代**：ADR 0024 第 3 条“规则压过项目里旧文件的说法”只对说明性的文件（README、注释、示例）照旧成立。已有测试和代码行为与规则不符时，按本 ADR 先问用户。

## 背景

规则是在项目文件写好以后才定的，旧测试和旧代码可能还按原来的做法。按 ADR 0024，模型会把规则当成更高的要求，于是可能悄悄改掉旧测试；也可能遵守旧测试，违反规则。哪种都可能不是用户想要的，只有用户能定。

宿主没法用确定性的办法判断“这个失败是不是规则造成的”，这要看语义。所以系统做两件事：在两个固定的时机提醒模型去查，并规定问法。由模型判断，宿主负责决定什么时候查、怎么问。

## 决策

1. **规则旁边写明冲突怎么办。** 给出规则时，紧跟一句：
   - 规则范围内已有的测试或代码与规则不符时，两边都不改；
   - 用用户的语言问一句“规则「X」与现状「Y」冲突，以哪个为准？”，然后结束这一轮，等用户回答。
   - README、注释、示例这类说明文字仍按规则改，不问。
2. **新规则先查一次。** 一条规则在本项目里还没给过别的根任务时，标成“新”，并要求模型在这条规则的范围内动手之前，先找与它不符的已有测试或代码。
   - 是否给过，看手册 `usage.jsonl` 里有没有别的会话给出这条规则的 `hit`。
   - 规则给出时记一条 `hit`（`given: true`，没有 `draw`），它不算随机对照的证据。
   - 同一条规则只在它第一次被给出的那个任务里查，以后的任务不再重复。
3. **自动检查失败时再提醒。** 本任务给过规则，且这一轮的自动检查失败时，重试说明后面加一句：如果失败来自与规则不符的旧测试或旧代码，而不是这次的改动有错，就按第 1 条问用户，不要再改。
4. **问过就不再重试。** 重试说明之后，模型只回复文字、没有调用工具，说明它已经解释了检查为什么过不了，或者已经在问用户。这时这一轮不再自动重试。这条对任何检查失败都成立，不只针对规则。
5. **提问要短。**
   - 一句话，说清是哪条规则、和什么冲突，不解释机制，不说“系统检测到”之类的话（与 ADR 0028 一致）。
   - 用户回答以后，按用户的话做。如果用户说的是“以后都这样”，反思照 ADR 0024 写一条取代旧规则的新规则。

## 后果

- 规则与旧测试不符时，用户会在任务结束时看到一句问话，不会发现测试被悄悄改了。
- 这仍依赖模型找到冲突。系统保证的是查的时机和问法，不保证每次都能找到。
- 每条规则在第一次给出的任务里多花几次读文件的步骤。
- 不针对任何规则、文件类型或领域写特殊逻辑。
