# ADR 0015：反馈检查不要求一次性附加要求，评审看到完整的文件清单与反馈

- **状态**：已接受
- **日期**：2026-10-14
- **依据**：
  - 用户 2026-10-14 13:46 看完小试点结果后说：“没让你改规则那不就是系统有问题吗”，要求查清改进流程为什么没比“只把反馈记成笔记”强，并修掉系统缺陷。
  - 试点记录在资料库 `validation-raw/step-6-pilot-20261014/`，分析见 `docs/handoff/step6-pilot-loss-analysis.md`。
  - 实验的评分（holdout 判定器、外部评审、统计、冻结计划）不变。这里改的是产品里门控的反馈检查与偏好评审。
- **替代**：
  - ADR 0006 第 6 条反馈检查的问法：在下文第 1 条之上收窄；
  - ADR 0014 第 3 条的规则 id `adr-0014`，改为 `adr-0015`，因此进入新纪元。
  - ADR 0005、0006、0007、0008、0013、0014 的其余部分仍然有效。

## 背景

试点里两个改进作业的反馈检查都被同一类问题拖低。

1. **一次性附加要求被当成要解决的问题。**
   - 反馈常常混着两类内容：
     - 对做法的意见，往往是长期习惯，例如“文件名里带了空格”“文末没有列出资料文件”；
     - 只针对那一次的附加要求，例如“这次我还想要一份新旧文件名对照表”“这次我想要短一点，800 字以内”。
   - 门控回放的是第一条反馈之前的任务原文（ADR 0006），回放运行根本没有收到附加要求。但反馈检查把整段反馈交给评审，问“反馈指出的问题是否已经解决”。
   - 文件类的候选确实学会了“文件名不带空格”（两次回放文件名都没有空格），反馈检查仍两次都判“没解决”：
     - 第 1 次：“没有新旧文件名对照表”；
     - 第 2 次：“没有对照表，且只看到 12 个文件”。
   - 于是候选与基线的反馈检查都是 0%，作业以 `no-improvement` 被拒。
   - 文档类的候选有一次判“没解决”，理由也是“可能超过 800 字”。
   - 要让候选通过，组件就得把“附加对照表”“限 800 字”写成长期规则，这正是 ADR 0013 要防的背答案。
2. **评审只看到前 12 个文件，且不知道还有别的文件。**
   - `runOutput` 遍历副本时取到 12 个改动文件就停，其余文件不提，删掉的文件也不提。
   - 整理 20 个文件的任务，评审因此认为“只处理了 12 个”。
3. **偏好评审不知道用户的反馈。**
   - 打平时的偏好评审只看任务原文。它两次都选了基线，理由是基线“保留了标题原样，用户没要求去掉空格”。
   - 对改进作业的反馈原题，用户的长期习惯正是要比的东西。

这三点与题目无关：任何带一次性附加要求的反馈、任何改动超过 12 个文件的任务、任何按反馈改变做法的候选都会受影响。

## 决策

1. **反馈检查只判做法上的问题。**
   - 评审提示写明以下几点：
     - 反馈里只针对那一次的附加要求（任务原文没有的新文件或改动），这次回放没有收到，不要求它；
     - 只判反馈对做法指出的问题，包括反馈里说的长期习惯；
     - 反馈里只有一次性附加要求时，回答 `null`（`unknown`）。
   - 一次性还是长期，由评审按反馈原文判断。产品里不写任何关键词或题目规则。
2. **评审看到完整的改动清单。**
   - `runOutput` 先找出全部改动文件，按路径排序。
   - 前 `OUTPUT_FILES`（12）个给出内容，其余只列路径。
   - 回放副本里被删掉的快照文件单独列出。
   - 两种清单各最多 `OUTPUT_PATHS`（200）条，超出的写明条数。
   - 两个评审提示都写明：只列了路径的文件不算缺失。
3. **偏好评审看到反馈原题的反馈。**
   - 改进作业的反馈原题打平时，偏好评审同时看到反馈原文。
   - 提示写明：反馈里的长期习惯属于用户要求，一次性附加要求不算。
   - 其他用例照旧，不附反馈。
4. **新纪元。** 评价器规则 id 改为 `adr-0015`，纪元 id 随之改变。ADR 0008 第 5 条照常适用：`adr-0014` 纪元的门控结论、父子比较与报告，不与新纪元的放在一起。

## 后果

- 照反馈改了做法、但没有做一次性附加要求的候选，反馈检查可以通过。
- 只做了一次性附加要求、没改做法的候选，不会因此得分。
- 反馈只有一次性附加要求时，反馈检查是 `unknown`。按 ADR 0006 第 7 条，候选这时不会被自动采用。这符合本意：一次性要求不该变成长期能力。
- 一次性与长期的划分交给评审模型判断，可能判错。判错时最多回到修改前的结果（多判为长期），或者让一次性要求不计入（多判为一次性），都不会把一次性要求写进组件。
- 评审提示变长了一些，多了改动清单。改动超过 12 个文件的任务，每次评审多几百个 token。
- 试点计划（`scripts/experiment/step6/pilot/pilot-plan.json`）里 parent 臂写的是 `adr-0014` 纪元。要在新纪元复测，需要用户同意后按新纪元重新冻结。
