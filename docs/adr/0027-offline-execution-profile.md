# ADR 0027：第 3 层的结果怎样装进运行——用户级执行配置、重放副本、外部评审与能力页批准

- **状态**：已接受（只在脚本化模型、运行器与评审下跑过；真实运行等用户开口）
- **日期**：2026-10-19
- **依据**：
  - ADR 0026“后果”里列出的未接线项（候选装进重放副本、外部评审打分、能力页批准、SDK 入口）；
  - 资料库 `docs/handoff/evolution-layer2-3-design.md` §3、§6。
- **替代**：
  - ADR 0026 第 1 条里“装载时作为能力版本的 `context-policy` 文字”一句；
  - ADR 0026 第 5 条里“要用户在能力页批准才写成能力版本生效”一句。
  - 其余各条不变。评价器纪元不变（规则 id 仍是 `adr-0019`）。

## 背景

ADR 0026 原来打算把执行指引写成项目能力版本里的 `context-policy`。这样做有两个问题：

- 离线运行是用户级的，练习题来自多个项目。写进某一个项目的能力版本，范围就不对了。
- 项目采用的 `context-policy` 会按 ADR 0018 第 4 条迁成手册条目，再按 ADR 0023 随机给或不给。评测时整段指引每次都给，实际使用时却拆成条目随机给。评的和用的不是同一个东西。

## 决策

1. **执行配置是用户级的。**
   - 用户批准的版本写在 `<NEXGENT_HOME>/offline-runs/applied.json`，从下一个任务起对所有项目生效。
   - 没有这个文件时，用产品默认值：没有执行指引，检索参数等于原来的常数。
   - 不写成项目能力版本，不迁进手册。
2. **运行时怎样用。**
   - 执行指引在根任务的第一个用户回合，随手册的注入消息给一次。它排在最前，带一行说明“任务自己的要求优先”，不进系统提示。
   - 检索参数决定三件事：
     - 手册每个回合取几条；
     - 相关性的两个门槛；
     - 每个任务最多抽几个启用的技能。
   - 文件没通过 `offlineCandidateProblems` 就不用。
3. **重放副本。**
   - 候选写进副本的 `.nexgent/offline-candidate.json`。
   - 副本只读这个文件，不读已采用的版本。所以起点版本和候选按同样方式评，两边只差候选本身。
   - 门控的重放副本不管跑哪个版本，都写一个 `trial-copy` 标记，`isTrialCopy` 认它。
   - 这同时修了一个已有缺陷：门控基线臂跑在 `baseline` 上时没有采用记录，原来会被当成真实项目，往用户手册、技能库和学习里写东西。
4. **怎样重放一道练习题。**
   - 先找来源项目：按 id 找它的用户数据目录；找不到，就在用户数据目录和最近项目里找 id 相同的项目。
   - 在来源项目当前采用的能力版本上，用门控的副本（快照、配置、资料）重放。
   - 发送的是自评所评那一回合为止的用户消息，用门控的运行器跑，每道题一个进程，审批一律拒绝。
   - 记录写进这次运行自己的账本 `<run>/ledgers/`，不写进项目的账本。
5. **外部评审怎样打分。**
   - 评审模型是 `CALIBRATION_MODEL`，推理开，effort `low`。提示与自评校准用的是同一个（`scorePrompt`），按练习题冻结的评分要点打分。
   - 分数 = `combineScore`，也就是两部分的平均：
     - 检查的通过率：副本里 kernel 为这次运行记下的检查，加上通用检查；
     - 评分要点的得分。
   - 给提案看的反馈是每条要点的得分和评语，以及失败的检查。
   - 以下情况都记为未知结果、0 分，已经花的钱照记：
     - 题目没有评分要点；
     - 题目没跑完；
     - 评审没给出可用的分数；
     - 来源项目或快照找不到。
6. **能力页批准。** 能力页加一栏“离线改进”：
   - **现在在用**：显示当前生效的版本，没有就显示默认设置，都用人话写。已采用的版本可以“停用，回到默认”，要再确认一次。
   - **练习题**：显示各类题的数量。训练、挑选、留出三类都至少有 1 道题，才能“制定新计划”。制定计划不花钱。
   - **同意上限才开跑**：按钮上写着计划的上限，金额必须与计划完全一致。点了以后在后台进程里运行（`offline-entry.js run <runId>`，占着 `<run>/lock`）。
   - **运行中**：可以“停止”，会在当前一步做完后停下；停下或中断的运行可以“继续”。只有超出上限而停下的不能继续，要重新计划。
   - **有推荐时**：把原来的版本和新版本并排显示。“采用”写入 `applied.json`；“不用”只记下用户的回答（`run.json` 的 `decision`）。
   - SDK 对应的方法是 `offline.list / plan / approve / resume / stop / decide / revert`。

## 后果

- 脚本化运行器与评审下的单元测试覆盖：
  - 候选写进副本，副本只读自己的候选；
  - 外部评审打分与反馈；
  - 找不到项目时记为未知；
  - 推荐的版本只在用户采用后才生效，采用后可以停用；
  - 界面上：先计划，同意上限才开始，采用与停用都由用户点按钮。
- 没有跑真实模型。离线运行的费用不进第 1、2 层的学习预算，只受用户批准的上限约束。
- 练习题少的时候，留出关几乎不会通过，结论多半是“没有找到更好的版本”。
- 第 3 层是否带来收益，仍要按 ADR 0019 第 8 条测量，等用户开口。
