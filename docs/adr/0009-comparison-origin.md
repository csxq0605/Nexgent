# ADR 0009：父子比较的起点先找未解决的作业，找不到就退回反馈当时的能力版本

- **状态**：已接受
- **日期**：2026-10-13
- **依据**：用户 2026-10-13 17:40 对“比较新旧两版改进器时从哪个任务起步”的三个选项回复“C”。
- **替代**：ADR 0008 第 4 条“父子比较与采用规则”里关于起点的那一句（“起点：元改进作业开始前最近一个结束的、由反馈触发的能力作业，取它的反馈任务快照、反馈 id、开始时的能力版本与当前纪元”）。ADR 0008 的其余部分全部仍然有效，包括 `decideImprover` 的判定顺序、只比一组、采用与副本保留。

## 背景

按 ADR 0008 的写法，起点是最近一个结束的反馈作业，两臂从它开始时的能力版本起步。「收益测量」用脚本化后端演练时，两类任务的父子比较都是“不采用，没有改进”。

原因是：第 1 个作业已经采用了修复；第 2 个作业开始时项目已经在修复后的版本上，它的反馈问题在这个版本上已经不存在。两臂从这个版本起步，基线直接通过反馈检查，子改进器没有可能赢。只要同一类任务里前一个作业修好了问题，这种情况就会反复出现，测量结论在设计上就注定是“零”。

## 决策

1. **起点分两种，按顺序找。**
   - **未解决（`unresolved`）**：元改进作业开始前结束的、由反馈触发的能力作业里，最近一个“真实作业没能解决反馈”的作业。“没能解决”指作业结束于 `rejected`、`failed` 或 `no-proposal`；但如果作业的门控结论里基线已经通过全部反馈检查（`feedbackPassRate.baseline` 为 1），说明问题在作业开始时已经不存在，这个作业不能作起点。两臂从这个作业**开始时**的能力版本起步。
   - **反馈当时的版本（`feedback-version`）**：找不到未解决的作业时，取最近一个结束的、由反馈触发的能力作业（ADR 0008 原来的选法），但两臂从它的反馈任务**运行时**的能力版本起步，即反馈那一轮之前会话所用的版本（`session.start.capabilityVersion`，其后有 `capability.version` 时取最后一条），没有记录时为 `baseline`。
   - 两种都找不到时不比较，元改进作业失败并写明原因（与 ADR 0008 相同）。
2. **作业开始时的能力版本。**
   - 作业进入提议阶段时记下的 `baseVersion` 就是它开始时的版本，优先用它。
   - 作业在提议前就结束时没有 `baseVersion`，从能力采用历史里取作业开始（离开 `queued` 的时刻；没有时用创建时刻）那一刻生效的版本。不再退回项目当前的版本。
3. **记录。**
   - `ComparisonOrigin` 新增必填字段 `kind`：`unresolved` 或 `feedback-version`。`comparison.json` 的起点与两臂各自读到的起点都写这个字段；`kind` 是起点的一部分，两臂不同即 `origin-mismatch`。
   - 元改进作业的日志与 `comparison.json` 写明这次用了哪种起点。实验报告按 `kind` 标出每组比较的起点种类。

## 后果

- 前一个作业修好了问题时，比较仍然有意义：两臂从问题还在的版本起步，各自要把它修好，比的是谁修得好、谁更省。
- 有未解决的作业时，优先比“旧版没修好的问题”，最能看出子改进器是否解决了父改进器解决不了的问题。
- 反馈当时的版本可能早于项目现在的版本：两臂可能重新修一次项目里已经修过的问题。这是有意的：比较的是改进器，不是能力。
- `ComparisonOrigin.kind` 是 v1 格式内追加的必填字段。步骤 6 之前没有 `comparison.json`，演练产生的旧文件不再通过校验，需要重跑。
