本表回答（9 项决定已由用户 2026-10-12 确认，见文末）：能力包长什么样、存在哪、怎么加载；模型怎样在会话里开发与试用组件，什么算候选；门控怎么比较、什么时候采用、什么时候回滚；账本加什么；做哪些工作包、谁依赖谁、每轮开哪几个讨论串（每轮最多 3 个）；`accept-step4` 检查什么；真实模型验收怎么做、花多少钱；哪些事要用户拍板。

计划 4.7 估计步骤 4 为 3 周；按本表排下来是 4 轮，关键路径是契约 → 能力存储与加载 → 门控。周数是范围估计，不是承诺。

## 目标与退出门槛

步骤 4 对应产品目标 ③：持续积累能力。计划 4.4 原话：任务里开发并试用成功的工具或技能，经门控确认更好之后成为新的采用版本；之后的新会话、新进程自动加载并真正用上它；变差就回滚。DSH 没有“版本化能力集 + 门控采用”，这部分完全由 Nexgent 定义。

退出门槛（计划 4.4 验收原文，按用户 2026-10-11 的 CI 规则与 10-12 的分支规则改写口径）：

1. **跨任务、跨进程实际调用**：任务 A 开发并使用一个工具或技能 → 成为候选 → 门控通过 → 新 OS 进程里的任务 B 自动加载并实际调用它；账本可证（B 的请求带新的 `capabilityVersion`，`task.outcome` 列出该组件，会话里有对应的工具调用或技能加载）。
2. **自动回滚**：人为注入一次退化后，宿主自动把采用版本退回上一版，之后的任务用回旧版本，账本与采用历史可证。
3. **被拒候选留档**：门控判定变差的候选保留完整记录（组件、回放结果、费用、拒绝原因），原版本照常可用。
4. **“CI 绿”的口径**：合并前在云端会话本地跑改动包及依赖方的测试与类型检查；`accept-step4` 无界面层与桌面层在 Linux 本地通过；验收前手动触发一次 Windows 工作流（程序层两平台）。工作流仍只能手动触发。
5. **真实模型一次**：Linux、thinking 开，主链（1、2）跑通；验收记录 `docs/validation/step-4-<日期>.md` 经用户认可。工作留在 `nexgent-app`，不合入 `main`（用户 10-12 选 B）。

## 设计要点

以下是派工的前提。标“待拍板”的在文末列给用户，其余由 W0 在契约 PR 里定稿。

### 能力包与存储

- **组件四类**（计划原文）：
  - 工具：**PTC 函数模块**（一个 JS 模块，导出若干函数，在 `run_code` 的同一种独立 Node 进程里执行，受调用方沙箱约束；每个导出函数注册为一个模型工具，名字带前缀以免与内置工具冲突，调用即留下 `tool.call` 记录）或 **插件包**（Nexgent 插件，在宿主进程内执行，不受沙箱约束）。
  - 技能：SKILL.md 目录。
  - 上下文策略：说明文件文本、压缩阈值、系统提示里允许改写的段落。白名单之外的字段（审批、费用上限、沙箱模式、门控配置）在 schema 层就不存在，候选改不到。
  - 协作方式：预设 JSON、团队模板、架构图。
- **内容寻址**：清单 `manifest.json` 列出每个组件的类型、名字、相对路径与文件哈希；版本号是规范化清单的 SHA-256。`.nexgent/capabilities/<version>/` 一旦写成即不可变，加载前按清单重新校验哈希，不符就当作退化处理（见“回滚”）。
- **基线**：版本 `baseline` 是空能力包，等于步骤 3 交付的行为。
- **采用历史**：`.nexgent/capabilities/activation/` 是移植自 PR #4 的修订链（`<n>.json`，`adopt` / `rollback` 两种修订，`link` 独占发布，比较后发布）。当前采用版本 = 链尾。
- **候选与试验**：`.nexgent/capabilities/candidates/<id>/`（候选内容与来源会话）、`.nexgent/capabilities/trials/<id>.jsonl`（门控回执）、`.nexgent/capabilities/decisions/<id>.json`（采用、拒绝或回滚的结论，含理由与费用）。被拒的候选不删除。
- **作用范围**：项目级（待拍板 1）。

### 加载

- 新会话创建时读取链尾，把能力包的组件交给各插件：技能根目录（优先级：项目 `.nexgent/skills/` > 采用的能力包 > 用户 > 内置）、预设与架构图目录、上下文策略、函数模块注册为工具、已批准的插件包加载为 profile 行。会话的 `session.start` 记下所用版本，账本每条记录带 `capabilityVersion`。
- 同一进程里，采用发生后新建的会话用新版本，已在运行的会话不变。恢复的会话：继续用它记录的版本（若该版本仍完好）；不可用时用当前采用版本并写一条切换记录。
- 加载失败（哈希不符、模块导入失败、清单 schema 不符）不会让应用起不来：退回上一可用版本，写记录，提示用户。

### 任务内开发与试用

- 模型通过新工具在**会话草稿区**写组件（宿主写入 `.nexgent/capabilities/drafts/<sessionId>/`，模型的普通文件工具仍然碰不到这个目录）：`capability_draft`（写或改一个组件）、`capability_try`（把草稿加载到当前会话的作用域：技能出现在本会话的技能列表、函数成为本会话的工具、预设可被本会话的 `delegate` 使用），其他会话看不到。
- 插件包的 `capability_try` 本身就要在宿主进程里执行代码，所以试用前也要人审批，与采用时的审批是两次独立的批准。
- 候选的产生方式：待拍板 2。推荐由模型调用 `capability_propose` 显式提交，宿主核对该组件在本会话里至少被成功调用过一次（账本有无错误的 `tool.call` 或技能加载），否则拒收。
- 成员（委派、队友、工作流）不能开发或提交组件，沿用 ADR 0004“成员禁用协作工具”的做法，把三个新工具加入禁用表。

### 门控 `capability_trial`

- **回放集**：从项目历史任务自动构造，每条 = 任务首条用户消息 + 资料 + 任务开始时的项目快照 + 该任务的确定性检查。快照要求宿主从步骤 4 起在每个根任务开始时记录（待拍板 7）。selection 集含产生候选的任务及同类任务，guard 集是其他历史任务，两者不重叠（移植 PR #4 的校验）。历史不足时门控等待，不降低门槛（计划 4.5）。
- **运行**：候选与基线在每条回放上各跑 r 次，每次在项目快照的临时副本里、经 SDK 起独立进程运行，互不影响，不写回真实项目；试验请求在账本里带 `trialId` 与 `arm: candidate | baseline`，与正常任务分开统计。
- **判定**：
  - 确定性检查：成果文件存在、按类型能解析（JSON、xlsx、CSV 列）、原任务里通过的测试命令重跑仍通过。宿主在每个任务结束时也跑同一组检查，写进 `task.outcome.checks`。
  - 审核模型：读两侧成果给出偏好与理由；在证据里与确定性检查分开标记（计划 4.4），只在确定性检查打平时作为“质量上升”的依据。
  - 无法比较的运行（取消、出错、超时）记 `unknown`，不当作失败也不当作通过；有 `unknown` 的试验不采用。
  - 采用条件（计划原文）：质量不降且成本下降，或质量上升且成本在上限内；guard 集上质量不降。参数（n、r、成本上限）待拍板 4。
- **触发**：待拍板 3。推荐任务结束后自动在独立进程里开始，受每个候选的试验额度约束；CLI 与桌面可查看进度与结论。
- **候选改不到门控**：门控配置、审批、费用上限、沙箱模式只存在于 `.nexgent/config.json` 的宿主字段（写入这些字段属于始终审批），能力包 schema 里没有对应位置。
- **插件包**：门控通过后不自动采用，进入“等待审批”状态；人批准才写采用修订（计划 4.9 #5 已定每次审批）。

### 回滚

- 两种触发（待拍板 6）：
  1. **加载退化**：采用版本校验或加载失败 → 立即写 `rollback` 修订回到上一版本。
  2. **使用退化**：采用后的前 K 个使用新版本的根任务里，确定性检查的通过率低于门控时基线的通过率，或新组件的调用连续出错 → 自动写 `rollback` 修订。
- 回滚只追加修订，不删除任何版本；回滚记录写明触发原因与证据（任务 id、检查结果）。
- “人为注入退化”的验收做法：改坏已采用的组件（函数模块抛错或技能给出错误步骤），或直接篡改能力包文件触发哈希校验失败，两种都检查。

### 账本

- 所有 `llm.request.*`、`tool.call`、`task.outcome` 写 `capabilityVersion`。
- `task.outcome` 新增：`componentsUsed`（实际调用的能力包组件：类型、名字、所属版本）、`memberCosts`（根会话汇总每个成员的 token 与请求数）；`checks` 由宿主填。
- 试验请求带 `trialId` 与 `arm`；采用、拒绝、回滚各写一条 `capability.*` 记录（或写进采用历史并在账本留引用，由 W0 定）。

## 范围

**做：**

1. 契约与规范：`CapabilityBundle` 清单、四类组件 schema、采用历史、候选、试验回执、决定记录；账本与会话新字段；`data-formats.md` §`CapabilityBundle` 清单、`permissions.md` §插件安装审批与能力包组件的执行边界；ADR 0005。
2. `@nexgent/capabilities`：内容寻址存储、哈希校验、采用历史（移植 activation）、草稿区、`capability_draft / try / propose` 三个工具、加载器、插件包的审批与加载。
3. 各插件接入能力包来源：skill、preset、workflow 架构图、context 策略、ptc 函数模块。
4. kernel：新会话解析采用版本、会话作用域注入、`capabilityVersion` 写入、`componentsUsed` 与 `memberCosts`、任务开始快照、任务结束确定性检查。
5. 门控：回放集构造、隔离运行、判定、采用与拒绝、使用退化监测与回滚、试验额度。
6. SDK、CLI、桌面：能力版本查询、候选与试验状态、插件包审批、手动回滚；`nexgent capabilities list / show / trial / rollback`；桌面右栏显示当前版本与候选状态，插件包审批对话框。
7. `accept-step4` 三层、真实模型验收、Windows 手动运行、验收记录、README。

**不做：** 桌面应用完整的“改进”页、自动诊断与提案、反馈触发（步骤 5）；改进器自身的版本化与递归（步骤 6）；跨项目或用户级共享能力包（若用户在拍板 1 选项目级）；插件包从 npm 安装、依赖构建脚本与版本豁免（DSH `plugin-manager` 的这些部分不需要，插件包只能是能力包内的本地模块）；热重载已在运行的会话；步骤 4 之前的历史任务进入回放集（没有快照）；安装包签名与自动更新。

## 轮次安排（每轮最多 3 个讨论串）

## 中期检查点（第 2 轮末）

脚本化 provider、Linux 本地：

1. 任务 A 在会话里写一个技能和一个函数模块，`capability_try` 后调用成功，`capability_propose` 生成候选；另一个同时运行的会话看不到这两个组件。
2. 用存储接口手动写一条采用修订后，新进程里的任务 B 自动加载并调用该函数；B 的账本记录带新版本，`task.outcome.componentsUsed` 列出它。
3. 篡改采用版本的一个文件，下一次加载退回上一版本并留下记录。
4. 任务结束时 `task.outcome.checks` 有宿主跑出的检查，任务开始时有快照。

判定：四项满足则第 3 轮开「门控」与「SDK 与桌面」；第 1 或 2 项不满足时「能力版本」延长一轮，「门控」可先对存储接口与假运行器开发。

## 真实模型验收

**任务族。** 表格 / 数据（计划 4.9 #8 已定的步骤 6 任务族之一，步骤 4 先用它）。素材由 `scripts/real-task/step4-*` 确定性生成：一个项目里有若干份同结构的订单 CSV。历史任务 R01 各做一份月度汇总；任务 A 再做一份，并要求“把汇总步骤做成以后可复用的函数或技能”（待拍板 8）；任务 B 换一份新数据做同样的汇总，不提示组件存在。隐藏判定从夹具独立算期望值。

**运行方案。** Linux 云端会话，开 thinking，用环境变量 `NEXGENT_API_KEY`。按推荐参数（selection 2 条、guard 1 条，每侧 r = 2）一次门控是 12 次任务运行加 12 次审核调用。

**预估费用。** 步骤 3 的补货任务每次约 0.09–0.19 美元。估计：R01 两次约 0.3；R02 约 0.3；R03 约 12 × 0.15 + 审核 12 × 0.03 ≈ 2.2；R04 约 0.2；R05 两三次任务约 0.5。主链合计约 3.5 美元；修复后重跑按最多一轮算，不超过约 8 美元。建议预算上限 **15 美元**，由脚本设置试验额度与 `costCaps` 并在累计估算超过上限时拒绝开始新运行。这是估算，不是账单；审核模型若改用更强模型（待拍板 5），R03 的审核部分约翻三到五倍。

## 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 日常任务多数没有 oracle，确定性检查只能查“文件在、能解析、测试命令过” | 两侧检查常常打平，门控退化为“只比成本”或依赖审核模型 | 审核意见单独标记、只在打平时使用；验收记录写明哪些结论来自审核模型 |
| 新组件让成本略升而质量持平 | 按计划的采用条件会被拒，真实模型 R04 可能走不到 | 如实记录；不为过验收放宽规则；R04 未满足时回到 R02 调整任务提示后重跑，或请用户决定 |
| 回放需要快照，大项目快照成本高 | 磁盘占用、任务开始变慢 | 内容寻址去重，只存工作区文件（遵守忽略规则），设大小上限，超限任务不进回放集并留记录 |
| 回放运行与真实项目共用外部资源（网络、端口、全局缓存） | 试验影响真实环境或彼此干扰 | 临时副本 + 独立进程 + 沙箱；`web_fetch` 与 `run_code` 的网络风险沿用步骤 3 的已知边界并写进验收记录 |
| 插件包在宿主进程内执行 | 审批后的恶意或错误代码能做任何事 | 每次审批（已定）；对话框写明这一点；验收主链只用技能与函数模块 |
| 门控只看少量回放与 r = 2 | 误采用或误拒绝 | 使用退化回滚兜底；所有决定可查、可手动回滚；步骤 6 再做统计检验 |

| 试验额度以 token / 请求数计，没有美元 | 费用上限不直观 | 摘要里同时给出估算美元，判定只用 token 与请求数 |

## 已定的决定（用户 2026-10-12）

计划 4.9 早已定下、本表沿用：插件包每次审批，技能与 PTC 函数自动采用（#5）；真实模型只设预算上限；改进与审核允许开 thinking（#6）。下列 9 项用户 2026-10-12 回复“都可以”，全部按推荐执行；上文标“待拍板”的地方以本节为准。

1. **作用范围**：项目级（`.nexgent/capabilities/`），不做跨项目共享。
2. **候选产生**：模型调用 `capability_propose` 显式提交，宿主核对本会话内至少成功调用过一次。
3. **门控时机**：任务结束后自动在独立进程里运行，受每候选试验额度约束；CLI 与桌面可查看。
4. **门控参数**：selection 至少 2 条、guard 至少 1 条（不足则等待），每侧 r = 2；质量以确定性检查通过率为主，审核意见只在打平时用；成本上限为基线的 1.2 倍。
5. **审核模型**：`claude-sonnet-5-5`、thinking 开，配置里可改为 `claude-opus-5-5`。
6. **自动回滚**：加载校验失败立即回滚；采用后前 3 个任务的检查通过率低于门控时的基线，或新组件连续出错，自动回滚。
7. **任务快照**：步骤 4 起宿主在每个根任务开始时记录内容寻址快照（`.nexgent/snapshots/`，去重，单个上限 200 MB）；之前的历史任务不进回放集。
8. **真实模型任务 A**：明确要求“把汇总步骤做成可复用的函数或技能”；模型自己提出改进留到步骤 5；验收记录写明。
9. **插件包**：做格式、两次审批（试用与采用）、加载与卸载，用脚本化测试覆盖；验收主链只用技能与函数模块。
