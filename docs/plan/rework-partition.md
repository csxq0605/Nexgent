## 0. 主线（一段话）

进化要成立，需要三样东西按顺序到位：**一把可靠的尺子**（每个任务都自评，用户真实任务组成练习题集），**能积累的载体**（经验手册 → 技能库 → 执行框架），**不把代价压给普通任务**（取证只在需要时、增量地做，学习花费告知、封顶、看得见）。界面最后把这些说成人话：“最近学会了什么、为什么没启用、要不要你决定”。长任务鲁棒性、权限、协作这些审查项按“哪一层进化依赖它”插进主线：第 1 层要先有轻的主路径和按相关性注入；第 3 层要进化默认工作流，所以协作语义要先修好。

## 2. 总原则（所有工作包都适用）

1. **Nexgent 是通用 agent。** 产品代码、系统提示、改进器 v0、评分要点生成说明里，不出现为某个用例或某类任务写的规则、例子、默认值。每个 PR 写一句“为什么对任何任务都成立”。
2. **用例只用来测量。** 看到实验结果后，不改产品迎合某道题，也不改题迎合产品；要改就作废这一轮、换新 id。
3. **评价器不归被改进的一方改。** 评分要点、可靠性门槛、预算、开关，改进器和第 3 层都改不了。
4. **结果不好就分析，不停手。** 某层打平或变差时，用日志找根因，修通用缺陷，再提复测，不能只报告“没效果”。
5. **测试通过不等于目标达成。** 重做的退出条件是 §9 的判据和用户在 Mac 上亲手试过，不是脚本全绿。
6. **工作分支与合入**：工作留在 `nexgent-app`，不碰 `main`；一个讨论串一项任务一个 PR，所属讨论串本地跑改动包及其依赖方的测试与类型检查后自己合入；CI 只能手动触发；commit 与 PR 只署 `csxq0605 <wsu0605@gmail.com>`。
7. **真实模型花费**：每个包写明估算与上限；超出上限或表里没有的花费先问用户；深度改进每次运行单独问（§10）。

## 4. 冲突与取舍

| # | 冲突 | 选择 | 理由 |
| --- | --- | --- | --- |
| 1 | 审查建议 `autoImprove` 默认关；进化方案要每个任务自动自评和学习 | 学习默认开，首次告知一次，预算封顶，花费可见，随应用停（ADR 0017 第 3 条） | 用户批准了“允许自评”和 3 美元日常预算；审查担心的是不知情、花费远超任务、关了还在跑，这四条逐一解决 |
| 2 | 调研举例“一天 10 个任务后台多花 0.3–0.5 美元”，按月是 9–15 美元，超过 3 美元预算 | 单任务自评上限 0.05 美元；预算不够时按“有用户反馈 → 检查失败 → 随机抽样”取样；确定性检查总是跑 | 预算是用户定的，不能悄悄突破；取样保住最有信息量的任务 |
| 3 | 审查要求去掉每轮快照（P5）；练习题集需要输入快照 | 只在学习开启时、任务开始时拍；按内容增量（只哈希变化的文件），遵守 `.gitignore`；结束时不再拍；按保留规则回收 | 练习题只需要“开始时的输入”；结束状态由工具层的写入记录给出 |
| 4 | 审查说宿主偷跑测试不对（E4）；自评要确定性检查 | 不在用户项目里重跑；检查在后台的项目副本里、按沙箱和审批规则跑，或直接用本轮模型自己跑测试的记录 | 主路径零额外等待，安全规则不绕开 |
| 5 | 审查说组件全量注入（P12、D9）；手册要注入 | 同一个机制：按相关性检索前 k 条，放在首条用户消息之前，不进系统提示 | 一次改完；不进系统提示也解决 P28 缓存失效 |
| 6 | 调研要按向量检索；Claude Platform 没有向量接口 | 本地词法检索（中英文分词加 BM25 一类） | 不引入第二个模型供应商；命中率进测量报告，不够再由新 ADR 改 |
| 7 | 调研说评分要点由外部评审生成；每个任务都调 opus 太贵 | 产品里用执行模型生成并打分；opus 只做抽样校准和测量，一致率低于 80% 暂停自动启用 | 预算内可行，可靠性由校准兜底 |
| 8 | 根因分析的复测是 4 臂约 80 美元；调研是 6 臂、按层分开 | 用调研的 6 臂与按层的检查点；第 1 层冒烟 ≈8 美元，第 1、2 层正式实验 ≈80 美元，深度改进复测另算 | 每层各自能停，花费分段批准 |
| 9 | 数据移出项目（P7）与“经验和技能用户级共享”都要改存储布局 | 一次规划：C1 同时定 `<NEXGENT_HOME>/projects/<projectId>/` 与用户级的手册、技能、练习题、改进器目录 | 布局只迁移一次 |
| 10 | 系统审查 P1–P4 由「kernel 维护」在做，K1 也改 kernel | K1 等 K0 合入后开工 | 同一讨论串顺序做，不撞文件 |
| 11 | PR #169 改了渲染层；D1 要重排渲染层 | #169 先合入，D1 在其上开工 | #169 的修复是通用的（副本带齐资料、临时目录不进最近项目、中文加粗），重做后仍需要；先合避免大冲突 |
| 12 | 旧验收 `accept-step5`、`accept-step6` 期望“3 条信号触发”“反馈检查当质量” | 这些项退役或改写，「测试与 CI」先列清单与理由交用户，再删 | 沿用“过时测试删除前先列给用户”的规则 |

| `scripts/accept-*.mjs`、`scripts/accept-common/**`、README、CLAUDE.md | 「测试与 CI」 |
| 根目录共享文件（`package.json`、`pnpm-workspace.yaml`、`tsconfig*.json`、`.github/workflows/`、`.gitignore`） | 集成者；需要改时在 PR 里单列 |

同一文件同时只由一个讨论串改。跨包的小改动由归属讨论串接一个小 PR。

## 13. 风险

| 风险 | 应对 |
| --- | --- |
| 自评不可靠，sonnet 评 sonnet 强化自己的错误 | 外部评审抽样校准，低于 80% 暂停自动启用；检查点 1 不过就先修自评 |
| 第 1 层仍然和笔记组打平 | 按总原则 4 分析根因（检索命中、条目质量、计数信号）；必要时提前做第 2 层的可执行载体；不改题 |
| 3 美元预算下学得太慢 | 取样优先级保住有反馈和失败的任务；报告学习速度；需要时请用户调预算 |
| 词法检索命中率低 | 命中率进报告；不够时新 ADR 再议 |
| 数据迁移损坏旧项目 | 复制后校验，旧数据不删；失败照旧读旧位置 |
| bash 沙箱在三个平台不同 | 先 macOS 与 Linux；Windows 不声称有系统沙箱，保留路径策略 |
| 「kernel 维护」是关键路径（K0–K6） | K 包都小而独立；其余讨论串与它并行；需要时由协调者临时再开一个 kernel 分支讨论串，按文件归属切分 |
| 新纪元后旧结果不可比 | 报告只比较同纪元结果，旧试点只作历史 |
| 深度改进花费超出估算 2 倍 | 每次运行前给上限，到闸门即停 |
| 界面先做完、内容还是内部术语 | D2 与 E1、G1 同轮验收，`strings.ts` 术语检查 |

## 14. 第一批可以马上并行派出的工作包

「kernel 维护」的 K0 已在运行，所以按 3 个讨论串的上限：

1. **C1 契约与规范一（「步骤三契约」）**：第 2 轮三个包都依赖它，先做。
2. **D0 → D1 合入 #169，界面第一轮（「SDK 与桌面」）**：与进化无关，可以马上开工。
3. **M1 做法类练习题族（「收益测量」）**：K0 合入后开工，或用户允许同时运行 4 个讨论串时马上开工；它是检查点 1 和 2 的长线准备。
