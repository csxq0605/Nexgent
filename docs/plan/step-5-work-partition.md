## 目标与退出门槛

步骤 5 对应产品目标 ③ 的“默认”部分：用户不写评测配置、不点名能力工具，只是照常用 Nexgent 并给反馈，系统就会在后台诊断问题、提出一个候选能力、用步骤 4 的门控比较，更好就采用，之后的任务自动用上。计划 4.5 验收原文：从 Main 提出反馈 → 看到候选 → 看到门控结果 → 下一次任务使用新版本（或看到拒绝原因）；全程不改配置文件。

退出门槛（按用户 2026-10-11 的 CI 规则与 10-12 的分支规则改写口径）：

1. **反馈闭环**：在一个项目里照常完成任务并给反馈（不点名能力工具），累计到触发条件后，后台自动开始改进作业，产出诊断、一个候选与门控结论，用户在桌面“改进”页与 `nexgent improve` 里看得到。
2. **下一次任务使用新版本**：门控采用时，新 OS 进程里的下一次任务自动加载并实际调用新组件，账本可证；门控拒绝时，拒绝原因可查，原版本照常可用。
3. **全程不改配置文件**：用户只用到“自动改进开 / 关”和改进预算两个设置，且都在设置页里改；回放集与检查由宿主从项目历史自动构造。
4. **“CI 绿”的口径**：合并前在云端会话本地跑改动包及依赖方的测试与类型检查；`accept-step5` 无界面层与桌面层在 Linux 本地通过；验收前手动触发一次 Windows 工作流（程序层两平台）。工作流仍只能手动触发。
5. **真实模型一次**：Linux、thinking 开，主链（1、2）跑通；验收记录 `docs/validation/step-5-<日期>.md` 经用户认可。工作留在 `nexgent-app`，不合入 `main`（用户 10-12 选 B）。

## 设计要点

以下是派工的前提。标“待拍板”的在文末列给用户，其余由 W0 在契约 PR 里定稿。

### 触发与作业

- **三种触发**（计划原文）：
  1. 反馈：一条计入的反馈让项目的反馈计数加一，到 N（4.9 #7 已定 N = 3）就开始一个作业，计数清零。哪些反馈计入：待拍板 2。
  2. 显式“改进”：用户在成果卡片或“改进”页点“改进”，或 `nexgent improve run`，立即开始，不看计数。
  3. 检查失败：根任务结束时 `task.outcome.checks` 有失败项，计一次。
- **计数持久**：计数存在 `.nexgent/improvements/queue.json`，用“已计入的反馈 id 集合”而不是一个数字，重启、并发进程都不会重计或漏计。
- **作业**：`.nexgent/improvements/<jobId>/`，里面有 `job.json`（触发原因、引用的反馈与任务、状态、各阶段费用）、`diagnosis.json`、作业日志；候选、试验与决定照旧写在 `.nexgent/capabilities/` 下，作业只存引用。
- **状态**：`queued → diagnosing → proposing → trialing → adopted | rejected | awaiting-approval | no-proposal | waiting-history | budget-exhausted | failed | interrupted`。`waiting-history` 是门控历史不足时的等待，历史补足后继续（计划 4.5：等待而不是降低门槛）。
- **运行方式**：照 `GateHost` 的做法起分离进程；同一项目同时只有一个作业，作业进行中到达的反馈计入下一批（待拍板 8）；作业进程被杀后，下次启动标为 `interrupted`，不自动重跑，用户可手动再点“改进”。
- **开关与预算**：`autoImprove` 只管“反馈与检查失败是否自动开始作业”，显式“改进”不受它限制（但受预算限制）。改进预算按 token 计，覆盖诊断、提案与门控三段；用尽即停，作业记为 `budget-exhausted`。默认值与是否审批：待拍板 1、6。

### 诊断

- **独立会话**：改进作业在项目的一个“改进会话”里运行（`session.start` 标 `purpose: improvement`、带 `jobId`），不出现在对话列表里，只在“改进”页可点开查看。模型与 thinking：待拍板 5。
- **只读工具**（只给改进会话）：读某个会话的记录切片（按轮、按记录类型，有字节上限）；读账本切片（按 taskId、memberId、capabilityVersion）；列出反馈。改进会话没有写项目文件、执行命令的工具。
- **输出**：模型调用 `improve_report_diagnosis` 交一份结构化诊断，宿主按 schema 校验，不符就要求重写，最多 3 次，仍不符记 `failed`：
  - `failureTypes`：MAST 三类标签（规格与系统设计、成员之间不一致、任务验证与终止），每条附证据（会话 id、轮、记录序号）；
  - `involved`：涉及的成员、工具、技能、能力组件；
  - `memberCosts`：按成员的 token、请求数与贡献（从账本汇总，宿主算，模型只能引用）；
  - `hypothesis`：一句话说明“缺什么能力导致了这个反馈”；
  - `proposalKind`：建议的组件类型（四类七种之一）或 `none`（诊断认为不是能力问题，例如反馈是需求变更）。`none` 时作业以 `no-proposal` 结束。

### 提案

- 一个作业只提一个候选，一个候选只含一个新增或修改的组件，组件必须符合步骤 4 的 schema（上下文策略仍是封闭白名单，改不到审批、费用、沙箱、门控、自动改进字段）。
- 产出方式（待拍板 3，推荐 A）：
  - **A. 在快照副本里重做**：改进会话转到提案阶段，宿主把反馈任务开始时的快照复制成临时项目，在里面用原任务的用户消息重新执行；改进会话可用 `capability_draft / try / propose`，宿主沿用步骤 4 的规则（组件在试用后至少成功用过一次）。好处是提案一定是“真用过”的组件，和步骤 4 的证据口径一致。
  - B. 只输出组件文件：模型直接交组件内容，宿主只做 schema 校验，不要求试用。便宜，但候选可能根本跑不起来，要靠门控淘汰。
- 候选记录增加来源：`origin: improvement` 与 `jobId`（步骤 4 的候选是 `origin: session`）。

### 门控（在步骤 4 的门控上改）

- **回放集**：selection 必含触发作业的反馈任务，再按步骤 4 的相似度补足；guard 照旧取不相似的历史任务；不重叠校验照旧。历史不足时作业停在 `waiting-history`。
- **回放截断**：反馈任务只回放到第一条反馈之前的轮次（反馈轮的内容是“用户事后指出的问题”，候选侧要在不被提醒的情况下做对）。这依赖“每轮的检查与快照分开记”（待拍板 7）。
- **反馈检查**（待拍板 4）：反馈任务的两侧成果各交给评审模型，问“这份成果是否已经解决了反馈指出的问题”，得出 `pass / fail / unknown`。证据里与确定性检查分开标记（计划 4.4 的口径）。
- **采用规则**：确定性检查与 guard 规则不变（ADR 0005 决策 5）。若按推荐把反馈检查计入质量，需要一份新 ADR 0006 取代 ADR 0005 的决策 5（决策不改旧文）。
- **费用**：试验回执与作业记录写估算美元（待拍板 9），判定仍只用 token 与请求数。

### 采用之后

- 采用、拒绝、等待审批照步骤 4。作业记录追加“首次被使用”：采用后第一个带新版本、且 `componentsUsed` 里出现该组件的根任务（taskId、时间）。“改进”页据此显示“何时被后续任务使用”。
- 使用退化回滚照步骤 4 的规则，回滚时作业状态旁注明“已回滚”。

### 账本

- 改进会话与它起的回放运行，账本记录带 `improvementId` 与 `improvementPhase: diagnose | propose | trial`；费用计入改进本身（ADR 0001 决策 5），与正常任务、普通门控试验分开统计。
- 每个作业结束写一条 `improvement.end` 记录（状态、各阶段费用、候选与决定的引用）。

## 范围

**做：**

1. 契约与规范：改进作业、诊断、提案来源、触发计数、`improvementId` 与阶段字段、反馈检查、`improvement.end`；配置的改进预算与开关；`data-formats.md` 新增改进作业一节并补 `trials/` 旁路文件；`permissions.md` 写改进会话的工具边界与预算审批；`capability/*` 错误码；SDK API 版本 5；ADR 0006。
2. `@nexgent/evolve`：触发与计数、作业宿主（分离进程、锁、恢复）、诊断会话与只读工具、提案（快照副本重做或直接输出，按拍板）、与门控的交接、预算。
3. kernel：每轮的检查与快照分开记（按拍板 7）、改进会话的 `purpose` 与工具集、账本新字段、检查失败的触发信号、只读查询的底层读取（会话切片、账本切片）。
4. 门控：反馈任务进 selection、回放截断、反馈检查、估算美元。
5. SDK、CLI、桌面：`improvements.*` API 与事件；`nexgent improve list / show <id> / run`；桌面“改进”页、成果卡片上的“改进”按钮、设置页的“自动改进”开关与预算。
6. `accept-step5` 三层、真实模型验收、Windows 手动运行、验收记录、README。

**不做：** 改进器自身的版本化、元提案与递归（步骤 6）；跨项目共享改进结果；自动生成新的确定性检查（ADR 0005 已列为不做，反馈检查由评审模型做，不改成生成代码）；对已在运行的会话热更新；Python SDK；安装包签名与自动更新；多个作业并行。

### W2 `@nexgent/evolve`（「改进流程」，新开）

- **第一部分（第 1 轮）：** 计数（反馈 id 集合，跨进程独占更新）、三种触发、作业目录与状态机、作业宿主（分离进程、`.lock`、日志、启动时把中断的作业标为 `interrupted`）、预算闸门；诊断与提案先用桩。
- **第二部分（第 2 轮）：** 诊断会话（提示参考 DSH `auto-review` 的分段写法，schema 校验与最多 3 次重写）；提案（按拍板 3）；候选写 `origin: improvement`；交给门控；记录“首次被使用”。
- **完成标准：** 2 条计入的反馈不开始、第 3 条开始；同一反馈重复提交不重计；两个进程同时提交反馈只开一个作业；作业进程被强杀后下次启动标为中断且不重跑；诊断不合 schema 3 次后作业 `failed`、不产生候选；`proposalKind: none` 时 `no-proposal`；提案多于一个组件或碰到受保护字段时被拒；预算用尽即停。

### W3 门控（「门控」）

- **职责：** selection 必含反馈任务；反馈任务回放截在第一条反馈之前；反馈检查（评审模型读两侧成果与反馈原文，A/B 位置按轮次交换，结果与确定性检查分开记）；按拍板 4 接入采用规则；试验回执与决定写估算美元。
- **完成标准：** 脚本化“该改进”候选在反馈检查上候选侧通过、基线侧不通过并被采用；反馈检查 `unknown` 时不采用；回放里看不到反馈轮的文字；guard 规则与步骤 4 相同；`accept-step4` 门控场景继续通过。

### W4 SDK、CLI 与桌面接入（「SDK 与桌面」）

- **职责：** SDK 实现 W0 的 `improvements.*` 与事件；CLI `nexgent improve list / show <id> / run [--deliverable <id>]`，`nexgent run` 结束时若开始了作业就打印一行；桌面“改进”页（每个作业：触发原因、诊断摘要、候选改了什么（组件差异）、门控结果（两侧检查、反馈检查、评审意见单独标记）、费用、是否采用、何时被后续任务使用、失败或拒绝原因），成果卡片与反馈框旁的“改进”按钮，设置页“自动改进”开关与改进预算，改进会话只读查看。

- **职责：** 脚本化剧本（“该改进”：反馈指出缺一列，提案一个技能后候选侧补上；“不是能力问题”：诊断给 `none`；“提案跑不起来”：组件试用失败）；反馈夹具（一个带若干历史任务、快照与反馈的项目）；`scripts/accept-step5.mjs` 沿用 step4 的结构；真实模型脚本与费用闸门；Windows 手动运行；验收记录与 README。
- **完成标准：** 每个检查项有能失败的反例测试；未接通的项报 `not-implemented`、退出码 2；真实模型脚本在没有密钥时退出码 2。

## 中期检查点（第 2 轮末）

脚本化 provider、Linux 本地：

1. 同一项目里 3 条计入的反馈后，后台自动开始一个作业；第 2 条时没有作业。
2. 作业的诊断会话交出合 schema 的诊断，读不到也写不了项目文件以外的东西。
3. 提案阶段产出一个 `origin: improvement` 的候选，组件在提案阶段被成功用过（按拍板 3 的 A），真实项目文件不变。
4. 反馈轮有自己的检查记录，原轮的检查没有被覆盖。

判定：四项满足则第 3 轮开「门控」与「SDK 与桌面」；第 1 或 3 项不满足时「改进流程」延长一轮，「门控」可先对假候选开发。

## 真实模型验收

**任务族。** 表格 / 数据（4.9 #8 已定的步骤 6 任务族之一，沿用步骤 4 的订单夹具生成器，素材由 `scripts/real-task/step5-*` 确定性生成）。反馈任务的隐藏判定从夹具独立算期望值；三条反馈都指向同一个可查的问题（措辞不同），这样“问题是否解决”有确定答案。

**运行方案。** Linux 云端会话，开 thinking，用环境变量 `NEXGENT_API_KEY`。改进模型按拍板 5。门控参数沿用步骤 4（selection 2、guard 1、每侧 r = 2）。

**预估费用。** 依据步骤 4 第 6 次运行：普通任务每次约 0.05–0.13 美元，一次门控（12 次回放）约 0.92 美元。估计：

| 项 | 估算（美元） |
| --- | --- |
| R01 历史任务 3 个 | 约 0.3 |
| R02 反馈任务 + 3 个反馈轮 | 约 0.4 |
| R03 诊断（读会话与账本，thinking 开） | 约 0.2–0.4 |
| R03 提案（快照副本里重做一次任务并试用组件） | 约 0.2–0.3 |
| R04 门控 12 次回放 + 反馈检查 4 次 + 可能的评审 | 约 1.1 |
| R05 下一次任务 | 约 0.1 |
| 主链合计 | 约 2.3–2.6 |
| R07 第二个作业（复用历史，另加反馈、诊断、提案、门控） | 约 1.8 |

主链加 R07 约 4.5 美元；步骤 4 用了 6 次运行才走通，按修复后重跑两轮算，合计不超过约 10 美元。建议预算上限 **15 美元**，由脚本设置改进预算、试验额度与 `costCaps`，累计估算超过上限时拒绝开始新运行。这是估算，不是账单；改进模型若改用 `claude-opus-5-5`（拍板 5），诊断与提案部分约翻三到五倍，主链约增加 1–2 美元。

## 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 反馈常常是需求变更，不是能力缺口 | 诊断硬造一个组件，门控里白花钱 | 诊断允许 `proposalKind: none`；`no-proposal` 是正常结论，不算失败；真实模型 R02 的反馈选“下次也该做到”的那类问题 |
| 反馈检查由评审模型判定，没有 oracle | “更准”的结论来自模型判断 | 证据里单独标记；真实模型层用隐藏判定独立复核 R05；验收记录写明哪些结论来自评审模型 |
| 回放截在反馈之前，候选侧仍可能做不到 | 门控拒绝，R05 走不到 | 如实记录；不为过验收放宽规则；按步骤 4 的做法，先查是不是产品缺陷，再决定是否调整任务后重跑，或请用户决定 |
| 诊断与提案读大量会话，token 多 | 改进本身比收益贵 | 查询切片有字节上限；改进预算闸门；费用计入改进本身并单列，步骤 6 再看能否被后续任务摊薄 |
| 计数与作业在多进程（桌面与 CLI 同时开）下重复 | 重复作业、重复花钱 | 计数用反馈 id 集合与独占更新；作业宿主用锁；H15 固定 |
| 每轮检查改变 `taskId` 或检查记录的语义 | 步骤 4 的回放集与使用回滚读错 | 拍板 7 推荐“任务 id 不变、检查与快照按轮记”，旧数据仍按任务读；`accept-step4` 作为回归 |
| 提案在快照副本里重做任务 | 提案阶段的费用接近一次任务；需要快照存在 | 计入改进预算；快照缺失（步骤 4 之前的任务）时作业以 `waiting-history` 或 `failed` 结束并写明原因 |
| thinking 回放依赖 beta 头 | 改进会话试用组件后的请求可能 400 | 沿用 #97；真实层出现即按 unknown 记录并修补 |
| 默认开启自动改进会产生用户没想到的费用 | 费用意外 | 改进预算默认值保守；设置页与“改进”页都显示本月已用；写入预算需审批（拍板 6） |

每条都有推荐；回“按推荐”即全部按推荐执行。

| # | 事项 | 推荐 | 其他选项 | 影响 |
| --- | --- | --- | --- | --- |
| 1 | 自动改进默认开还是关 | **默认开**（步骤名就是“默认的反馈改进流程”；现在 `autoImprove` 默认 `false`，改为 `true`），设置页可关 | 默认关，用户手动开 | 是否“不改配置也能用上”；默认费用 |
