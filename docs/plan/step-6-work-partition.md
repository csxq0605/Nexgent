## 目标与退出门槛

步骤 6 对应产品目标 ④“递归改进”：步骤 5 让 Nexgent 能根据反馈改进自己的能力（技能、工具、上下文策略、协作方式），步骤 6 让“负责改进的那部分”（改进器）也能被改进，并且用一份可复现的报告如实回答：这样做到底有没有带来收益、花了多少钱。计划 4.6 验收原文：一份可复现报告，同时给出能力激活证据、holdout 效果、费用与失败／缺测；没有收益时明确写出。

退出门槛（沿用步骤 5 的 CI 与分支口径）：

1. **改进器有版本**：步骤 5 的改进流程整理成默认改进器版本 v0，行为不变（`accept-step5` 在 v0 下照常通过）；改进器版本按内容寻址，有采用历史，可回滚。
2. **元改进闭环**：系统对改进器自身提出一个类型化改动，得到子改进器；子改进器在项目副本里实际承担一次改进作业、产生后代候选；父、子从同一起点各自产生后代，按固定规则比较，更好才采用；采用后下一次真实改进作业由新改进器执行，作业记录与账本可证。
3. **评价器冻结**：门控的采用规则、反馈检查的评审设置、隐藏判定与 holdout 集合在一个纪元内不变，父子比较和报告不跨纪元；改进器改不到它们。
4. **可复现报告**：两个任务族（表格 / 数据、多文件代码），`dev / selection / guard / holdout` 不重叠，holdout 只用于报告，每个 holdout 用例每臂至少 3 次重复；费用包含改进与元改进本身；写出开发费用能否被后续任务摊薄；结果按正、零或负如实写。报告由脚本从原始记录重新生成，内容一致。
5. **“CI 绿”的口径**：合并前在云端会话本地跑改动包及依赖方的测试与类型检查；`accept-step6` 无界面层与桌面层在 Linux 本地通过；验收前手动触发一次 Windows 工作流（程序层两平台）。工作流仍只能手动触发。真实模型实验在 Linux、thinking 开；验收记录 `docs/validation/step-6-<日期>.md` 经用户认可。工作留在 `nexgent-app`，不合入 `main`。

## 设计要点

以下是派工的前提。标“待拍板”的在文末列给用户，其余由 W0 在契约 PR 里定稿。

### 改进器版本（改进器也是能力包）

- **改进器文件**（`ImproverBundle`，待拍板 1 定放在哪）：一个 JSON 清单加若干文本文件，三部分：
  1. **诊断策略**：现在 `POLICY` 的几段话，按段落编号存成文本（每段有长度上限）。
  2. **提案算子**：允许提哪几种组件、优先顺序，以及每种组件的提案简报模板（现在 `proposalBrief` 的文字）。插件始终不在里面。
  3. **比较策略参数**：只放“怎样挑回放用例、挑几个、每侧跑几次”这类参数，每项有固定的上下限（待拍板 2）。
- **v0**：把步骤 5 现有的文字与默认参数原样抽出来，作为内置版本；没有任何改进器采用记录的项目就用 v0。步骤 5 的全部测试与 `accept-step5` 在 v0 下必须照常通过（H01）。
- **版本与采用**：和能力包一样，版本是规范化清单的 SHA-256；采用历史是摘要链（复用 `activation.ts` 的写法）；每个改进作业开始时固定一个改进器版本，写进 `job.json` 与账本（`improverVersion`），作业中途采用新改进器不影响它；可以手动回滚。
- **评价器不在改进器里**（待拍板 2、5）：门控的采用规则（`decideTrial` 及 `costRatioCap`、`costApprovalRatio`）、守护集最少 1 个、反馈检查的评审提示与模型、改进预算、`autoImprove` 开关，都不是改进器的一部分，改进器改不到。

### 元改进作业

- **触发**（待拍板 3）：项目里每累计 K 个结束的改进作业（推荐 K = 3），开始一个元改进作业；也可以显式触发（`nexgent improve meta`、改进页按钮）。元改进作业与普通作业共用“同一项目同时只有一个作业”的作业位。
- **元诊断**：一个只读的改进会话（`purpose: improvement`、`phase: meta-diagnose`），读历次改进作业的记录（状态、诊断、候选种类、门控结论与理由、反馈检查通过率、费用、首次被使用、是否被回滚），交一份结构化的元诊断：哪类作业失败最多、失败在哪一段、假设“改进器缺什么”。宿主按 schema 与证据校验，最多 3 次，与步骤 5 诊断相同。结论可以是 `none`（改进器没有明显问题），此时作业以 `no-proposal` 结束。
- **元提案**：一次只提一个类型化改动（`ImproverChange`），宿主做 schema 与上下限校验，不写自由代码。改动类型：
  - 改写或新增诊断策略的一段；
  - 改提案算子的允许种类或优先顺序；
  - 改某种组件的提案简报模板；
  - 在上下限内改一个比较策略参数。
  改到评价器字段、超出上下限、多于一个改动，一律拒绝。
- **子改进器必须真跑一次**（计划 4.6 原文“新版本必须实际承担下一次改进作业，产生后代候选”）：子改进器只在父子比较里真的跑完一次作业、产出了后代候选，才有资格被采用；没产出后代的子改进器直接判负（父也没产出时判打平、不采用）。
- **采用之后**：采用的子改进器从下一个真实改进作业开始生效，作业记录写 `improverVersion`，“首次被使用”与能力的写法相同。父子比较里在副本中产生的后代候选不带回真实项目（真实项目里的能力仍只由真实作业改变）。

### 父子比较

- **同一起点**：取触发元改进前最近一个结束的、由反馈触发的作业，用它开始时的项目快照与它的反馈集。宿主把这个起点复制成两份项目副本 P、C，写下起点摘要（快照摘要 + 反馈 id 集合 + 纪元 id），两份必须相同，否则不比较。
- **两臂各跑一次完整作业**：P 用父改进器、C 用子改进器，各自在副本里跑诊断 → 提案 → 门控（门控在副本里再建自己的回放副本，规则不变），门控采用时只在该副本里采用。
- **比较规则**（待拍板 4）：纯函数 `decideImprover` 固定；比较“后代是否通过门控、门控测得的质量、作业总费用（诊断 + 提案 + 门控，估算美元）”；任何 `unknown` 即不采用。
- **副本保留**：比较用的两份副本默认在决定写完后删除；实验脚本可以经 SDK 选项要求保留，用来在副本里跑 holdout（见“测量”）。这个选项不出现在设置页。
- **费用**：一次元改进作业约等于两个普通作业加一次元诊断与元提案，计入元改进预算（待拍板 3），账本记录带 `metaJobId` 与 `improvementPhase: meta-diagnose | meta-propose | compare`。

### 评价器与纪元

- **评价器**：决定“好不好”的部分，即门控的采用规则与参数、反馈检查与偏好评审的提示和模型、守护集规则；实验里还包括隐藏判定与 holdout 集合。
- **纪元 id**：评价器设置的规范化摘要。每个 `TrialPlan`、每次父子比较、每份报告都写纪元 id；父子比较两臂纪元不同即不比较（`improvement/epoch-mismatch`）；报告只汇总同一纪元的数据。
- **纪元怎样更新**（待拍板 5）：只在用户改评价器相关设置、或新 ADR 改规则时进入新纪元；步骤 6 不做自动更新评价器。改进器、元改进作业和模型都写不到评价器设置（加入 `GUARDED_PROJECT_CONFIG_FIELDS`）。

### 测量（实验脚本，不进产品）

- **任务族**（4.9 #8 已定）：
  - **表格 / 数据**：沿用步骤 4、5 的订单夹具生成器，按月份与变体（地区表、品类表、退货率表等）确定性生成；用户约定（例如某个总要有的列、某个口径）只在反馈里出现。
  - **多文件代码**：新写一个生成器，生成小型 JS 项目（4–6 个模块 + 可见测试 + 隐藏测试），变体有跨模块修 bug、跨三个文件加功能、保持接口的重构；用户约定（例如金额一律用整数分、新函数要有对应测试文件）只在反馈里出现。
- **四个集合不重叠**（按生成器种子与变体划分，待拍板 6 给数量）：
  - `dev`：会收到反馈、触发改进作业的任务；
  - `selection`：作为项目历史、供门控挑选比较用例的任务；
  - `guard`：作为项目历史、与 dev 明显不同、供门控守护集挑选的任务；
  - `holdout`：从不进入任何实验项目的历史，只在副本里用来测效果，并且至少包含一个 dev 里没出现过的变体。
  脚本检查：门控实际挑中的用例都在 dev ∪ selection ∪ guard 里；holdout 任务的用户消息、种子与素材在实验项目的会话、快照与回执里都搜不到。
- **模拟用户反馈**：反馈文字由脚本按隐藏判定查出的问题从固定模板生成（每条措辞不同、不提能力工具），不用模型生成，保证可复现（待拍板 6）。
- **holdout 的臂**（每个任务族）：
  - `base`：改进前的项目（起点快照）；
  - `parent`：父改进器那份副本（含它的后代，若被副本内门控采用）；
  - `child`：子改进器那份副本。
  每个 holdout 用例每臂至少 3 次，每次在该臂的新副本里新开会话跑，互不影响。
- **测什么**：隐藏判定通过率（主指标）；每次任务的估算美元；组件是否被加载并调用（`componentsUsed`，激活证据）；改进与元改进的总费用。
- **报告口径**（待拍板 7）：按 holdout 用例配对，给出 `child − parent`、`parent − base` 两个差值的均值与 95% 自助法区间；区间下限 > 0 记“正”，上限 < 0 记“负”，否则记“零（样本内看不出差别）”；摊薄：若每次任务省钱，写出“改进 + 元改进的总费用要多少次后续任务才能省回来”，若是质量提高，写出每提高一个百分点花了多少美元。没有收益时明确写出。
- **可复现**：生成器种子、改进器与能力版本、纪元 id、模型 id、thinking 设置全部写进实验清单；报告由 `scripts/experiment/step6/report.mjs` 从原始记录生成，同一份原始记录重跑得到相同的报告；模型输出本身不可复现，报告写明这一点并给出重复间的波动。

### 账本与记录

- 新字段：`improverVersion`（作业与改进会话的每条记录）、`metaJobId`、`improvementPhase` 新值 `meta-diagnose / meta-propose / compare`；元改进作业结束写一条 `improvement.end`（`kind: meta`）。
- 新文件：`.nexgent/improvers/`（改进器版本与采用历史，待拍板 1）、`.nexgent/improvements/<jobId>/` 里元改进作业的 `meta-diagnosis.json`、`change.json`、`comparison.json`（起点摘要、两臂作业引用、`decideImprover` 结论）。
- 格式在会话 JSONL v1、账本 v1、改进文件 v1 内追加，步骤 5 的数据照常读出。

## 中期检查点（第 3 轮末）

脚本化 provider、Linux 本地：

1. v0 下 `accept-step5` 42/42，改进器版本可采用、可回滚。
2. 第 K 个作业结束后自动开始一个元改进作业，元诊断与元提案合 schema，越界改动被拒。
3. 父子比较两臂起点摘要一致，各在副本里产出后代与门控结论，真实项目的文件、会话、能力与成果不变。
4. 子改进器被采用后，下一个真实作业的 `improverVersion` 是子版本。

判定：四项满足则第 4 轮开「SDK 与桌面」与「收益测量」第二部分；第 2 或 3 项不满足时「改进流程」延长一轮，「SDK 与桌面」可先对假数据开发。

所有判定由脚本从文件、会话、账本、改进作业与比较记录、采用历史和进程状态得出，不看模型或界面的自述。

## 真实模型实验

**任务族与规模**（按拍板 6 的推荐）：每个任务族 dev 2 个、selection 2 个、guard 1 个、holdout 3 个（其中至少 1 个是 dev 里没有的变体）；每个 holdout 用例每臂 3 次。

**运行方案。** Linux 云端会话，开 thinking，用环境变量 `NEXGENT_API_KEY`。执行、诊断、提案、元诊断、元提案都用 `claude-sonnet-5-5`（拍板 8）。门控参数沿用步骤 5（selection 2、guard 1、每侧 r = 2，费用规则按 ADR 0007）。

**预估费用。** 依据步骤 5 第 2 次运行：普通任务约 0.08 美元（多文件代码估约 0.15 美元），一个改进作业（诊断、提案、门控）约 1.05 美元。每个任务族：

| 项 | 表格 / 数据（美元） | 多文件代码（美元） |
| --- | --- | --- |
| R01 历史任务 3 个 | 约 0.25 | 约 0.45 |
| R02 dev 任务 2 个 + 反馈轮 | 约 0.4 | 约 0.6 |
| R02 初始改进作业 | 约 1.05 | 约 1.5 |
| R03 元诊断与元提案 | 约 0.3 | 约 0.3 |
| R04 父子比较（两个作业） | 约 2.1 | 约 3.0 |
| R05 holdout 3 用例 × 3 臂 × 3 次 = 27 次 | 约 2.2 | 约 4.0 |
| 合计 | 约 6.3 | 约 9.9 |

两个任务族跑一遍约 16 美元；用户任务自己提出候选引起的门控（步骤 5 第 2 次有 1.67 美元）可能再加 1–2 美元。步骤 4 跑了 6 次、步骤 5 跑了 2 次才走通，所以本步至少要给一次重跑的余量。**这超过了以往每步 15 美元的上限**，见拍板 8：推荐上限提到 **35 美元**；若保持 15 美元，就只能缩小规模（见拍板 8 的选项 B）。这是估算，不是账单；元提案若改用 `claude-opus-5-5`，元诊断与元提案部分约翻三到五倍，每个任务族约增加 1–1.5 美元。

## 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 样本少：每族 3 个 holdout 用例 × 3 次 | 差值的区间很宽，大概率记为“零” | 这是如实的结论，报告写明样本量与区间；计划 4.6 第 5 条要求正、零、负都如实记录；不为得到“正”而换用例或加重复 |
| 元改进的效果要隔两层才看得到（改进器 → 后代能力 → 任务） | 父子差异很小，噪声盖过信号 | 比较时同时看后代是否通过门控、门控质量、作业费用三个中间量，报告分别列出 |
| 父子比较的两个作业是单次运行 | 比较结论本身有偶然性 | `decideImprover` 只在差异明确时采用（拍板 4）；报告写明每次比较只有一个样本 |
| 改进器的改动是文字（诊断策略、简报模板） | 文字改动的效果难以预测（MASS 观察到改动大小与效果几乎无关） | 一次只改一处；子必须真跑；守护集与回滚不变 |
| 同一个模型既写改进器又被它指挥，又当反馈检查的评审 | 自我强化的错误 | holdout 只用隐藏判定；评价器（含评审设置）冻结、改进器改不到；反馈检查与隐藏判定不一致的次数单列 |
| 嵌套副本（作业副本里再建门控副本）占磁盘 | 实验中途磁盘满 | 副本只在实验选项下保留，登记大小，超过快照上限拒绝；云端会话按需清理 |
| 多文件代码族是新写的，可能太难或太容易 | 三臂都 0% 或都 100%，什么也测不出 | W6 第一部分用脚本化与少量人工检查定难度；真实实验前先用 v0 跑一个 dev 任务看通过率（计入预算），太偏就调变体后再开始，调整写进报告 |
| 费用超出估算 | 实验做不完 | 实验脚本有费用闸门，累计估算超过上限时拒绝开始新运行；按任务族顺序跑，先跑完的那族先出结果 |
| thinking 回放依赖 beta 头 | 元改进会话中途换工具的请求可能 400 | 沿用 #97；出现即按 unknown 记录并交「kernel 维护」修 |

## 待拍板（每项给推荐）

| # | 事项 | 推荐 | 其他选项 | 白话与例子 |
| --- | --- | --- | --- | --- |
| 1 | 改进器放在哪、管多大范围 | **A：项目级，单独一条版本线 `.nexgent/improvers/`**，复用能力包的存储与采用历史代码，与项目能力分开采用、分开回滚 | B：作为能力包里的第 8 种组件，和技能、工具一起进同一个版本；C：用户级，所有项目共用一个改进器 | 选 A：项目甲的改进器学会了“诊断时先看失败的检查”，项目乙不会自动得到；回滚甲的某个技能不会顺带把改进器也退回去。选 B 的话，两者绑在同一个版本号上，回滚一个就会连带另一个 |
| 2 | 改进器能改什么、不能改什么 | **能改：诊断策略的段落、提案算子（允许的组件种类与顺序、每种的简报模板）、比较策略参数（只能在上下限内：selection 2–4 个、每侧重复 2–3 次、挑用例的方式）。不能改：采用规则与费用倍数、守护集至少 1 个、反馈检查的评审提示与模型、改进预算与开关（这些算“评价器”）** | B：比较策略参数也不许改，改进器只改文字 | 例子：改进器可以把“诊断前先读失败的检查”写进诊断策略，也可以把 selection 从 2 个调到 3 个；但不能把“费用超过 2 倍要你批准”改成 5 倍，也不能把守护集减到 0。否则它可以靠放松考题来“变好” |
| 3 | 元改进什么时候开始、默认开还是关 | **每累计 3 个结束的改进作业（采用、拒绝、不需要改进、失败都算，取消和中断不算）自动开始一次；产品里默认关，设置页可开，也可手动触发；开了以后用单独的元改进预算，默认每项目每 30 天 600 万 token（约 6 美元），预算与开关写入都要审批** | B：默认开，并和现有的改进预算（300 万 token，约 3 美元）共用 | 一次元改进要把父、子两个改进器各跑一遍改进作业，约 2.5–3.5 美元，现有每月约 3 美元的改进预算一次就用光，普通改进会被挤掉。所以推荐默认关，等本步的报告显示有收益再考虑默认开；实验脚本里会打开 |
| 4 | 父、子改进器怎样比、什么情况下采用子 | **每次元改进只比一组（同一快照、同一反馈集），两臂各跑一次作业。子被采用的条件（按顺序判断）：任何一臂有 unknown → 不采用；子没产出后代 → 不采用；子的后代通过门控而父的没有 → 采用；两者都通过且子的门控质量更高 → 采用；质量相同且子的作业总费用至少低 10% → 采用；其余不采用** | B：比两组（两个不同反馈集），两组都不差、至少一组更好才采用；更可靠，但每次元改进的费用翻倍 | 例子：同一批“缺 avg_order_value 列”的反馈，父改进器提出的技能被门控拒了，子改进器提出的技能通过了，就采用子。两边都通过、质量一样，但子少花了 15% 的钱，也采用；只少花 5%，算打平，不换 |
| 5 | 评价器多久更新一次（纪元） | **只在你改评价器相关设置、或写新 ADR 改规则时进入新纪元；本步不做自动更新评价器。父子比较与报告只用同一纪元的数据** | B：每做 N 次元改进自动开一个新纪元（例如把反馈检查的评审提示也交给模型改） | 例子：步骤 6 实验期间，“质量提高且费用不超过 2 倍就采用”这条规则和反馈检查的评审提示都不变。如果中途你把 2 倍改成 3 倍，之前和之后的结果分成两个纪元，不放在一起比 |
| 6 | 测量规模与反馈来源 | **每个任务族：dev 2、selection 2、guard 1、holdout 3（至少 1 个是 dev 里没出现过的变体）；holdout 每用例每臂 3 次；三臂 base / parent / child；模拟用户反馈由脚本按隐藏判定查出的问题套固定模板生成，不用模型写；OpenFOAM 族不做** | B：holdout 加到 5 个用例（结论更稳，每族多约 1.5–2.7 美元）；C：反馈也让模型扮演用户来写（更像真人，但不可复现） | 例子：表格族的 holdout 里有一个“品类退货率表”，dev 里只出现过地区表，用它看学到的东西能不能用到没见过的表上。反馈像“这张表又少了 avg_order_value 这一列”，是脚本从模板里取的，同一次实验重跑措辞相同 |
| 7 | 报告口径（怎样算“有收益”） | **以隐藏判定通过率为主指标，按 holdout 用例配对，给出“子 − 父”“父 − 改进前”两个差值的均值与 95% 区间；区间整体大于 0 记“正”，整体小于 0 记“负”，跨过 0 记“零（看不出差别）”；费用包含改进与元改进；摊薄写成“要多少次后续任务才能把改进的钱省回来”或“每提高 1 个百分点花多少美元”** | B：只报均值，不给区间与正 / 零 / 负 | 例子：子比父平均高 8 个百分点，但区间是 −5 到 +21，就写“零：样本内看不出差别，均值 +8”。不会因为均值是正的就说“递归改进有效” |
| 8 | 真实模型实验的模型与预算上限 | **全部用 `claude-sonnet-5-5`、thinking 开（元提案可在配置里改 `claude-opus-5-5`）；Linux；预算上限提到 35 美元（一遍约 16–18 美元，留一次重跑的余量）；Windows 真实模型可选** | B：保持每步 15 美元：只有表格族做完整的元改进与父子比较，多文件代码族只测“改进前 vs 步骤 5 改进器”两臂、holdout 2 个用例，一遍约 11 美元，几乎没有重跑余量 | 计划要求两个任务族都测，且每个用例重复 3 次；按步骤 5 的实际花费，两个族完整跑一遍就超过 15 美元。选 B 的话，多文件代码族就回答不了“改进器自己被改进后有没有用”，报告要写明这是缺测 |

计划 4.9 已定、本表沿用：任务族为表格 / 数据 + 多文件代码（#8，OpenFOAM 可选，本步不做）；改进与审核允许开 thinking 或换更强模型（#6）；插件包每次审批（#5）；真实模型只设预算上限、不设停止条件（#9）。步骤 5 已定、本表沿用：门控费用规则按 ADR 0007；改进预算、`autoImprove` 默认开、同一项目一次一个作业（ADR 0006）。
