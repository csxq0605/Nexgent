## 总原则（所有工作包都适用）

1. **Nexgent 是通用 agent。**
   - 产品代码、系统提示、改进器 v0、门控与评审提示里，不出现为某个实验用例或某类任务写的规则、例子、默认值。
   - 每项改动在 PR 描述里写一句“为什么对任何任务都成立”。只对某道题有用的改动不做。
2. **用例只用来测量。**
   - 看到试点结果后，不改产品去迎合某道题，也不改题、改评分去迎合产品。
   - 要改，就按 ADR 0011 第 6 条作废这一轮，换新的试点 id。
3. **改进器的文字只由元改进改。** 线程不手写改进器段落或简报来让实验通过。`v0` 不变。
4. **不改评价器**：除 ADR 0013 的两条外，不改评价器（反馈检查的打分方式、评审输入、费用规则）。
5. **工作分支**：工作留在 `nexgent-app`，不碰 `main`；一个讨论串一项任务一个 PR，合入时本地跑改动包及其依赖方的测试与类型检查；CI 只能手动触发。

## 目标与退出门槛

1. 改进器改为用户级共享，旧项目级版本线只读；元改进按用户计数与计预算；项目可关“参与改进器学习”（ADR 0012）。
2. 门控进入 `adr-0013` 纪元：
   - 改进作业的候选在同类题上不变差才采用；
   - 没有同类题时等用户批准；
   - 含原题具体数值的组件在提案时被退回，门控前再查一次（ADR 0013）。
3. 小试点按 ADR 0011 冻结后跑完，产出试点报告，回答两件事：评分是否可靠；`memory` 臂能否运行。并附 `parent − base`、`memory − base`、`parent − memory` 三个比较。
4. `accept-step5`、`accept-step6` 在新规则下 Linux 本地全过；期望有变的检查项逐条列出原因。
5. 全量测量是否开跑、预算多少，由用户看了试点报告后决定。不在本表范围内。

## 小试点的冻结内容（ADR 0011，由「收益测量」写进 `scripts/experiment/step6/pilot-plan.json`）

### 题目

两类新任务，每类 8 题。素材由生成器按种子确定性生成，每题的文件与评分表写进计划文件。

**文档写作**（输入：项目 `materials/` 下的会议记录、周报、访谈稿、事故记录等纯文本或 docx；输出：项目里的 Markdown 文件）

| 集合 | 题 |
| --- | --- |
| dev | ① 根据 3 份周会记录写本月会议纪要；② 根据产品说明与 20 条用户意见写一页改版建议 |
| selection | ③ 根据 4 份销售周报写月度小结；④ 根据两份方案写对比备忘 |
| guard | ⑤ 把一份英文操作说明改写成中文分步指南 |
| holdout | ⑥ 根据事故记录写复盘；⑦ 根据 5 份访谈稿写需求摘要；⑧ 根据会议记录写决议与待办清单（dev 里没有的变体） |

**文件整理与转换**（输入：项目 `inbox/`、`data/` 下的 csv、xlsx、docx、md；输出：项目里的文件与目录）

| 集合 | 题 |
| --- | --- |
| dev | ① 把 `data/` 下 4 个 csv 合并成一个 xlsx，每个文件一张表；② 按“日期_来源_标题”规则重命名并按年/月归档 `inbox/` 下的 20 个文件 |
| selection | ③ 把 xlsx 第一张表导出为 UTF-8 csv，去掉合计行；④ 把一份 docx 转成 Markdown，保留标题层级与表格 |
| guard | ⑤ 把 12 个 md 笔记的标题与日期汇总成索引表（csv） |
| holdout | ⑥ 把 3 个 xlsx 的同名表纵向合并并去重；⑦ 把 docx 中的所有表格分别导出为 csv；⑧ 按扩展名和大小规则清理并归档一个混杂目录（dev 里没有的变体） |

### 评分表与反馈

- 每题 3–6 个要点，每个要点标一种类型：结果错误、漏做、格式不对、没核对就交、项目约定（每题至多 1 个）、个人口味。
- 两类各有一条“项目约定”，只在反馈里出现。它是通用的工作习惯，不是答案：
  - 文档类：文末列出引用的资料文件名；
  - 文件类：输出文件名不含空格。
- 模拟反馈按没通过的要点套模板生成：主问题一条、其余要点各一句，评分 2 / 无评分 / 3，与现有 `feedback.mjs` 的计数规则一致。“个人口味”只出现在反馈里，不进判定。

### 判定

| 类 | 主指标 | 判定方式 |
| --- | --- | --- |
| 文件整理与转换 | 要点通过率与整题通过（全部非口味要点通过） | 确定性：文件存在、行列数、逐格数值、文件名与目录规则、编码 |
| 文档写作 | 要点通过率 | 能写成字符串检查的（必含的数字、日期、负责人、引用文件名）用确定性检查；其余由外部评审 `claude-opus-5-5`（thinking 开、提示冻结）逐条判 是 / 否 / 看不出，“看不出”按未通过计并单列 |
| 文档写作（辅助） | 两臂两两偏好 | 外部评审按 A/B 两种顺序各判一次 |

**评分可靠的判据**（三条都满足才算可靠）：
1. 每个判定器对脚本准备的已知好答案判过、已知坏答案判不过，全对；
2. 文档类 6 组“已知一好一差”的成对样本，外部评审至少选对 5 组；
3. 两两偏好在两种顺序下一致率 ≥ 80%。

循环内评审（门控反馈检查）与外部评审的逐题一致率照实报告，不设门槛。

### 臂

| 臂 | 做法 |
| --- | --- |
| `base` | dev 任务与反馈之前的项目快照的副本 |
| `memory` | 在 `base` 副本里，由编排经 `@nexgent/capabilities` 的存储接口直接写入并采用一条上下文策略 `project-notes`：`instructions` 为该类全部计数反馈原文（按时间先后，超长时保留最新的），描述写“用户以前对本项目成果的反馈（原文）”；不诊断、不过门控；清单记录它的能力版本与全文摘要 |
| `parent` | dev 反馈触发改进作业（`v0`，`adr-0013` 纪元）之后的项目副本 |

不跑元改进与 `child` 臂。

### 统计与报告

- 主指标：按 holdout 题配对的要点通过率之差，两层自助法 95% 区间（先抽题，再在题内抽重复），2000 次，种子 `step6-pilot`；区间下限 > 0 记“正”，上限 < 0 记“负”，否则记“零”。
- 每题每臂 3 次，报告重复间波动。
- 另报：
  - 整题通过率；
  - 评分可靠的三条判据结果；
  - 内外评审一致率；
  - 被采用组件按“项目约定或事实 / 做事方法”分类；
  - 背答案率（ADR 0013 第 2 条的函数）；
  - 追问成果的次数（按臂）；
  - 费用。
- 报告由 `report.mjs` 从原始记录生成，字节可复现。
