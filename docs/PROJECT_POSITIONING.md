# Nexgent 产品与设计定位

> 状态：现行设计
>
> 适用范围：产品行为、内核之上的各层、桌面应用与命令行
>
> 文件格式与权限见 [`spec/`](spec/)

## 1. 一句话定位

**Nexgent 是一个在你的项目文件夹里干活、自己组队、并在日常任务中记住什么做法有效的通用智能体应用。**

> **One project. A team that learns.**

## 2. 系统形态

![Nexgent architecture](../assets/diagrams/architecture.svg)

桌面应用与命令行共用一个进程内 SDK；每一轮在内核循环里走完；上下文、组织者和工作区围绕这个循环；会话存储让一切可恢复，结局记忆把同类任务上有效的做法带到下一轮。

## 3. 想做成什么

Nexgent 是一个通用的任务智能体：用户面对的是项目、对话、资料和成果，而不是提示词和配置。它要做到四件事：

1. **日常任务好用。** 在真实的项目文件夹里干活，多轮对话，能停、能撤回、能恢复，成果有版本。
2. **自己组织怎么做。** 每个项目有一个常驻的协调者对话：小事自己做，大事自己分工、组队，做不下去就换一种分工；长而能分开的活交给讨论串在后台做；每次做完自己复盘，改进分工。
3. **在做事的过程中改进。** 改进的单位是用户手上的这个任务和日常的一个个任务，而不是离线拿题集反复重放打分。用户感受到的是“它记得我说过的话、同类事做得越来越顺”，界面上不需要一堆改进设置。
4. **不为某个任务特化。** 产品代码、系统提示和判定规则里不写只对某类任务成立的东西。订单、表格、科研这些案例只用来测量。

内核（一轮对话的循环、工具、会话、沙箱）从 DeepSeek Harness 参考改写，Nexgent 自己的部分主要在上面这几层：任务内的即时调整、组织方式、以及跨任务记住什么。

技术选型：TypeScript，Electron 桌面应用加命令行，不做浏览器访问的 Web 服务；运行架构用 npm 上的 Cordis；DeepSeek Harness 只作只读参考，以子模块固定在 `reference/deepseek-harness`，不参与构建，改写的文件加来源头注并登记在 `THIRD_PARTY_NOTICES.md`；模型走 Claude Platform，默认 `claude-sonnet-5-5`、开 thinking，不做多 provider 抽象。

## 4. 一轮对话怎么走

1. 用户发消息。宿主判断这一轮要不要组队，并把项目规则、相关经验、资料引用、上一次同类任务顺利的分工放进这一轮的上下文。
2. 模型思考、调用工具（读写文件、运行命令、搜索、委派成员……）。只读工具和多个委派可以同时跑；要审批的操作按顺序问用户。
3. 用户随时可以插话，下一次模型请求就带上。
4. 模型用 `present` 交付成果。宿主跑完成检查：测试、用户设的检查命令、交付的文件能不能打开。没过就在同一轮里接着改，默认最多 2 次。
5. 轮次结束，记下结局：检查结果、花费、分工、用户中途纠正了几次。之后用户返工也会补记。

会话记录是只追加的 JSONL，每次模型请求在账本里记一条，所以进程被强杀后可以恢复，花费也查得清楚。

## 5. 任务内：一纠正就调整，可靠记得前面的事

- **运行中插话。** 输入框不锁，消息排进当前这一轮，在下一次模型请求前插入。正在跑的命令不打断，“停止”照旧可用。插话可以带附件。
- **转给成员。** 用户中途说的话自动转给正在运行的每个成员，比如说“统一用整数分”，正在写代码的成员下一步就收到。
- **原话不丢。** 上下文压缩时，摘要后面逐字附上用户说过的所有原话（任务、纠正、反馈），按时间排列，最多 6 万字符，超出时保留最新的。这样任务跑得再久、压缩过几次，开头定下的约定仍然在。

这几条都是对话机制，与任务类型无关。做法参照 Codex：每次请求前收进排队的用户输入，压缩时原样保留用户消息。

## 6. 自己组队，卡住时改组

- **要不要组队由宿主决定，不让模型临场决定。** 小任务（没有资料、一行、40 个字或词以内）自己做；其余默认组队。同类产品的经验是“让模型自己决定派不派”最不稳定。
- **一个入口。** 模型用 `organize` 工具一次给出分工：1–6 个角色，角色只有通用的五种（规划、调查、实现、测试、审查），写明谁等谁。能并行的并行，每个成员在自己的工作副本里干活，结束时合并。宿主用已有的委派和工作流来执行，模型不需要分别学几套。（早先让模型自己拉队友、发消息、管任务板的一组工具已删除，2026-10-20；信箱与任务板的状态代码还留着，讨论串目前没用它。）
- **成员交回结构化汇报**：做完了什么、没做完什么、检查结果、卡在哪里。界面上的“小组进度”卡按此显示，卡住的成员会标出来。
- **卡住就改组。** 分工没有进展，或用过成员而检查失败时，提示模型换分工。换分工必须写原因，原样重来会被拒绝。界面上多一行“改了分工：原因”。
- **始终留对照。** 即使默认组队，也有一部分任务单独做，用来比较组队到底值不值。

## 7. 记住好的分工

- 每个不算小的任务结束时，在用户级组织库 `<NEXGENT_HOME>/organizations/runs.jsonl` 里记一条：是否组队、最后用的分工、改了几次、用户中途纠正几次、检查结果、整棵任务树的花费。之后同一对话里出现返工（评分低、说“不对”“改回去”、删掉交付的文件），也记下来。
- 任务按文字的相似词归类；文字对不上时按做法（改了哪类文件、用了哪些工具）归类。开始时还不知道这次的做法，就按同一项目上一次任务的做法先归类，让这一轮拿到的组队建议和复盘改法与它最后记进的那一类一致。
- 一次“顺利”指：正常完成、检查没失败、用户中途没纠正、之后没返工；请了外部评审的，评分还要不低于 0.7。没有测试也没有用户反馈的任务，结局本来不知道，所以更常请外部评审（约 3 成，其他任务约 1 成）。同一类里组队和单独做各满 5 次后，有一边明显更顺利才下结论。
- 下次遇到同类任务，在内置分工和这一类顺利过的分工里抽样挑一个（花费越高扣分越多），并把它上次顺利时的角色写进提示，让模型从那里开始。任务中途改出来的分工只要顺利，也会被复用。
- 对照比例：没有结论时 1/5 单独做，有结论后 1/10。
- 界面上只有一句话，例如“同类任务用‘规划、并行实现、审查’分工，比单独做的顺利率高 35%，花费多 30%”；同类组队任务有 4 次以上时再加一句“组织调整后，比一开始花费少 30%、快 20%，质量没变”（最近几次与最初几次的中位数比较）。没有设置项。
- 早先的“换个做法再试”（在副本里换一种分工重做、两边并排挑一个）已删除（2026-10-20）：改进不该要用户来挑，由下一节的复盘代替。项目副本的机制留着，讨论串用它隔离（第 7b 节）。

## 7a. 协调者：每次组队做完自己复盘

用户的定义（2026-10-20）：每做完一个任务，不等人反馈，自己看哪一部分用的 token 最多、耗时最长、经常失败，就去改那里。

- **量什么。** 一轮结束时，宿主只从会话记录里算出这一轮的组织画像（`organization-profile`）：协调者自己和每个成员各一份，记花费（按用量折算的份额和美元）、耗时、失败、重做、空等和白做的活。协调者的空等是等成员交回的时间；成员的空等是排队等空位的时间（`subagent.start.queuedMs`）；白做指成员合并进来的文件后来被整份重写或删掉。画像随这一轮记进组织库。
- **找热点（看数据）。** 任何一条成立就算热：失败加重做至少 2 次；活全被白做；占花费或耗时至少 4 成，且高于同类任务里同种角色的中位数；成员排队超过自己时间的 3 成。最热的一处胜出。找热点只看量出来的数，不请模型。
- **判断原因、只改一处（模型反思，2026-10-20 第三轮）。** 按热点的种类列出适用的改法：只读相关文件、拆成两个并行成员、合并（不再单独派人）、并行开始、改同一文件的先后做、把前面的完整结果交下去；退回过的不再列。适用的不止一种时，模型（这次运行用的模型，一次辅助请求）读这一处的运行记录（协调者自己这一轮，或这个成员 / 讨论串每次运行的消息、工具调用和失败），写出原因，从列出的改法里选一个并写明理由。模型调用失败、或给的改法不在列表里、或没写原因和理由时，按固定顺序取第一种。这一步在后台做，不拖慢这一轮结束；下一个任务开始挑分工前等它写完。下一次同类组队任务的分工说明里多一句英文提示，说清上次哪里热、这次只改什么，模型选的还附上它找到的原因。
- **留还是退。** 用同样的量判断：试了 2 次，每次目标值都比改之前同类任务的中位数低至少 2 成，就留下；任何一次没顺利、或整个任务比原来的中位数贵出 2 成以上，立刻退回。退回的改法对同一种角色和原因不再试。留下的改法以后同类任务都带上（最多 3 条）。
- **界面。** 小组卡上一行：“这次比上次改了一处：……（上次……占了 55% 的花费）”，或“上次的改动变好了，已留下”“上次的改动没变好，已退回”。没有开关。
- **记在哪。** 组织库 `runs.jsonl` 多两种行：`change`（这次要试的改法、改之前的基线，以及谁选的：`chosenBy` 为 `model` 时带 `cause` 与 `reason`）与 `verdict`（留下或退回）。人的反馈只是额外的信号（算进“顺利”），不是前提。模型只决定改哪种，留还是退永远只看同样的数。

## 7b. 讨论串

协调者把长的、能分开做的活交给讨论串（2026-10-20）。讨论串本身是一个普通对话：用户可以进去看、直接跟它说话；它也能自己组队。

- **四个工具。** `start_thread`（起一个讨论串并交代任务）、`message_thread`（纠正、回答它的问题、给下一步）、`read_thread`（看它的状态、最后的回复和上一轮带回项目的文件）、`list_threads`。成员和讨论串自己看不到这四个工具。同时最多 3 个在跑，一个对话最多 12 个。
- **在后台、在副本里。** 讨论串在自己的项目副本里干活，每一轮结束时三方合并回项目；两边都改了同一处时保留项目的版本，讨论串的那份另存。
- **做完叫醒协调者。** 协调者交代的一轮结束时，协调者收到一条短讯（讨论串名、做完了 / 在问问题 / 没做成、它的最后回复）：协调者正在跑就并进这一轮，否则开始下一轮。用户自己在讨论串里说的话不叫醒协调者。讨论串的每次回复最后写 `Done:`、`Not done:`、`Checks:`、`Blockers:` 四行，`Blockers:` 不是 `none` 时算“等你回复”。
- **算进复盘。** 协调者交代的每一轮，在协调者的记录里记成一次成员运行（`executionForm: thread`），所以组织画像把讨论串当成一个部分来量（花费、耗时、失败、空等、白做）。这一轮起的讨论串都结束后，宿主再量一次这一轮（讨论串的花费算进整个任务），交给组织库，再照第 7a 节找热点、改一处、留或退。讨论串怎么分，也就进了组织记忆。
- **界面。** 总对话里每个讨论串一张卡片（进行中 / 做完了 / 等你回复 / 等你批准 / 停了 / 没做成，等你回复时写出它在问什么，一个“进入讨论串”按钮）；讨论串（或它的成员）有一步操作等你批准时，卡片上写“等你批准”和一行提示，侧栏那一行也带黄点，点按钮进去批准；短讯显示成一行小字；侧栏里讨论串挂在总对话下面，等你回复的带黄点；讨论串里顶上有回到总对话的按钮。

## 7c. 总对话的专用提示与项目笔记

第三轮（2026-10-20）：项目的总对话每轮开头多两段系统提示，别的对话、成员和讨论串都没有。

- **怎么当协调者。** 小事自己做，有几部分的活组队，长而能分开的活交给讨论串；派讨论串时写清目标、输入（文件、资料、已知的事）、完成标准和不许做或不许碰的东西，并把笔记里适用的规则带过去；讨论串的短讯到了，先用几行给用户汇总它做了什么、留下了什么，再决定下一步（回答它、给它或别的讨论串下一部分、检查它的活、或收尾）。提示是通用的，不针对任何任务。
- **项目笔记。** 记跨任务都成立的事：长期目标、用户的长期规则、做过的决定和原因、踩过的坑，按 Goals / Rules / Decisions / Pitfalls 分节，一行一件事带原因；不记进度、不记一次性的要求、不抄项目文件里已有的东西；错了就改那一行。总对话用 `update_project_notes`（整份替换，最多 8000 字）写，存在项目数据目录 `coordinator-notes.md`（模型的文件工具写不到那里），每轮开头整份给它看。只有总对话看得到这个工具。

这块在同类产品和论文里都没有现成实现：产品多是固定角色、由模型临场分派；自动优化多智能体系统的研究要离线拿打分题集反复跑。Nexgent 把比较摊到用户的日常任务上，靠结局记录而不是重放。

## 8. 项目规则

- 用户亲口说成长期约定的话（“一律”“项目里”“以后都”）记成项目规则；只针对这一次的（“这次”“这里”）不记。
- 规则保留用户给的具体数值和格式，按用户说的范围记；没说范围时只管这次碰到的部分，重复出现再放宽。范围小的优先，同一范围新的优先。
- 每次任务都给出全部生效的规则，放在注入内容最前面。规则压过项目里旧文档的说法，只有本次任务消息里明确的要求能压过规则。
- 拿不准是不是长期规则时，在能力页“等你看一眼”里问用户。
- 规则与现有测试或代码冲突时，两边都不改，先问用户以哪个为准；README、注释、示例照规则改。

## 9. 经验

- 每个任务结束后，后台给结果打分、总结一条可复用的做法，写进经验手册（项目级或用户级）。下次做类似的事时按任务文字检索，放在首条用户消息之前。
- 一条经验有没有用，靠随机给与不给的对照判断：试用中的经验一半机会给模型，启用的经验大多数时候给。结局只认确定性检查、用户的明确信号和外部评审的抽查，不认同一个模型给自己打的分。帮上忙够多次才正式启用，带偏了自动停用。
- 学习默认开，每个项目 30 天最多花 3 美元，可以在设置里关掉或改预算。花费单独记。

## 10. 权限与安全

- 文件权限分只读、可写工作区（默认）、完全访问，另有计划模式（先只看不改，批准后才动手）。
- 命令在系统沙箱里跑（Linux 用 bubblewrap，macOS 用 seatbelt），只能写项目目录和会话临时目录；Windows 没有系统沙箱，会如实说明。
- 读写项目外的路径、写敏感文件、在沙箱外重跑命令要用户批准；提权、删项目外内容、下载并执行这类只能“仅本次”允许。
- 命令策略按 shell 语法解析，`bash -c`、`env`、`xargs` 这类包装会逐层展开再判断。
- 费用按美元计，任务、对话、项目三级上限，达到 80% 预警。
- 密钥只从环境变量或本机的 `credentials.json` 读，不写进项目。

细节见 [权限](spec/permissions.md)。

## 11. 删掉和关掉的机制

早期版本（计划的步骤 4–6）靠“拿过去的任务在副本里重放、两边打分比较”来采用新能力，并有离线搜索更好执行配置的“第 3 层”。这条路花钱多、慢，和“改进发生在手上的任务里”相反：

- 改进作业、改进器与元改进、离线进化已删除（用户 2026-10-19 同意），代码在归档分支 `archive/offline-evolve`；`nexgent improve`、`nexgent improvers` 也随之删除。契约里的旧字段还在，只为读得懂旧项目。
- 能力候选与门控试验（`capabilities.autoTrial` 默认关）、第 2 层技能库（`learning.skills` 默认关）代码还在，默认不运行，界面不显示。

留下来的有用部分是结局评审（第 7 节，没有测试和用户信号的任务更常请外部评审，比例 0.3，不可设置）。门控里“新插件要用户批准”的一步已删除（2026-10-20）：等批准的候选一律拒绝，界面不再问。

## 12. 还没做到的

- 插话、组队、分工复用都有脚本化模型的测试，真实模型只在 macOS 上小规模试过，效果要更多日常任务来确认。协调者复盘（包括模型选改法）、项目笔记和讨论串只有脚本化模型的测试；热点规则和可选的改法是固定的几种，模型只在其中选。
- 讨论串在后台需要审批时，总对话的卡片会显示并能一键进去，但批准本身要在那个讨论串里做；进程退出时还在跑的讨论串，下次打开时记为中断，不会自己续上。
- 分工的比较要攒次数，前期多半显示“还在比较”；归类以文字为主，说法相近、内容不同的任务会被合在一起。
- 组队一般比单独做贵。
- macOS 沙箱没有实测，Windows 没有系统沙箱，Windows 与 macOS 安装包没有验证。

文件格式见 [数据格式](spec/data-formats.md)，权限见 [权限](spec/permissions.md)。
