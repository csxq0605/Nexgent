# Nexgent 0.8 架构快照

本文件保留截至 `5e61906` 的 0.8 实现合同，不代表完整任务智能体与编排进化已完成。下一版定位及可演化范围见 [架构入口](architecture.md)；以下四文件协议仅解释现有代码。

## 1. 执行对象与责任

一个智能体版本是内容寻址的完整源码包：任务程序 T、改进程序 M、协作程序 W 与角色资料 R。`solve(problem, tools)` 消费 benchmark 公开输入；`improve(context, broker)` 读取当前源码及公开开发证据，返回后代源码；可选 `select_parent(archive)` 决定扩展的研究分支。缺少可选选择器时继续当前研究版本，部署冠军不会隐式替代它。

宿主不实现领域算法、不代写后代。它负责版本校验、进程与能力限制、独立评分调用、预算准入、停止恢复和事件账本。插件是受信任的 benchmark 实现，智能体源码是受限的被测程序；二者的权限不同。

## 2. Benchmark 合同

插件独立安装，通过 `nexgent.benchmarks` 入口组发现。核心只导入合同与注册表。入口默认是无参构造器；需要工作区数据时可提供 `from_project(project_root)`。加载不得隐式下载数据。

| 接口 | 要求 |
| --- | --- |
| `spec: BenchmarkSpec` | 稳定 ID、名称、任务提交合同、领域工具 API、可选 `module:Class` 工具工厂、成本单位 |
| `initial_files()` | 提供 task.py 的合理初始方法；通用 seed 添加可演化研究程序 |
| `research_context()` | 可公开的领域指导和已有证据，不包含最终答案/确认数据 |
| `snapshot()` | 完整插件源文件、依赖版本与数据版本摘要，进入冻结实现身份 |
| `evaluate(bundle, split, seed, runner, ...)` | 使用宿主已绑定的运行器，返回独立评分与真实执行收据 |

演化协议使用逻辑分区 `development`、`selection`、`final_transfer`、`meta_transfer`。插件将这些角色映射到自己的独立数据池；例如 BBH 的 `final_transfer` 使用本地命名为 `transfer` 的池。分区别名不构成新的独立数据。确认分区及固定程序评估可使用插件额外公开支持的 split。

报告返回规范化质量 `score`（越大越好）、`score_available`、`status`、任务列表、`suite_digest`、`evaluator_digest` 与 `execution`。逐任务标识必须在配对两次评价中一致；可测的错误答案与资源缺测分开。`work_units` 的定义由插件公开，不能跨插件直接相加解释为同一计算量。

`ProgramRunner` 将通用 `tools.ask/parallel/search` 与可选领域工具绑定到被测程序。模型请求始终走同一宿主准入与账本；领域插件无需实现 Provider、进程或预算系统。评分器的私有答案不进入源码进程。

## 3. 三种运行

1. **固定程序 benchmark**：`evaluate_benchmark` / `nexgent evaluate`。登记源码、分区、种子和预算，调用 solve，完整保留失败/缺测；不执行 improve。
2. **源码演化**：基线、公开开发研究、候选独立选择、部署冠军与研究档案、冻结后的迁移评价。任务和改进程序均为实际源码，不是宿主参数枚举。
3. **实际改进器比较**：两版 M 从同一 T 起点生成后代，开发选择之后再评价迁移数据。可把同一对 M 放到另一插件的 T 和领域合同上；旧领域任务代码的直接 2×2 互换在该情形下不作有效归因。

每一种运行都返回统一可查看、导出和恢复的研究记录。固定程序成绩不被命名为 RSI 效果。

## 4. 开发阶段的实际元反馈

`broker.probe_improver(files, label)` 是框架能力，智能体决定何时调用。它冻结参考 M、候选 M、注册时的共同任务起点和公开历史；每组实际执行一次 improve，再评价实际后代。仅开发数据可反馈。

源码实验和改进器实验分别回答“这个任务程序表现如何”和“这个改进程序实际产生什么后代”。后者不是增加一个口头 critic 或直接评价现成任务代码。两组模型请求和开发实验有匹配上限，工具模型请求也计入各组成本。探测有自己的缓存作用域，不能免费复用另一已付款研究来伪装本次预算效率。

一次外层执行至多一次探测、深度上限 1，内层宿主拒绝再次调用。比较相同非任务 AST/角色内容时直接跳过；AST 相同判断不是一般程序语义等价证明。

完整探测源代码、执行、后代与成本保存为不可覆盖的工件，模型接收有界节选和可追踪身份。返回版本与实际被测 M 不一致时，宿主标记未验证；智能体自报支持状态仅作为自述保存。开发支持仍需独立后代/迁移检验。

## 5. 研究方法及可证伪贡献

STOP 提供改进程序自应用与实际下游效用的先例，DGM 提供可执行源码档案，Hyperagents 将任务与元程序共同演化并检验 improvement@k。Nexgent 采用这些明确归属的路径；不能把已存在机制重新命名为原创。

本项目待检验的组合是：**跨 benchmark 的可继承程序架构 + 智能体可调用的实际后代反馈 + 可追踪的源码/预算归因**。机制假设是实际后代反馈能帮助修改改进程序，减少只改任务参数、语义无效修订及对失效研究方法的继承。竞争解释包括额外模型计算、领域基线差异、档案选择和 API 抽样。需要等预算、无元反馈或冻结改进器对照，保留负结果。

已有科学 demo 对照未发生元程序变化，是未支持 RSI 的结果；BBH 固定强基线的 500/500 是接入与评分检查。软件测试、执行递归链、任务提升、改进器生产率与创新假设的支持是五个不同的验收层次。
