# 通用框架入口

2026-10-02：组织提案是一个应用能力，不能定义框架的能力上限。默认 Main、
`nexgent run` 和 Python 的 `Nexgent` 现在组合相同的 `TaskService`。
没有另建执行器、工具协议或一套候选发布账本。

## 已接通的结构

| 部分 | 复用的实现 | 普通入口中的行为 |
| --- | --- | --- |
| 任务执行 | TaskService / Episode | 工具、子任务、成果、预算和恢复使用同一运行时 |
| 执行策略 | AgentPackage / package channel | 默认 Python 决策循环；应用可替换整个执行程序，不要求组织提案或 DAG |
| 成员与协作 | delegate / parallel / artifact | 成员有任务内名称、职责、独立执行过程；共享实际输入和交付引用，负责人读取再汇总 |
| 工具 | ToolRegistry / ToolProvider | 工作区能力成为一个提供者；应用可注册自己的成熟工具，框架不认识其业务含义 |
| 评价 | 既有 evaluator adapter | 固定宿主评价程序在只读子任务中运行，共用原任务预算；不加载任务生成的工具或可修改评价提示 |
| 反馈 | 既有 Episode 事件与输入工件 | 用户反馈、对话交付和按反馈重跑跨进程保留 |
| 跨任务改进 | 既有 AutoEvolution / EvolutionService | 默认真实任务回归或显式项目策略负责候选、比较、门控与发布；新任务解析当前包版本 |

工作区文件读写、公开网页读取、CSV/Excel 和计算工具是可替换的提供者能力。
执行器及通用评价器没有 Excel 工具名、特定题目或组织候选格式的判断。
自动授予工作区基础工具；领域插件保留在注册表中，须按任务明确授予。

## 使用与组合

```python
from nexgent import Nexgent

agent = Nexgent("my-project")
task = agent.create("完成任务", inputs={"material": {"facts": [1, 2, 3]}})
result = agent.run(task["id"])
agent.feedback(task["id"], "后续需要更清楚地说明验证方法")
```

创建 `Nexgent(root, tools=registry, package=package, evaluator=adapter)` 可替换
工具注册表、初始执行策略和独立评价器。沿用现有 `ToolSpec` handler
`(arguments, ToolContext)`、`make_package()` 和评价 adapter 合同；不要求私有 DSL。
也可传入 `benchmarks={adapter.id: adapter}` 组合现有 BenchmarkAdapter，供项目改进
策略调用；宿主负责在重启时提供同一版本的 adapter，或将其安装为已有评价插件。
`package` 是新 channel 的初始版本，不能借构造函数覆盖已有部署。
也可显式选择已注册的 `package_channel`；同一任务冻结所选包及已授予工具的版本。

模型通过已有 `develop_tool` / `develop_service` 在受限 worker 中创建纯计算工具、
或上下文服务。成员通过普通 `delegate` 创建，`task.agent` 含 `name` 和
`instructions`；其职责不会增加权限。返回的 `output_refs` 是实际成果引用。
宿主在 `context.delegation_scope` 提供负责人/成员身份和剩余委派深度。成员直接
完成已经分派的职责，不为“独立核对”再创建同职责成员；不同工作仍可在宿主
深度限制内委派。远端模型结果未知时，成员和负责人进入既有待恢复状态，保留
原请求与成员身份，不能把超时当作失败后再创建新成员重发。

成员目录复用 AgentPackage 的 `roles` 注册表和 O 类角色组件。已发布成员通过
`task.agent: "注册名称"` 委派，宿主从该任务冻结的包读取完整职责；目录预览放在
`task.context.organization`，与当前部署同步的新任务会获得当前成员，旧任务保留
原有版本。目录只预览职责，不消耗整个模型上下文。Main 的“协作”页和 CLI `team`
展示已发布成员、实际任务分工、状态和成果；`agent.team(episode_id)` 提供同一投影。
初次组合可以使用 `framework_package(members={"analyst": "通用职责"})`，已有部署
仍只能通过门控更新，构造函数不会覆盖它。

委派时 `task.instructions` 可提供本次分派的具体资料或说明；宿主把它与父任务
目标保存在成员的 `context.assignment`。角色职责仍从冻结包读取，工具授权仍按
父任务缩小。父任务的私有评价上下文、记忆和附件授权不会随这份说明自动传递；
文件／工件仍通过已有输入引用显式分享。已创建成员的资料快照不会被后续修改覆盖。
默认成果复核接收任务及实际已读取输入，避免最近执行记录截断后丢失事实与限制。
这个自检仍属于执行策略；固定独立验收另外运行，不能被候选修改。
Main 会话优先显示结构化交付中的可读文字，完整结构保留在“成果”页与导出中。

完成的任务内成员可作为 `task_members` 改进选项。独立的开发规划模型决定是否
保留，设计模型把实际职责和用户反馈概括成通用成员职责及协作策略；宿主编译成
已有 PackagePatch v3，再使用同一套配对评价、发布和回归回滚。任务事实不应进入
成员职责。目录加载不算成员激活，门控需要成员真正完成委派任务；未调用的角色
不能凭目录存在通过激活检查。已注册成员的正常复用不会单独触发新改进。
先前候选被拒绝后，新的用户反馈可以发起新一轮；相同反馈及已完成阶段不会重复执行。

用户反馈或独立拒绝也可触发 `organization_design`，无需先成功执行过一个拟新增
成员。规划模型根据证据选择是否修改组织；设计模型描述新增／调整职责、明确移除
的成员和协作方式。宿主仅编译这些字段为现有 PackagePatch v3，附加模型注释不会
成为包声明或工具授权。未提及的现有成员保留，目录最多十六位成员，共享资源的
角色不被当作可单独修改的成员。没有增加一套组织存储或发布协议。

新增和修改的成员必须在配对任务中实际完成委派，移除必须从候选包中实际消失。
新增成员导致费用过高时仍拒绝，不能因用户
请求创建就跳过比较。Main“改进”页和 CLI `improve` 显示实际候选的新增、调整、
移除职责及协作方式，并区分候选、发布、拒绝和回滚；仅已发布版本用于新任务。

配置自动改进时，反馈包会纳入相同包版本下的真实委派成员。成员成功使用的工具
或服务可进入与主任务相同的候选、独立 selection、guard 和发布流程；只有实际
通过门控的包版本会影响新任务。普通入口提供有限计算额度，显式预算仍优先。

```powershell
nexgent --root ./my-project run "完成任务" --attach ./input.json
nexgent --root ./my-project feedback EPISODE_ID "反馈"
nexgent --root ./my-project learn EPISODE_ID
nexgent --root ./my-project run-resume EPISODE_ID
nexgent-gui --project ./my-project

# 原组织提案应用及既有历史数据仍可使用
nexgent --root ./my-project run "组织应用任务" --organization-demo
nexgent-gui --project ./my-project --organization-demo
```

`run-list` 同时列出框架任务和旧组织记录；旧记录 ID 的反馈、学习和恢复保持兼容。
模型配置仍可通过 `--model-root` 复用已有目录。

## 普通任务怎样完成

Main 的一次提交依次执行任务和独立验收。验收拒绝时，系统自动创建一次修正子任务，
沿用原任务的执行版本、资料和权限，读取原交付与评价反馈，再提交修正成果重新验收。
最终输出引用指向真实的修正工件；原工件、首次评价和费用仍保留。修正不会发布框架版本。
新初始策略在声明成果全部发布后直接提出完成并进入原有成果复核，不再要求
模型额外生成结束动作。复核读取真实工件；拒绝就继续修正，批准才返回成果，
之后仍执行固定独立验收。多成果任务在成果齐全前不结束。旧包的结束方式保留，
已有部署不会被默认策略更新覆盖，升级仍须通过门控。
执行、修正和固定评价共同受原任务的预算约束，Main 的任务用量包含三者。
默认普通任务允许四十次模型调用和十六万输出 token，成员共用该额度。Main 的
“模型调用上限”和 CLI 的 `--max-calls` 可在创建时调整；SDK 的显式预算优先。
已经创建或暂停的任务不会因调整默认额度而获得额外预算。
跨任务改进使用独立预算，Main 的“改进”页单独汇总这些根任务的真实费用，不混入原任务
预算或配对比较费用。费用缺失会明确标记，不以已知小计冒充完整费用。

数值交付需要独立计算收据；文件交付需要对实际文件的读取收据。
编号列表的序号不作为计算量。模型口头声称“已验证”不能满足这些证据条件。
“事实(2)”与“步骤(3)”等条目引用同样属于序号；数量、数值 JSON 和 `f(2)`
等函数参数仍需要独立计算证据，验收快照记录分类要求的版本。
这些条件是基本证据检查，具体业务正确性仍由独立评价器判断；应用可以替换整个 adapter。

评价不可用或缺少证据时，成果保留为“已有成果 · 待验收”，不会启动成果修正。
Main 的“继续完成”和 CLI `run-resume` 可再次验收，不重跑原执行。
暂停中的修正同样复用持久的子任务身份。预算已经耗尽时，继续不能突破上限。

同一对话的上传资料按快照路径保留，不受最近四次交付的上下文窗口限制。
关闭并重开 Main 后选择原任务，可继续使用原资料；新对话不继承这些授权。
每次最多上传八个文件，对话最多保留六十四个快照。
“按反馈重做”使用原任务输入和自定义上下文，加入该任务保存的反馈；后来的对话交付
不会混入重做输入。它创建一次新任务，不等于框架进化。

收到已计费且有完整用量的重复 JSON 字段响应时，复用运行时已有的单次修复阶段，
从原上下文请求一份新决策；有歧义的回复不执行、不默选某个字段，失败费用仍计入预算。
未知远端结果不自动重发。新初始策略同时接受顶层 `done` 和动作封套中的 `done`，
二者进入同一套工件验证和交付检查；已注册的执行包仍保持其冻结版本。

旧组织应用仍使用兼容服务，尚未迁成此框架上的 AgentPackage 策略。
保留历史行为不等于已完成应用迁移。

## 默认跨任务改进

`Nexgent(root)` 自动组成项目改进策略，不要求手写 benchmark 配置。保存人类反馈、
独立验收拒绝、执行失败或主任务／成员开发了新能力时，既有持久协调器捕获来源。
成功交付本身不会在每次任务后消耗模型调用来做无目标的改进。

默认回归使用原任务的冻结资料、上下文和本次反馈进行配对比较；另一个不同、相同
部署版本下验收通过的真实任务作为 guard。反馈重做的多个后代按一个历史任务计算。
guard 不提供给候选生成器；两部分冻结为已有宿主工件，后来的对话和反馈不会改变
已进入门控的任务集。历史不足时保持等待，新的真实任务完成后自动推进。
这不是未见任务集，selection 复用开发来源，不作为独立泛化证明。

默认策略先用成熟的单组件 BehaviorPatch v2 修改执行程序或策略／技能；新工具与
服务仍用现有可移植能力采纳流程。显式项目配置继续支持多组件 PackagePatch 和
编排搜索。这样默认任务不必先成功生成一份复杂的 manifest 变更。

默认独立配对要求质量不下降，并满足评分提升至少 0.1，或执行消耗减少至少 20%。
消耗沿用既有 `conservative_work` 口径，包括模型调用、保留的输出 token、工具工作量
和节点，不是供应商货币价格；缺失用量不能按已知小计通过。成功率仍为 1、消耗上限
仍为原版 1.25 倍，无任务退化且修改目标必须实际加载。零基线不能凭“节省”发布，
质量和消耗都没有改善时拒绝。SDK 的 `PromotionPolicy(min_cost_reduction=0.2)` 可选择
同一规则；省略该字段的显式策略保持原有质量门控和序列化身份。
通过后按既有流程发布并检查另一历史任务，guard 失败则回滚。主任务完成后
的新任务读取当前部署，后续“实际采用”只统计执行中真正加载修改的任务。

Main 的“自动改进后续任务”可关闭并跨进程保留；“改进”页显示提案、配对评分、
失败门控、发布、回滚、实际采用以及独立改进用量。关闭保留任务能力与待处理提案。
默认每个提案最多五个根任务，每个根上限 40 次模型调用、160000 输出 token、20 次
工具调用；全提案上限 200 次模型调用、800000 输出 token（不含提示输入 token）。
回归额度与默认普通任务一致，避免能完成的多成员任务因较低的回归额度而无法验证。
原任务显式零模型／输出预算不会启动默认模型改进。以上费用独立于原交付预算。

```powershell
nexgent --root ./my-project improve                 # 只查看，不调用模型
nexgent --root ./my-project improve --advance       # 推进待处理提案
nexgent --root ./my-project improve --enable off    # 关闭默认自动推进
```

SDK 对应 `improvement_status()`、`advance()`、`set_auto_improve(False)`。
规划前从相同 channel 的既有记录提取最近最多八次公开改进结果：所选假设、生成
错误类别、配对门控及质量／消耗汇总、是否回滚、后续采用数量。经验冻结在已有
development intent 中，重启不会换成后来结果，不复制历史 guard 的任务、输入、
答案或模型回复。规划器据此调整或放弃提案；执行策略和组织生成器读取选定计划
及同一经验快照。Main 显示本轮参考的历史次数，没有新增记忆数据库或发布服务。
裸 `TaskService` 的无配置行为保留；默认产品组合属于 `Nexgent`。已有任务策略不会
因启动新宿主而被覆盖；宿主提供的默认改进器使用独立版本 channel，旧提案保留所冻结
的改进器身份。显式自定义策略也保留自己的冻结身份。

## 尚未完成

已接通的默认任务流程不等于完整自主 RSI 已完成。

- 默认历史回归及配置后的跨任务候选与发布复用[已有改进策略](guides/ordinary-auto-evolution.md)。
  新默认 Python 策略下的自主候选、实际发布和后续任务复用还须真实验证。
- 通用宿主插件开发、服务接口扩展、记忆策略和改进策略自身的修改仍未完整接入。
- 交付评价为开发反馈；它不是隐藏任务集上的收益证明。执行程序中的自检也不能
  冒充这个独立评价。评价失败保留实际交付，并显示验收失败或缺测。

工具、服务和执行策略候选已复用同一套现有门控。成员能力发布、跨进程加载和拒绝
回退已通过 Python 策略集成验证；真实模型自主完成候选生成与发布仍待验证。
公开组合接口的[普通 Main 发布与复用](validation/member-capability-release-20261002.md)
使用确定性 Python 应用，不代表真实模型自主改进。
不能用另一个定制 demo 的成功或组织提案采纳来替代这项工作。

本轮[真实入口与失败记录](validation/framework-runtime-20261002.md)区分普通交付、
反馈续用、机制检查和尚未通过的多成员能力开发整轮。

2026-10-04 的[默认交付流程修复](validation/product-flow-20261004.md)记录了上传、反馈
重做及重启续用的三轮真实 Main 使用，以及修复前的两次失败；它不代表完整自主 RSI。

后续[默认项目改进](validation/default-project-improvement-20261004.md)记录无需配置的
Main 提案与真实配对拒绝，以及发布／回滚／重启后实际采用的集成验证，分别注明证据范围。

[委派资料与普通交付](validation/assignment-delivery-20261005.md)记录空组织下真实
Main 自主创建成员、汇总与固定独立验收，以及重启后资料保留；它不代表组织发布成功。
