# 从任务编排到持续自改进：Nexgent 的文献综合与设计选择

日期：2026-09-16；实施状态更新：2026-09-20。状态：**重新定位后的设计依据；P1 任务执行、P3 跨任务行为更新控制面和 P4 递归改进器确定性机制闭环已实现。尚未登记真实模型递归效果实验，没有新增统计效果结论**。

本文回答一个具体问题：Nexgent 应当如何成为持续完成任务、依据反馈改善自身工作方式的通用智能体系统，而不是围绕几个 Python 文件建立的修改与评分工具？科学发现是证明该能力的一个领域；OpenFOAM 是独立领域任务及工具适配，不定义核心架构，也不要求其他任务采用 CFD 工作流。

本文形成时只研究和撰写设计。此后落地的 P1 提供不可变 AgentPackage、任务轨迹、评审、预算和恢复语义；P3/P4 实现了受限 `O/M/S` 更新、R 自更新、实际后代元评测、独立通道和 guard/rollback 的无模型机制试验。它们没有把下述真实模型候选效用与统计假设变成已证实结论。历史源码、实验登记、失败和零收益结果不被覆盖；文献中的能力、固定版本代码的能力、Nexgent 的现状和待验证研究分别表达。运行字段见[任务运行时验证记录](task-runtime-validation-20260920.md)，递归机制见[P4 控制面](../design/p4-recursive-improver-control-plane.md)。

## 1. 先定义被改善的系统行为

Nexgent 的主要对象应是实际执行任务的 agent：理解目标、构造计划、分派角色、选择工具、读取证据、检查中间产物，根据结果决定继续、补证、改变方法或结束，并将有用经验带到后续任务。模型调用、工具调用和行为选择必须发生在被测任务程序里，而不能全部藏在外部源码设计器中。

为讨论设计，将一个可复用系统版本记为 `A_v = (O_v, M_v, S_v, R_v)`。这是行为划分，不是规定四个文件或四个独立模块：

| 对象 | 可变内容 | 必须观察的后续行为 |
|---|---|---|
| `O`：协作与编排 | 角色职责、角色数量、信息传递、串并行、条件分支、重试与停止规则 | 后续真实任务是否以不同角色、依赖关系或路径执行；不能只比较流程图或角色名字 |
| `M`：记忆及使用方法 | 有来源的事实与失败经验、组织方式、检索与筛选、压缩、失效与冲突处理 | 哪条记忆被检索、进入谁的上下文、影响了什么决定；“写入更多文本”不是这一影响的证据 |
| `S`：技能与工具协议 | 可复用步骤、模型提示、工具组合、输入输出约束、校验方法、错误恢复程序 | 后续任务是否调用了该技能版本，产物是否符合契约，是否少犯同类错误 |
| `R`：改进策略 | 如何解释反馈、选择修改对象、构造候选、分配研究预算、保留或舍弃变化 | 后续改进尝试是否采用了新策略，并在可比资源下产生更有用的系统版本 |

模型权重更新可以是未来的一种机制，但当前设计不依赖它。行为可以由代码、声明式模板、技能协议、模型指令或记忆策略承载。文件数量、命名和语言不是能力定义；只有修改文件而未改变后续行为，也不满足持续系统改进的证据要求。

### 三种研究命题必须分开

| 命题 | 更新关系 | 合理的成功证据 | 不需要强加的条件 |
|---|---|---|---|
| 固定优化器的架构搜索 | 固定 `R` 搜索更好的 `O/S` | 新任务 agent 的实际完成质量、可靠性或资源效率优于控制 | 不要求优化器改写自身；ADAS/AFlow 类型工作本身有产品价值 |
| 持续系统自改进 | 任务反馈改变可复用行为；改进后的系统进入后续任务与改善过程 | 版本化变化、真实复用、后续任务收益和退化检查 | 不要求每轮都修改 `R`，也不要求所有组件同时更新 |
| 改进过程的递归提升 | 系统还可改变 `R`，新的 `R` 后续承担改善工作 | 被改变的改进策略实际执行；固定任务起点、资源和评价条件下，后代生产能力提高 | 不以 `meta.py` diff 或一个角色自述代替效用测量 |

单次任务中的规划、反思和重试可以有效，但如果没有持久变化和后续复用，只支持该任务内的适应能力。反过来，不能因为严格的元递归效用暂未建立，就否认已被验证的任务系统或架构搜索效果。产品目标与更强的科研命题应当共存，不互相冒充。

## 2. 六项一手依据如何变成设计与检验

下表“原方法与边界”是文献阅读结论；后四列是 **Nexgent 的设计选择及待实施检验**，不是声称论文已经替本项目证明了效果。

| 来源与原方法、结论边界 | Nexgent 可变行为对象 | 应读取的任务反馈 | 后续怎样实际使用 | 验证与必要消融 |
|---|---|---|---|---|
| [AutoSci v1，§3–7](https://arxiv.org/html/2605.31468v1)：结构化跨项目记忆、阶段技能、DAG 增强及反馈驱动的版本更新。两项端到端案例和自动审稿结果展示研究流程，不构成独立 SciEvolve 因果消融或元改进器效用证据 | `M/S/O` 都可成为改进目标，不局限于 agent 源码函数 | 中间产物缺证、任务失败、用户纠正、复核意见与高成本步骤 | 新任务检索经整理的证据，执行修订后的技能与协作模板，记录实际版本 | 固定编排、只累积记忆、技能单独更新与联合更新的对照；应用补丁之后还须做独立任务验证 |
| [ADAS，§3–4](https://arxiv.org/html/2408.08435)：固定 Meta Agent Search 从档案生成 agent 的 `forward` 代码，反思、验证并修错。论文展示任务表现和设计迁移；不展示 meta-agent 流程自身进化 | `O/S` 的完整执行逻辑，包括角色交互、工具与控制流 | 任务验证结果、源码/运行错误、既有候选表现 | 下一次任务运行被选中的完整 agent，下一次搜索使用带评价的档案 | 与手工固定 agent、只改提示、相同预算的普通采样对照；将其保留为固定优化器基线，而非贬为“没有 RSI 所以无效” |
| [AFlow，§3–4](https://arxiv.org/html/2410.10762)：固定 MCTS 变体搜索代码工作流，按执行评分回传经验。实际主要搜索提示和结构，模型、温度、格式固定；预设 operators 辅助搜索 | `O` 的依赖、分支、循环及角色提示，`S` 的组合方式 | 每个候选在任务验证集的输出、得分、错误与调用成本 | 被测任务由搜索得到的工作流执行；经验进入后续搜索选择 | 固定 `R` 的工作流搜索基线；查真实调用图，避免把增加三个角色或重复更多调用称为结构创新 |
| [STOP，Algorithm 1、§3–5](https://arxiv.org/pdf/2310.02304)：用当前 improver 改善自己，并以其改善下游程序的结果定义元效用；报告受限任务上的提升与迁移。模型权重固定，作者限定为 scaffold 层面的递归代码改进 | `R` 的诊断、候选生成、搜索、验证与预算分配程序 | 实际运行候选改进策略后，其生成的任务 agent 效果，而非改进建议的文字评分 | 新 `R` 必须在下一批真实改进尝试中被调用；不要求每个任务都触发元修改 | 冻结更新前后 `R`，比较同任务起点的后代产出；基线包含固定 `R` 与相同资源的搜索 |
| [DGM，§3–4、§6](https://arxiv.org/html/2505.22954)：coding agent 根据日志修改自身工具、提示与工作流，档案保存不同分支供后续自修改；其外层档案与父代选择是固定的。证据主要来自编程基准，编程能力与自修改能力的关系是其重要假设 | `O/S` 及承担修改的 agent 本体；探索档案保留不同方法 | 可定位的执行失败与成功轨迹，完整任务评分及后代记录 | 实际选中的改进版本继续处理任务和修改任务；未立即胜出的版本可作为探索起点 | 固定初始 modifier、只用冠军分支与档案探索对照；检查父代选择和真正承担任务的版本一致，不强制选择器也要自改 |
| [Hyperagents，§3、§5.2](https://arxiv.org/html/2603.19461v1)：任务 agent 与可编辑 meta-agent 组成一个程序，允许记忆、诊断及未来改进机制变化；另用冻结 meta 的 imp@50 检查生成能力迁移。多域结果不是任意任务上的保证 | `R` 可依赖并更新 `M/S/O`，按行为及依赖定义范围，而非指定 `meta.py` | 实际后代质量、成本、失败模式与已积累的跨任务证据 | 演化后的策略真正产生后续版本；单独元评价期间冻结被测策略身份 | 同起点、相同资源、开发选优再测隐藏任务；不关闭恰好构成候选差异的行为分支后再宣称已测元机制 |

上述工作没有共同要求“每代修改某个元文件”。STOP 明确研究 improver 的自引用更新；Hyperagents 扩大元机制的可编辑性；DGM 保留固定外层；ADAS/AFlow 则为固定优化器下的架构搜索提供直接依据。Nexgent 的验证必须说明自己在检验哪一种关系。

## 3. AutoSci 论文机制与固定代码的边界

采用论文对应 `arxiv-v1` 标签的固定 commit [`6bc834a805a1744959a9983809e5d6f0263ef791`](https://github.com/skyllwt/AutoSci/tree/6bc834a805a1744959a9983809e5d6f0263ef791)；不混用继续变化的 `paper` 分支 HEAD 或主分支。以下为已核查源码，不等于端到端消融证明：

- [SciDAG CLI](https://github.com/skyllwt/AutoSci/blob/6bc834a805a1744959a9983809e5d6f0263ef791/scidag/cli.py) 将模板、LLM 与执行器连接起来；[executor 开头](https://github.com/skyllwt/AutoSci/blob/6bc834a805a1744959a9983809e5d6f0263ef791/scidag/executor.py#L1-L18) 明确该版本运行整个采样图，条件路由和 early-stop pruning 是后续工作。不能把论文中的自适应路由描述直接视为这个固定实现已有的能力。
- [SciEvolve 行为边界](https://github.com/skyllwt/AutoSci/blob/6bc834a805a1744959a9983809e5d6f0263ef791/runtime/schema/scievolve.yaml#L24-L51) 指向记忆、技能协议、DAG 模板与操作提示；它明确以影响未来消费行为的表面为修改对象。这个边界启发 Nexgent 的 `M/S/O` 设计，不要求任意核心源码重写。
- [`forge` 写入技能内容](https://github.com/skyllwt/AutoSci/blob/6bc834a805a1744959a9983809e5d6f0263ef791/tools/research_wiki.py#L4407-L4438)、[`morph` 写入模板及操作提示](https://github.com/skyllwt/AutoSci/blob/6bc834a805a1744959a9983809e5d6f0263ef791/tools/research_wiki.py#L5374-L5434) 证明存在真实行为载体更新路径；`morph` 默认 dry-run，应用需要显式 apply。所核查的应用路径包含变更与来源记录，不能据此宣称已有独立任务效能晋升门或元能力验证。

因此，本项目采用“反馈形成持久行为更新”的思想，同时增加应用后的任务效用检验。持久化、可执行和有效是三项检查；不能将“更新被写盘”缩写为“系统已经学会”。

## 4. Nexgent 的具体研究闭环

### 4.1 任务执行是主体，系统研究来自真实障碍

一次任务 episode 的计划是：

1. **任务建模**：明确用户目标、成功标准、可用资源和缺失信息，形成可恢复的任务状态。
2. **组织执行**：选择或构造协作方案；给角色提供相关证据与职责；实际调用模型、技能和工具。
3. **中间检查**：区分工具故障、契约错误、信息不足、推理错误、方法失败以及预算不足；记录依据，不由代理自授“验证通过”。
4. **任务内修订**：根据反馈补充证据、改变角色或方法、调整计划；必要时终止无效分支。修订是否发生由执行轨迹说明。
5. **跨任务改进**：从可重复或高影响的障碍形成假设，选择 `O/M/S` 的变化；只有当“如何改进”本身出现问题时，再研究 `R`。
6. **独立检查与复用**：测试拟议变化，保留版本与失败；后续任务显式加载被采用的版本，继续接收反馈。

是否用图、代码或技能协议实现以上过程，应由表达需求决定。DAG 适合可展开的依赖；循环和反馈分支需要显式状态与有界执行规则，不能画一个 DAG 就声称已实现动态编排。任务程序应能在多种协作方式之间选择，初始设计可以固定，不要求每次都重新发明架构。

### 4.2 反馈归因决定修改对象

| 可观察失败 | 至少要收集的依据 | 可研究的变化 | 反例与替代解释 |
|---|---|---|---|
| 下游角色缺少必要输入 | 角色真实输入、上游已存在产物、契约缺项 | 改信息传递与交接校验 `O/S` | 如果上游根本没有证据，增加传递边不会解决问题 |
| 多个角色重复检索或重复犯错 | 检索内容、已存证据、未命中或未使用原因 | 调整检索、去重、失效与来源规则 `M`，必要时重排角色 `O` | 仅堆更多上下文可能提高成本或引入干扰 |
| 工具输入无效或结果误解 | 工具契约、参数、错误、实际结果及后处理 | 修改技能步骤或校验 `S`，增加必要检查角色 `O` | 环境故障不能通过改科学方法来假装修复 |
| 反复提出无效修改 | 修改记录、反例、后代的真实表现与总成本 | 更新诊断、候选选择或预算策略 `R` | 改角色名字、加入更强模型、扩大预算可能解释表面收益 |

这里的归因首先是待检验解释。即使错误定位到某节点，也不能未经干预比较就认定该节点是唯一原因。任何变化都应保留触发证据、适用条件和可能使其失效的情形。

### 4.3 继承应以行为依赖记录，不按文件后缀归类

每个候选变化至少需要描述：修改了什么行为、依据哪些实际记录、预计改变后续哪一步、由哪些版本化对象承载、如何判定无效、消费它的任务与角色是谁。

执行记录需串联“失败证据 → 修改候选 → 验证 → 被后续任务实际加载 → 结果”。任务图、消息依赖、技能调用、记忆检索和工具收据都属于证据。未执行的配置、未调用的函数、没有消费的记忆，不能计作继承效果。

`R` 可能通过某技能或记忆检索策略实现，不能把它机械等同于一个文件；同一个共享函数也可能同时影响任务和改进过程。独立归因前必须画清依赖。如果无法无损分离，就报告整体版本效应，不声称得到纯粹的元效应。

### 4.4 固定内核与领域边界

预算、外部凭据、执行隔离、独立评价和证据账本可以保持稳定；可变的是受预算约束的 agent 行为。保留可信内核不违背持续自改进，也不能为了“完全自修改”让候选修改自己的评分结果。

核心不写死文献五阶段、数学方程、科研角色或模拟软件。领域适配提供任务输入、工具契约、可见反馈、评价方法和环境资源。科学发现可以使用文献、实验与报告；OpenFOAM 适配可以提供案例、求解器与工程检查；其他领域采用自己的任务工件。领域工具不是自动进化策略，数值求解器也不是多智能体编排的替代品。

## 5. 待验证的机制主张

以下是候选研究假设，**未证实，也未完成新颖性证明**。记忆、技能更新、工作流搜索与元迁移各自均已有上述先例；不能仅以组合或重新命名声称首次提出。

### H1：失败归因驱动的协作、记忆与技能联合更新

假设：当失败同时涉及信息遗漏、记忆失用和技能契约时，基于实际轨迹定位原因，再有选择地联合更新 `O/M/S`，比固定编排、只保存经验文本或单组件更新更能降低后续同类失败，并在未见任务上保持质量。

可反驳预测：在相同模型与预算下，联合方案应提高预登记的后续任务成功率或减少错误；回放时确有新对象被消费。如果仅增加调用次数就达到相同表现，或去掉所谓归因后效果不变，就不支持“归因驱动联合更新”的机制解释。没有证据要求多组件同时变化时，应允许单项修复或不修改。

### H2：跨域保留有效的改进策略

假设：从一个任务领域学到的诊断、实验选择、失败记忆使用或协作修订规则，可在另一领域从共同初始任务 agent 起步，更有效地产生改进。

可反驳预测：冻结转移前后的 `R` 及其必需依赖，在相同目标任务起点、模型和资源下，转移策略应提高开发选优后的隐藏任务收益，或降低达到同等质量的成本。如果只携带领域答案才能获益、效果只来自更大上下文/更多调用，或目标域变化为负，则应收窄或拒绝该假设。

Hyperagents 已研究元策略迁移，因此本项目不能将“跨域转移”本身作为新颖点。这里可能研究的是有运行证据支持的失败归因与协作/记忆/技能干预之间的关系；它必须通过对应消融建立，不能由架构图证明。

## 6. 实验应怎样检验这些设计

### 6.1 必须先测真实任务 agent

新的任务环境应要求被测 agent 实际使用模型与工具完成多步骤工作，产生能独立检查的产物，并具有需要反馈修订的情形。模型自评分可以是反馈之一，不能作为唯一终点评价。固定的初始 agent 必须先能运行，再比较学习与编排收益。

可选任务类型包括资料证据整合后设计并检查实验、在代码库中诊断并修复真实问题、或利用领域软件完成带约束的分析；具体任务集、许可、资源和评价在后续独立登记中确定。本文不授权执行这些任务，也不预设某个领域必须成功。

原先纯数值或确定性规则 `solve` 的 0 API 运行可以验证算法、插件、评分和隔离，但其中没有被观察的模型协作过程。即使外部设计器用了多角色，它也只证明设计过程有模型调用，不能替代“任务 agent 会编排并根据任务反馈改变协作”的验证。

### 6.2 控制必须排除便宜的替代解释

| 控制/试验组 | 保留什么、改变什么 | 回答的问题 |
|---|---|---|
| 固定任务系统 | 初始 `O/M/S/R`，相同模型和任务资源 | 自改进相对可工作的初始系统是否有价值？ |
| 更多调用的固定编排 | 工作方式不变，提供与改进方案可比的调用/token 预算 | 收益是否只是多做了几次采样、反思或投票？同时报告质量—成本曲线，不能只匹配名义调用数 |
| 只积累记忆 | 允许保存同来源经验文本；编排、技能和改进规则固定 | 收益是否仅来自更多历史信息？检索上下文规模与更新成本需计入 |
| 固定优化器架构搜索 | 用稳定搜索程序改 `O/S`，保留完整执行反馈 | 联合系统是否超越 ADAS/AFlow 类固定优化器的合理实现？固定优化器本身的阳性仍是有效结果 |
| 有选择的 `O/M/S` 联合更新 | 根据失败证据研究行为变化；`R` 可先固定 | H1 是否成立？在有针对性的组件移除与归因移除消融中是否保留优势？ |
| 可改进的 `R` | 在前述有效任务系统上进一步改变改进策略 | 更强的元递归命题是否成立？不能以此组失败否定其他已证实层面的价值 |

完整多组件因果分析可能需要组合消融，但不应先无限扩展运行矩阵。应先登记一个有明确机制差异的最小比较，再决定是否值得投入组件交互研究。本轮没有设定新调用预算或启动任何实验。

### 6.3 把任务内修订、跨任务积累和元效用分开测

- **任务内**：记录失败被识别后，实际选择了什么新步骤，是否改善当前产物；区分重试成功与规则改进。
- **跨任务**：冻结评测任务，控制任务顺序；比较记忆/技能/编排版本被后续未见任务消费后的结果。保持全新的任务与重复任务分开，防止答案记忆冒充方法迁移。
- **元效用**：冻结更新前后的改进策略及其依赖闭包；从共同目标任务系统起步产生后代，开发选优后在未反馈给改进器的任务上评分。`k` 是后代尝试资源之一，还要匹配模型、tokens、工具、墙钟与研究成本。
- **成本与缺测**：记录任务调用和改进调用，失败和嵌套过程不能漏账。执行错误的有效失败评分与资源中断缺测分开；基线保底产生的零收益要同时报告后代失败率。

限制嵌套深度应限制额外资源和自修改范围，不应把候选真正不同的行为统一替换为同一固定流程。登记前要通过实际轨迹确认待比较机制可被当前上下文激活。若没有激活，结果只能描述该上下文下的系统表现，不能外推到未执行机制。

## 7. 历史负结果怎样约束新设计

[v1 审查](framework-mechanism-v1-review.md) 记录查询契约错误、无效源码修复和未建立的元效用。[v2 审查](framework-mechanism-v2-review.md) 记录：一次 probe 完成但两组正式子代都是 0；选择器使主第二轮回到初始程序；独立科学与 BBH 评价产生了 5 个实际被评价任务后代，但开发选优均保留基线，配对收益为 0。

这些结果不因重新定位而变成成功。它们说明此前的测试覆盖了一部分源执行与评价机制，同时暴露了机制未激活、契约不匹配以及任务对象不足以检验模型编排的问题。M0/M2 在禁用 probe 的上下文中共同调用同一 `research_cycle`，尤其不能被重新解释为已经比较了不同的有效编排。

新实验必须明确改变了研究问题和被测对象，另行登记，不能继续挑选旧 seed 或修改旧结果。需要保留的工程基础是实际收据、不可变版本、真实错误、共同起点和独立评价；需要重写的是以四文件和 `meta.py` 改动为中心的产品与成功定义。

## 8. 后续设计的验收边界

在实现前，应能说明一条完整且可证伪的证据链：

```text
真实任务执行与中间反馈
    → 有依据的失败解释
    → 具体行为变化（协作 / 记忆 / 技能，可选改进策略）
    → 新版本被真实任务或后续改善过程消费
    → 在控制资源、信息与评价后观察结果
```

任何环节缺失，就报告当前已完成的环节，不补写成功。用户界面以目标、任务产物、进行中的工作、反例、已学到且实际使用的能力为主体；源码、账本和消融是可展开的证据，不要求用户不断介入内部文件。稳定且有效的行为允许保持，失败的研究假设允许结束。

本文提供的设计选择尚需落实为新的通用任务运行与研究合同。它不声明当前仓库已经实现这些行为，也不声明拟议联合更新或元迁移具有已验证的创新性。
