# NExgent 重启研究：从有限策略搜索到源码级递归自我改进

研究日期：2026-09-15。本文记录**重启实现前的文献机制复核与待验证设计**，不是当前实现或实验结果清单；后续实现见[当前架构](design.md)，科学收益仍需独立实验判断。本文取代上一轮“有限策略搜索已足以作为交付主体”的判断。它不否定已有数值测量，但不再将这些测量解释为整个智能体软件已学会改进自身。

## 1. 研究问题与取证范围

本轮问题是：如何让一个科研智能体通过外部文献、内部运行证据和实验，修改自己的任务实现、改进器实现和协作程序，并让后代实际继承、执行这些修改？需要同时回答两个问题：系统是否具备这条执行闭环；这条闭环是否产生了超出固定优化器、更多推理和经验记忆的收益。

方法：重新检索一手原文；阅读算法、实际提示词/源码差异、实验设置、成本和附录；对照本地实现定位机制缺口；形成两条实现路线和可证伪实验。没有执行模型请求。未使用二手博客作为机制证据。这是有界问题导向研究，不是覆盖整个领域的系统综述。

## 2. 上一轮实现的问题在哪里

本节依据本轮实际读取的仓库源文件，而不是从论文反推实现。旧代码随后已迁往相邻目录 `NExgent-rejected-prototype-20260915`；以下文件名均相对于该归档中的 `nexgent/nexgent/rsi/`。归档只保留在本地工作区，不随当前仓库或安装包发布。

| 实际实现 | 能证明什么 | 不能支持的结论及重构要求 |
| --- | --- | --- |
| `contracts.py` 的 `TASK_OPTIONS` 固定 library、derivative、selection、ridge、threshold；`validate_task_policy` 限制取值。 | 能在既定数值方法族中搜索配置。 | 不能生成新的求解器、诊断器、检索方法或科研工作流。把这些枚举写入 Python 文件也不会改变问题性质。 |
| `proposals.py` 的 `task_mutations`、`_alternative`、`_next_meta` 由开发者实现。 | 父代配置会真实影响变体顺序、范围和组合。 | 可变的是固定解释器的输入；解释器的搜索逻辑、提出假设的方法和修改操作本身不变。 |
| `provider.py` 固定按 evidence → critic → designer 调用，最后从 `task_choice` 表选索引。 | 三次真实模型调用和严格、可审计的有限选择。 | 模型无法改变角色数量、信息流、实验时机或改进器程序。索引方案修复了接口可靠性，却进一步明确了它是封闭候选空间。 |
| `worker.py` 的元评价从共同 `SEED_TASK_POLICY` 调用 `task_mutations`，截取两名后代。 | 公共同起点降低了已有任务水平的混淆，可测固定变异解释器在不同配置下的表现。 | 它没有加载、运行被测后代的真实 LLM 改进器，更没有测试其编写后代源码的能力。不能把该分数称为实际源码改进器的 improvement@k。 |
| 新进程、摘要、谱系、预算收据、数值保留集。 | 测量、恢复和溯源的工程基础有效。 | 被测对象有限时，再严谨的收据也不会把有限搜索变成软件架构进化。这些基础应复用，结论范围必须收缩。 |

因此，重启目标不是增加枚举、扩大 grid、让 JSON 更灵活，或把固定角色换一个名字。**可变主体必须是能够被加载执行的完整智能体软件；测试中必须观察到后代使用自己继承的改进代码产生下一代。** 共同起点本身不是问题，问题在于测试时用宿主固定算法代替了被测改进器。

## 3. 一手原文给出的机制与证据边界

### 3.1 STOP：直接把改进器应用于自身

STOP 的操作对象是程序源码，递归关系是 `I[t+1] = I[t](meta_utility, source(I[t]), LM)`；元效用通过实际执行候选改进器、让它改进下游程序来计算。它是单条递归链，没有 DGM 式跨代档案父代采样。生成的搜索程序可以改变 beam、采样和组合逻辑。实验比较 seed、贪心和思维链等方法；GPT-4 的增益不能外推到所有底模，另两种测试模型出现退化。附录示例包含 37 次元效用上限、每次 5 次重复、内部至多 6 次模型调用且每次最多 6 个样本；这些是调用预算，不是通用美元成本。作者也明确底模没有被训练更新。[STOP 算法 1、§4–5、附录 E](https://arxiv.org/pdf/2310.02304)

**启示：** 自引用必须落实为“运行新改进器源码”，而非“把新提示或元配置交给旧改进器”。嵌套评价的总成本容易乘法增长，需要在最外层统一计账。

### 3.2 DGM：可执行软件谱系与非贪心父代

DGM 让被选中的编码智能体修改自己的代码仓库，并保存仍具备编辑能力的后代。父代权重结合 sigmoid 变换后的任务表现与 `1/(1+有效子代数)`；低分祖先仍可能成为后续突破的起点。最终稿消融中，始终选最优父代的 Greedy 在 SWE 子集为 39.7%，DGM 为 50.0%。但诊断改进机会的指令生成步骤以及档案/父代选择仍固定。单次 SWE 运行约 22,000 美元，两个主要消融各约 10,000 美元，不能称为严格等成本优势。[DGM §3、A.3、C.2–C.4、E.1](https://arxiv.org/pdf/2505.22954)

**启示：** 需要区分“可保留的探索祖先”和“当前部署的冠军”；任务成绩也不能替代改进能力的独立测量。

### 3.3 Hyperagents：任务程序和改进程序共同可编辑

Hyperagents 将 task 与 meta 纳入同一个可改程序；meta 可读取档案和评价，改变生成及应用修改的过程。其 imp@50 试验固定被测 meta，从匹配的任务起点实际生成后代，正文规定按 validation 选候代、报告 test 增益。主要实验的父代选择仍固定；E.5 允许最新智能体改写选择程序，但相对随机策略的优势未达显著，且未超过手工策略。成本 D.2 写 33M 自修改 tokens 加 `0.506M×100` 评价 tokens，并报合计 88.6M；该算式实际是 **83.6M**，原文存在算术不一致，不能将合计视为精确账单。[Hyperagents §3、5.2、D.2–D.3、E.5](https://arxiv.org/html/2603.19461v1)

**协议细节：** 附录 D.3 的简写公式直接对一个任务集合取最大值，省略了正文的 validation/test 区分。NExgent 应明确写出两个集合，不能利用这个记号省略来合理化按最终测试分挑选。[Hyperagents §5.2 与 D.3](https://arxiv.org/html/2603.19461v1)

### 3.4 HGM：改进潜力不等于当前成绩

HGM 用整条后裔分支的成败估计 clade metaproductivity，再以 Thompson sampling 选择扩展；评价对象和“扩展还是再评价”的分配另行决定。相关性实验会排除直接泄漏目标的后裔支路。800 次任务评价预算下，它与 DGM/SICA 比较；论文报告 HGM 的两组分配 CPU 小时为 517、347，对应 DGM 为 1231、2385。这不是墙钟时间或完整 API 账单。其理论关联依赖理想化假设和真实 CMP oracle，经验估计器不等于实现了最优 Gödel Machine；本轮未找到将选择器、异步和评价分配完全正交拆开的消融。[HGM §3–4 与附录 D](https://arxiv.org/html/2510.21614v1)

**启示：** 保存后代贡献有价值，但相关性 credit 仍可能由“被多分配了预算”造成；需要预算匹配的兄弟分支试验。

### 3.5 后续反证线索：源码、上下文与算法变化不能混为一谈

Metaⁿ 固定元操作 Ω，通过增加其读取的低层源码/轨迹和 wrapper 深度递归。CO 消融中，移除层间上下文使分数从 0.845 降至 0.751，移除可调用代码库降至 0.825；作者把大部分增益归于上下文传递。CO 的单次生成和 agentic 运行分别报告约 5.3M、36.1M tokens。它适合作为强的上下文/层叠基线，不能替代本项目要求的改进器源码重写。[Metaⁿ §3.4、附录 C–E](https://arxiv.org/html/2608.24735v1)

AI4AI-Bench 区分修改训练算法与修改预算、容量或超参数：10 个冻结仓库，探索为单 B300、4 小时，提交源码后最多 12 小时从头训练，最终评价不对探索开放。它不测试多代智能体自继承，但说明“改了源码”仍不足以证明算法机制发生改变。[AI4AI-Bench §1–3](https://arxiv.org/html/2608.20318v1)

## 4. 论文机制 → 可执行接口 → 实验 → 失败方式

下表中的接口和试验是针对 NExgent 的设计推导，不是论文已经实现的同名 API。

| 论文机制 | 建议可执行接口/对象 | 必须补做的实验 | 主要失败方式 |
| --- | --- | --- | --- |
| [STOP 的自应用](https://arxiv.org/pdf/2310.02304) | `bundle.improve(self_source, evidence, broker)` 返回完整后代源包。 | 固定初始 improver 与继承 improver 的等预算比较；确认第二次调用的源码身份改变。 | 新程序只保存在磁盘，下一代仍调用宿主旧函数；嵌套预算失控。 |
| [DGM 的档案与分支](https://arxiv.org/pdf/2505.22954) | 内容寻址 `AgentBundle`、可查询 `LineageView`、包内 `select_parent`。 | archive、best-only、latest-only；相同模型和总预算。 | 把保留祖先误作线上晋升；只记录活下来的成功分支。 |
| [Hyperagents 的可改 meta](https://arxiv.org/html/2603.19461v1) | task、improver、orchestrator、memory routines 同属源包。 | 共同任务起点实际执行各版 meta；跨科学任务族；源码/记忆互换。 | 名义上改 meta，运行时仍由固定 evidence→critic→designer 完成工作。 |
| [HGM 的后裔生产率](https://arxiv.org/html/2510.21614v1) | `LineageView` 提供后裔成败、成本和选择概率，选择程序可重写。 | 给候选祖先等额扩展预算；与单节点分数和 clade credit 比较。 | 幸运后代、重复评价和历史预算造成 credit 偏差。 |
| [Metaⁿ 的通道消融](https://arxiv.org/html/2608.24735v1) | 将可调用源码、记忆/证据、任务输入作为不同交付物。 | old/new code × old/new memory 四格互换。 | 仅更长上下文带来收益，却归功于程序变更。 |
| [AI4AI 的干净重跑](https://arxiv.org/html/2608.20318v1) | 源包加依赖锁；只读评估环境；从原始输入重跑。 | 丢弃探索缓存后独立复现；固定训练/推理/实验预算。 | 候选依赖探索期缓存、隐藏答案或延长运行时间。 |

## 5. 路线 A：直接自应用的科研程序改进器

### 5.1 可变主体与递归

用一个可执行 Python 包实现整个研究程序，包内可以组织成多个文件，但只约定少量边界入口：

```python
# 这是边界示意，不是已实现的代码。
solve(problem, evidence_view, broker) -> ResearchResult
improve(self_bundle, evidence_view, utility_handle, broker) -> CandidateBundle
```

`improve` 可以读取并重写 `solve`、自己以及二者使用的控制流、工具封装和委派函数。`utility_handle` 是宿主提供的开发评价能力，不能更改其实现或读取最终保留集。它可以被新代码以不同的次序、次数和实验选择方法使用，总额度由宿主扣除。

第 t 代新进程加载 `B_t`，执行 `B_t.improve(source(B_t), ...)` 得到 `B_child`。独立评估后，可选择该后代继续执行。若被接受的 `improve` 改动是新的失败归因、实验选择或补丁验证算法，下一代必须使用这些新实现。宿主禁止存在“无论选谁都执行 seed improver”的快捷路径。

### 5.2 适用性与代价

优点是自引用关系清楚，容易通过源包 hash、冷启动和实际后代生成证明闭环。缺点是改进器候选的元效用要再次启动若干完整研究程序，成本嵌套；单链也容易丢失尚未显示收益的中间版本。实现可以保留所有版本，但若使用固定的档案选择器，须明示这是路线 A 的固定边界。

科研场景中，`solve` 输出的是带证据的发现，而非只有一个方程分数。任务可以要求区分两个动力学机制、设计能区分它们的干预、拟合可解释模型，并在新轨迹上复现。源码修改可涉及新的估计器、实验安排或失败检测，不应限制为预置 library 名称。

## 6. 路线 B：完整源包的群体 Hyperagent，连编排一起进化

推荐作为产品主路线。它保留路线 A 的自应用要求，同时让跨任务组织方式和跨谱系搜索成为可变软件。

### 6.1 一个版本到底包含什么

```text
AgentBundle (不可变版本快照)
  entry.py                # 稳定请求协议的入口适配
  research/               # 检索、假设、实验、推断、复现、报告的实现
  improvement/            # 诊断、设计源码变更、应用/测试和总结的实现
  coordination/           # 动态角色创建、消息路由、调度、父代选择
  shared/                 # 工具组合、证据索引、缓存/记忆读写算法
  retained_artifacts/     # 明确继承的知识与经验，和代码分开标识
  manifest + dependencies
```

这些目录只是初始组织方式，不能成为只能修改某几个函数的永久白名单。允许新建、合并、删除内部模块并改变依赖关系。manifest 描述包内入口和资源需求，不列举“允许的科研算法”。声明仍须符合宿主预算和权限。

### 6.2 运行协议与可变编排

宿主执行的最小动作是 `run(bundle_digest, operation, input_artifacts, budget_lease)`，其中 `operation` 至少区分科研任务和自改进。科研阶段如何调研、分配实验、询问同行或停止，由包内控制程序决定。固定的消息协议只是传递载体；它不应规定必须有六个角色、固定 DAG 或固定调用次序。

`broker` 提供受预算控制的模型、文献读取、实验执行、文件工件和子任务能力。包内程序能决定创建什么研究工作单、调用哪个自己实现的子模块、如何综合返回证据，也能重写这套决定程序。真实并发不是证明创新的必要条件；可变控制流和可观察的委派行为才是。

跨代搜索由包内 coordinator 建议父代和工作项。宿主核验引用确实存在、执行不可变版本、记账和保存结果。若保留固定搜索 controller，则需将它标注为尚未实现的可变范围，不能描述为“全部编排已进化”。为了分别归因，记录三个身份：**提出/执行这次修改的程序版本、被修改的基础版本、生成的后代版本**；重组多个祖先时还要记录模块来源。

### 6.3 可信宿主留下什么

宿主只保留协议解析、操作系统隔离、资源计账、工件完整性、独立测量和用户授权边界。它不替代科研推理或决定改进假设。这些边界相当于实验仪器和运行环境：允许候选重写最终评分器、伪造用量或读隐藏标签，会使改进结论失去可识别性。

源码级候选必须在隔离进程/容器中运行；把字符串 `exec` 到产品服务里，或仅靠 AST 禁止若干 import，并不是有效隔离。密钥留在宿主 broker；候选通过计账能力访问模型。此处是实现条件，当前研究文档没有声称仓库已具备这些能力。

### 6.4 两条路线的选择

| 维度 | 路线 A：直接自应用 | 路线 B：群体源包 |
| --- | --- | --- |
| 最容易证明的属性 | 改进器源码真的调用自己并产出后继。 | 任务、改进器、编排在谱系中共同继承与执行。 |
| 主要复杂性 | 嵌套元效用和单链退化。 | 多版本调度、异步结果和后裔 credit。 |
| 最小公平对照 | 固定 `I_0` 对继承 `I_t`。 | 固定 meta、固定编排、best-only 与完整系统。 |
| 推荐用途 | 第一条可检查的机制试验；不能当完整产品替代品。 | 最终架构方向；分阶段开放模块，不夸大未实现部分。 |

## 7. 可证伪的创新假设

以下均是待检验主张。自修改程序、档案、工具进化、动态协作、CMP 和 meta transfer 均已有先例；本次有限检索不足以证明任何组合具有发表意义上的新颖性。

### H1：用受控代码互换给改进器和编排分配贡献

**假设：** 相比只按任务成绩或观察到的后裔成绩选祖先，对任务源码、改进源码、编排源码做预算匹配的组件互换，能更可靠地识别可迁移的改进机制，从而提高未见任务的单位成本收益。

**可能的区别：** 本文提出把模块互换实验用于跨代搜索决策；它比只看 clade 相关性更强调干预归因，也比仅迁移一个整体 meta 更细。是否已被相关研究覆盖，仍需后续检索。

**实验：** 从同一任务起点比较 `(A_common, M_seed, O_seed)`、`(A_common, M_new, O_seed)`、`(A_common, M_seed, O_new)`、`(A_common, M_new, O_new)`，每组使用实际代码与相同总预算；记忆固定。随机分配兄弟支路的预算，报告互换失败率和非线性交互，不能只保留能跑的组合。

**证伪条件：** 收益仅在原始共同训练的整包中出现；或等额增加随机分支便消除优势；或移植的不兼容成本超过所得收益。

### H2：让“先做哪个诊断实验”成为可进化的源码

**假设：** 在对科学错误机制存在歧义时，改进器先选择能区分假说的开发实验、再提出源码修改，会比收到日志立即改代码产生更高的保留集收益/成本。

**可能的区别：** 候选不是新增一个固定 critic；可被重写的是误差分组、竞争解释、实验价值估计和停止采样的程序。它把科研方法作用于智能体自己的失败机制。这仍可能只是既有主动实验设计的应用，需要控制组来判断价值。

**实验：** 保持底模、数据和源码权限一致；对照立即补丁、固定诊断清单、可进化实验选择三组。给出预先声明的可观察预测，例如误差源于时间离散化时，改变采样间隔的实验应改变残差形态。评价预算包含诊断成本。

**证伪条件：** 额外实验只增加 tokens；机制预测不准；收益在没有实验、仅多一次模型推理时同样出现。

### H3：可迁移的自适应协作算法，而非固定多人提示

**假设：** 让协作程序随失败证据重写，并验证它在不同科学任务上如何安排独立复现、并行探索和合并证据，能优于固定角色图及同等 tokens 的单智能体。

**实验：** 冻结任务算法后互换协作代码；用固定三角色、固定更大图、单体更多推理、可变编排四组对照。角色是否真实被调用、消息依赖、重复工作量和总延迟均由宿主计量。删除新增协作机制后重跑，检查是否恢复原失败模式。

**证伪条件：** 去掉协作源码只保留其文字建议后收益仍在；固定图获得同等表现；新编排仅靠更多请求取胜。

## 8. 源码级 improvement@k：测真正被改进的程序

为避免把任务水平、提示积累或固定 seed 代理误认作 meta 能力，使用下面的操作化协议。它是基于上述文献的本地实验设计。

1. 固定任务起点 `A_ref`、开发/验证/最终测试分组和底模；冻结待比较的改进器源码 `M_seed`、`M_t`。**冻结的是每组被测程序的版本，不是将其替换为宿主算法。**
2. 各组实际运行自己的 `M`，从 `A_ref` 及其后代生成源码包；允许各组提出不同算法和内部编排。每次改进尝试都扣预算，语法失败、无效提交和超时也不免费。
3. 同时限制候选尝试数 k、模型 tokens、开发评价次数和墙钟时间；只匹配 k 不足以证明计算公平。若研究父代选择，则把 `G` 作为显式实验变量；若研究纯 `M`，各组保持同一 `G`。
4. 仅在 validation 上选定版本；最终 test 只在选择结束后评价。报告

```text
A_star = argmax_A validation_score(A), A in {A_ref} union generated_candidates
imp@k(M; A_ref) = test_score(A_star) - test_score(A_ref)
```

5. 单独报告所选后代的退化率。把 `A_ref` 加入候选集合是保留部署控制的约定，必须公开；不同选择约定的 imp@k 不直接混用。
6. 扩展为任务族外测试、不同起始任务算法和多随机种子；固定数据随机种子不能消除 API 本身的随机性，后者通过重复运行和用量收据处理。
7. 改进器在测试阶段可以修改目标 task 源码，但不能修改自己；这项冻结用于隔离已获得的改进技能。主运行中的 meta 则继续允许自修改。

元评价不能再调用固定 `task_mutations` 代替 `M_t`。它也不能将进化后更强的 `A_t` 直接作为新组的独有起点。

## 9. 分层验收与诚实的负结果

| 层次 | 必须可审查的证据 | 不能据此宣称 |
| --- | --- | --- |
| 接口能运行 | 完整源包、可重建依赖、真实 Provider 及科学实验、失败收据。 | 已发生自我改进。 |
| 源码继承闭环 | `B0 → B1 → B2`；每次实际执行的源包 hash；B1 的改进源码参与生成 B2；动态控制流发生可解释变化。 | 改变必然有益。 |
| 任务能力提高 | 共同任务、同等总预算、独立保留集与冷启动复现，和静态强基线比较。 | 改进器能力提高。 |
| 元能力提高 | 真实源码 improvement@k；任务起点/预算匹配；新任务族；源码/记忆互换。 | 已证明无界加速或通用智能。 |
| 创新机制获得支持 | 预先声明机制预测、针对性消融和竞争解释检验。 | 未检索所有先例便声称首创。 |

首次小规模运行应定位为机制试验：检查继承、拒绝和执行链，允许得到零提升甚至退化。正式效能实验应先小样本估计成本与方差，再确定任务数/种子数；不得为了“跑出成功”反复改评价或增预算后仍沿用原结论。

不要使用刻意不能解析正常任务的 seed 来制造巨大相对收益。至少配置一个合理静态科研代理、一个固定源码改进器，以及一个等预算更多推理对照。离线确定性 stub 可以测试隔离和继承协议，但只能称协议测试，不能代替源码 RSI 的智能行为证据。

## 10. 研究流程如何成为产品，而不再成为用户要操作的 harness

用户给出问题、证据范围和资源预算后，系统应自己产生研究计划、检索原文、形成竞争解释、安排实验、检查结果，并在有证据时提出自身软件改进。信息窗口显示当前研究问题、关键证据、正在检验的假设、实验结果、当前可信结论、预算和实际能力变化。

内部可以有多种研究职责，但没有必要让用户逐条批准每条角色边或源码补丁。系统将“需要用户价值判断或新增权限”的决策与“研究程序自己的执行决策”区分。实现阶段首先交付完整可运行的软件闭环及透明证据，再检验效率和科学收益；界面只是观察这个系统的窗口。

**当前推荐：** 用路线 A 建立一条真实的源码自应用证据链，作为路线 B 的实现与测试基础；主架构采用路线 B。不得把 A 的初步冒烟结果、一个离散选择 demo，或一份未来设计文档再次当作完整源码级 RSI 产品交付。

## 11. 2026-09-16 实现后的估计对象与识别条件

本节是实现后的追加说明。§1–10 保留了 2026-09-15 的研究推导与当时状态，不能将其中“尚未实现”或较开放的理想接口当成当前软件清单。当前实现采用 `task.py`、`meta.py`、`workflow.py`、`roles.json` 源包及受限 Python 能力协议；源码均可继承，宿主能力、评分器与预算保持固定。§6 的任意多模块/任意依赖包路线尚不等同于当前四文件实现；隔离收据也明确 `os_filesystem_container=false`，独立进程加语言限制不被表述为容器证明。实现依据：[源码包与 splice](../../src/nexgent/kernel/programs.py)、[实际进程运行器](../../src/nexgent/kernel/runner.py)、[元评价](../../src/nexgent/evolution/meta_evaluation.py)、[实验控制器](../../src/nexgent/evolution/controller.py)。

### 11.1 三个不同的估计对象

| 对象 | 当前可执行干预 | 估计的效应 | 不可混用的解释 |
| --- | --- | --- | --- |
| 一份任务程序是否更好 | 冻结完整源包，直接执行 `solve`，在共同任务/种子上评分 | 特定包的任务质量、失败率和实际成本差异 | 任务分数上升不等于产生后代的能力提高 |
| 哪一组源码影响了任务表现 | `task` 初始/演化 × 非 task 源码初始/演化的 2×2 互换，直接执行 `solve` | 模块替换的条件效应及交互 | 这里没有运行 `improve`，不能称为元生产率实验 |
| 改进器是否更会改进 | 相同任务起点分别实际执行两版冻结的 `improve`，开发集选后代后再转移评价 | 固定预算下生成更好任务程序的能力 | 不能只给演化组更强的现成 task，也不能用宿主固定优化器代理其源码 |

“任务代理与 meta 同属可编辑程序”及跨域 meta 迁移已有 Hyperagents 先例。本项目把实际后代、来源收据和模块交换串起来作为审计与归因方案；实现这一方案本身不证明新的元学习算法。[Hyperagents §3、§5.2、附录 D.3](https://arxiv.org/html/2603.19461v1)

### 11.2 直接 2×2：任务模块与非任务模块的条件效应

令 `T0,T1` 是初始/演化 `task.py`；`N0,N1` 是相应的 `meta.py + workflow.py + roles.json`。在固定 split 和数据种子 s 下，定义：

```text
Y[a,b;s] = score(solve(splice(Ta, Nb)), split, s)
task_effect_given_N0 = Y[1,0;s] - Y[0,0;s]
task_effect_given_N1 = Y[1,1;s] - Y[0,1;s]
non_task_effect_given_T0 = Y[0,1;s] - Y[0,0;s]
interaction = Y[1,1;s] - Y[1,0;s] - Y[0,1;s] + Y[0,0;s]
```

四格都必须报告，包括不兼容、超时与预算缺测；不能删掉不利的交换再宣称组件可迁移。源包在同一命名空间中按 `workflow.py → task.py → meta.py` 执行：task 可以调用 workflow 帮助函数，meta 也可能覆盖同名函数。因此 `N` 的直接效应可能只是共享依赖或名称覆盖；它不意味着该 meta 更会研究，也不自动分离 `meta.py` 与 `workflow.py` 的贡献。

这里的识别条件是：固定任务数据、评分器、运行器、数值预算和原始观察输入；文件来源与组合可重建；缓存的身份包含上述条件；失败不按正面结果筛除。若希望进一步归因“meta 控制流”与“协作 workflow”，需要另外执行两者的交叉组合，并逐格运行真实 `improve`。当前直接 2×2 不提供这个更细的估计量。

### 11.3 当前实际 improvement@k 的精确定义

当前函数冻结每个被测非 task 程序 `N_j`，形成共同任务起点 `P_j = splice(T_ref,N_j)`。**每次调用均从同一个 `P_j` 出发**；当前 k 不是采用后代 meta 的递归深度，也不是顺着上一子代 task 连续爬坡的代数。这细化了 §8 的一般方案。

1. 各组先取得同一数据种子的 development 基准。冻结代码、公开历史、角色模型映射、候选额度与资源上限；各组实际执行 `P_j.improve`，不能替换为固定代理。
2. 每组最多 k 次调用和 k 个后代名额。批量回复按返回顺序消耗名额，超量明确记录；空回复也消耗尝试，失败调用不自动重试以补齐 k。改进器内部的多角色推理和一次修订属于同一次实际 improve 的成本。
3. 模型可以同时提出 task/meta/workflow 修改。原始回复与完整源包保留；实际计分使用 `splice(candidate,P_j)`，并记录 `discarded_non_task_changes`。被测 improver 在此实验内不自我更新，两个组以同一规则投影。
4. 在 development 上，从起点及有效后代中选分数最高者；同分保留较早者，起点排首位。资源缺测不当作 0 分参加比较。
5. 选择完成后，仅对起点和选中后代执行 `meta_transfer`。转移结果不进入任一组的生成上下文或修订，也不把另一组刚出现的错误历史提供给后执行组。

```text
C_j = {P_j} union {projected valid offspring of actual improve(P_j)}
A*_j(s) = argmax[A in C_j] development_score(A,s)
imp@k_j(s) = meta_transfer_score(A*_j(s),s) - meta_transfer_score(P_j,s)
paired_gain(s) = imp@k_evolved(s) - imp@k_initial(s)
```

必须按各组自身的 `P_j` 扣除起点分数，因为共享非 task 代码也可能改变 `solve`。即便扣除起点，这个差值仍是“整个冻结非 task 实现与其 task 接口”的效应，不是纯抽象算法能力。投影若破坏新 task 与新 workflow 的联合依赖，也应保留失败：它说明一次任务改进无法脱离共同演化模块独立移植，不应悄悄换回完整候选以提高成绩。

调用返回的 `execution` 必须指向请求的 bundle、source digest 与 `entry=improve`。缺失收据可以保留描述性数字，但证据层级降级；身份不符、资源失败和中断不能补零后生成正面均值。仅对完整配对取均值时，同时列出全部缺失原因和种子，说明非随机缺失会造成选择偏差。当前默认的小 k 是可负担的机制检验，其数值不可直接与论文的 improvement@50 等同。[Hyperagents 的 improvement@k 设置](https://arxiv.org/html/2603.19461v1#S5.SS2)

### 11.4 “匹配预算”需要核对哪些量

当前独立 meta study 为**每次真实 improve**设置相同上限：6 次模型请求、30,000 预约 completion tokens、3 次开发实验尝试；实验次数在进入评价前扣除，缓存复用不绕过尝试上限。另有总调用/评价预算、每次模型 180 秒上限、improve 总时限和共享数值预算。新 seed 的常见路径是 3 次请求，触发一次修订时为 4 次、最多 16,400 预约 completion tokens、通常最多 2 次开发实验；这是初始源码行为，继承程序仍可在相同宿主上限内改变分工与顺序。[预算执行位置](../../src/nexgent/evolution/controller.py)

相同上限不等于相同实际花费。模型输入 tokens、回复 tokens、角色调用数、失败/未知账单、数值工作和墙钟时间必须分别报告。30,000 是 completion 的预约上限，不是输入加输出总 token 上限；若长上下文组显著更贵，不应将其优势解释为等成本创新。角色到模型的实际映射也要从收据核验：相同默认配置不保证所有新角色最终使用同一模型。

数值工作按顶层 report 的 `work_units` 计一次，不叠加包含于其中的工具收据；broker 实验和正式计分若共享 `measurement_key` 则去重。没有 key 时不能仅凭数值相等认定重复。跨 study 复用缓存时，应同时给出逻辑预算和新发生的物理计算；复用不能被写成一次新的独立复现实验。失败已预约的模型请求不免费，未知 usage 不推定为零。

识别目标是“相同可用资源制度下的程序效果”，不是对所有观测强行截成同等实际费用。若要主张单位成本优势，应预先定义成本口径并给出质量—成本关系，不能在看到结果后只选有利口径。

### 11.5 源码继承由实际执行证明

最小闭环证据不是文件时间戳或模型自述，而是可连接的来源链：

```text
B0 source + improve execution receipt -> generated B1
B1 differs from B0 in executable meta/workflow
B1 source + entry=improve execution receipt -> generated B2
```

逐项核验：B1 的 bundle digest 和 component digests；其真正父代；生成 B2 的 `execution.bundle_id/source_digest/entry`；调用图/角色和输入输出 artifact；B2 的生成事件及源码。这证明改动过的程序参与了下一代生成，仍不证明其改动有益。

`select_parent` 的收据只证明该版本的选择程序被运行。若它选择祖先 B0，而实际 improve 又执行 B0，则不能说 B1 的改进器生成了下一代。同样，roles.json 文案变化不直接等于 workflow 控制流变化，task.py 增加预算 guard 也不等于 meta 算法变化。档案保留、探索父代、部署晋升是不同事件。当前 Store 可能让相同 source+parent 的开发实验包与正式候选共享 ID；若首个存储元数据来自实验，需要从 `offspring_generated` 的 artifact 恢复正式假设和代码证据，不能仅依赖 bundle 的初始 rationale。

### 11.6 两个演化种子与三个转移种子

[注册批次 source-rsi-20260916-v2](registered-source-batch-20260916.json) 包含演化种子 **11、22**，每个种子有 full/task_only/greedy 三个组、各三代，所有组共享初始程序 `agent-07bf1dac73f145b3240d` 和相同公开先验研究。每个 study 上限为 24 模型调用、120,000 预约 completion tokens。这里的两个种子控制开发数据与演化过程的任务环境；它们提供每个组两个独立研究轨迹，不能保证外部 API 采样被同一随机数完全控制。

统一确认阶段预先指定的 **7101、7202、7303** 是三个转移数据种子，用于对已经冻结的最终程序做成对检查；本审查不读取它们的结果。三个转移重复不会把两条演化轨迹变成六条独立的算法学习重复。正确汇总先在每条演化轨迹内对转移重复配对，再报告两条轨迹间的一致性；不把同一后代上的所有任务行堆起来当作大量独立算法样本。

另一个维度是实际 meta study 的数据种子：模块 API 默认 101/202/303，controller 当前默认 401/502/603，均须以那次独立注册为准；不能因为也有三个种子就与上述统一 confirmation 混同。主运行自动产生的内部 final_transfer 也不是本次公开机制审查的数据来源。

当前两演化种子的设计足以暴露执行链、预算失败和方向不一致，尚不足以稳定估计广泛分布上的效应或宣布统计显著。确认数据必须等最终程序/比较对象冻结后统一查看，不能边看边决定下一份候选代码。机制审查只读公开源码、development/selection 证据，并在[公开机制归因审查](source-mechanism-review-20260916.md)保留模型主张与实际实现不一致的记录。

### 11.7 由公开反例提出的下一项机制实验

两条 full 轨迹的正式后代均未改变 meta/workflow/roles；因此把它们的非 task 部分与初始程序做付费生成比较，只会比较同一改进器的抽样重复，不能估计元算法变化。本结论来自公开源码与生成/selection 记录，不使用确认集。下一项假设应针对已观察到的缺口：源程序缺少实际探测新改进器所生成后代的能力，而且修订审计存在“声称改变机制、实际只改注释”的反例。

[机制审查 §5](source-mechanism-review-20260916.md#5-下一项元机制研究把实际改进器探测交还给研究程序) 给出尚未实施的 `probe_improver` 契约：同一已注册 task 起点、冻结公开历史、真实执行新旧 improve、开发后代效用反馈、最大嵌套深度 1、同账本预算与单 outer 一次探测。两代机制 pilot 首先检验真实反馈和继承，零收益、负收益及未验证修订仍保留其证据状态；能力接通与元生产率提高是不同结论。

Nexgent 的定位是**通用 RSI 智能体框架**。科学发现是本文的演示领域；核心 seed、模型编排、源码继承和探测不能依赖 SINDy、动力系统或固定任务数量。领域任务、工具、文献、种子与评价由独立 adapter 注册，通过 `context.domain/task_contract/tool_api/literature` 提供给同一通用研究程序。将科学内容移至 `examples/scientific_discovery` 与第二领域验证属于下一阶段工作，尚不能当成已完成或跨领域效果已获证明。

**0.8 实现状态补注（2026-09-16）：** 上段及 §11.7 的“尚未实施/下一阶段”描述保留的是 0.7 审查结束时的设计状态。现已完成通用核心与领域包的源码分离；最终实际路径为 [benchmarks/scientific_discovery](../../benchmarks/scientific_discovery/) 和 [benchmarks/bbh](../../benchmarks/bbh/)，并非先前拟定的 `examples/`。领域通过 `nexgent.benchmarks` entry point 注册，核心 `agents.seed` 要求注册领域提供 task 源码，不再导入科学包或固定科学任务数量。科学方法资料与提示归属科学插件，BBH 插件是另一个领域适配器。

`probe_improver`、实际新旧改进器执行、探测后证据反馈与未验证修订的区分也已实现。独立 `controller.meta_evaluate` 已经由真实本地源码进程的跨 benchmark fixture 验证：两个原始 M 分别保留身份，共用目标 task 起点；目标工具和契约进入实际进程；跨域不运行旧 task 的 2×2 归因；私有转移反馈不进入后续生成请求。顶层或任务行显式 `score_available=false` 均作为缺测。这些测试使用脚本模型回复，证明接口与执行链，不能证明真实模型跨领域元生产率提高。上文两个 full 的无 meta 改动结果及注释修订反例保持不变；新两代真实模型机制 pilot 尚需按其独立注册记录报告结果。
