脚本模拟了什么：脚本化的 Claude Messages API 服务端，按系统提示里的 `Member: <name> (<form>)` 行给每个会话分别应答，经 `@nexgent/sdk` 驱动，共 11 个项目：

- 直接执行；委派（fresh 带资料、fork 带父历史、同名成果、子进程里强杀 fork 成员后恢复）；
- 只读父会话下的预设与沙箱继承；PTC、表格、网页三个工具；
- 工作流（脚本、图、含环的图被拒、强杀后恢复）；团队（并发、邮箱、任务板依赖，强杀 Lead 后恢复）；
- 取消传播（委派、队友、工作流成员）；费用树；成员审批；用户级技能。

最后用全新 SDK 查询恢复后的状态。注入的故障：子进程强杀（fork 成员流到一半、工作流成员流到一半、团队消息排队未投递时）、流式超时、调用方取消、run_code 超时。

桌面层：先跑步骤 2 的桌面场景（D01–D10），再跑成员场景（D11–D14）。成员场景是真实 Electron 主进程、真实界面、真实 SDK，模型用脚本化服务端：委派成员、成员审批、子会话只读视图，以及成员流式时强杀主进程并重启。

全量 `pnpm test`（`850a8cdf` 的内容，Linux）：114 个文件，1427 通过，9 跳过，0 失败；`tsc -p tsconfig.tests.json` 通过。

## 失败与缺测

- 失败的用例与原因：正式运行没有失败项。本步骤开发中发现并已修复的缺陷：
  - 恢复的成员不计入 `formsUsed`（H10 发现，#71 修复）；
  - 在 `approval.request` 事件回调里同步回答审批会被丢掉，回合挂起（H14 场景发现，#73 修复，场景改为同步回答以固定修复）。
- 没有测到的部分：
  - 真实模型只在 Linux 跑过；R08（Windows 真实模型）是可选项，这次没跑。
  - 每种形态只跑了一次，没有成功率或时延分布。
  - 真实模型层运行在 #73 合入之前的基线上，#73 之后没有复跑。
  - 桌面层没有接真实模型；macOS 没有测；安装包没有打。
  - 真实模型下 fork 委派、强杀恢复、取消没有测（只在脚本化 provider 下）。
- 已知但未修的问题：
  - kernel 的 `perProject` 费用上限仍未生效（步骤 1 遗留）。费用只按 token 显示，没有价目表。
  - 真实模型在“不指定形态”时选了直接执行，这是预期内的；被要求团队或工作流时都照做了。

## 结论边界

- 本记录证明：
  - 脚本化 provider 下，`accept-step3` 的无界面层 23 项与桌面层 14 项在 Linux 上全部通过。覆盖委派（fresh / fork）、团队、工作流、PTC、表格、网页、技能、费用树、成员审批、取消传播、强杀恢复与恢复后查询，以及桌面应用里的成员块、子会话视图、成员审批和重启。
  - 真实 Claude Sonnet 5.5（thinking 开）用直接、委派、团队、工作流四种形态，以及不指定形态，各完成一次两轮补货任务。成果由隐藏判定独立验证，累计估算花费远低于 15 美元上限。
  - 仓库里没有 Python 文件（H23）。
- 本记录不证明：
  - 协作形态比直接执行更好或更省；
  - 成功率与时延（每种只跑一次）；
  - macOS、Windows 真实模型、安装包；
  - 实际账单金额。
- 是否满足退出门槛：第 1 项 满足（Linux 本地与 Windows 手动运行都通过）；第 2 项满足；第 3 项的“没有 Python 文件”满足，验收记录待用户认可。
