脚本模拟了什么：一个脚本化的 Claude Messages API 服务端回答同一项目里的所有请求（用户任务、诊断、提案、门控回放、反馈检查、评审），全部经 `@nexgent/sdk` 的产品路径，改进作业由 SDK 自带的 improve-entry 在独立进程里运行。

- **主链**：3 条计入的反馈开始作业，诊断、提案（快照副本里）、门控（selection 含反馈任务，反馈检查候选通过、基线不通过）、采用；新进程里的下一任务加载组件，`firstUse` 有记录。
- **失败检查**：测试通过后文件被改坏、测试失败照样交付各计 1；失败的探索性命令与先失败后修好的测试不计（用户 2026-10-13 选 B）。
- **自动改进关**：反馈只记录，不开作业。
- **显式作业与异常**：诊断报告被拒 3 次、proposalKind none、两个组件、预算用尽（以及用尽后再 run 被拒）、组件抛错。
- **等待历史、并发与恢复**：历史不足时等待，补齐后继续；两个进程同时提交只开 1 个作业；作业进程被强杀后重开标为 interrupted、不重跑。
- **H19**：重跑步骤 4 的无界面层。
- **桌面层**：先回归 D01–D18，再跑“改进”页（D19–D23：作业卡片与作业文件一致、成果卡片上的“改进”、设置保持、首次被任务使用）。

## 失败与缺测

- 失败的用例与原因：正式通过的第 2 次没有失败项；第 1 次的失败与修复见上表；脚本化层在 Linux 上没有失败（全量测试有一次偶发超时，见上），在 Windows 上前两次的失败与修复见“Windows”一节。
- **第 2 次运行发现的缺陷（能力存储，不影响 R01–R06）：被抢先的采用会留下一条假的“adopted”决定。**
  - 现象：第二个作业的候选 `23bb11e9` 有两条决定，同在 13:29:30：`4dc6e974` 写着 outcome adopted、revision 2、toVersion `398b2297…`；紧接着 `5742cf42` 写着 rejected（interrupted）。实际的采用链里 revision 2 是会话候选的 `2a35cff6…`，`398b2297…` 从未生效。按决定列表看历史的人会看到一次没有发生的采用。
  - 原因：`packages/capabilities/src/capability-store.ts` 的 `#commit` 先 `writeDecision`，再 `commitActivation`；后者发现采用链已被别的进程推进时返回 null，但已写下的 adopted 决定没有撤回或标记。门控（`packages/capabilities/src/trial/gate.ts` 约第 526–536 行）随后再写一条 interrupted。回滚走同一个 `#commit`，同样受影响。
  - 处理：#119 改为先提交修订、成功后再写决定，被抢先时只留 interrupted 决定。修复后没有用真实模型重现这一竞争；脚本化层与 Windows 第 3 次运行都包含 #119。
- 没有测到的部分：
  - 真实模型只完整跑通一次；门控在 2 次完整运行的 4 个作业里采用 1 次。
  - 第二个作业没走到采用：它被一个会话候选抢先，不能说明第二个作业的候选本身好坏。
  - 反馈检查由评审模型判定，没有人工复核它的判断；确定性检查与隐藏判定是脚本里的纯函数。
  - 只测了技能；函数模块、上下文策略、插件在本步的真实模型下没有作为改进作业的候选进门控。
  - R08（Windows 真实模型）、macOS、安装包没有测；桌面层没有接真实模型。
  - 改进预算用尽、作业被取消、awaiting-approval 后由用户批准这几条路径只在脚本化层测过；awaiting-approval 批准后作业状态是否跟着更新，真实模型下没有触发。
- 已知但未修的问题：
  - 费用是按 token 与价目表估算的，不是账单。
  - 模型在普通任务里会自己用能力工具提交会话候选（本次 2 个），它们的门控费用（1.67 美元）不算在改进预算里，单列为“作业以外的门控试验”。

## 结论边界

- 本记录证明：
  - 脚本化 provider 下，`accept-step5` 的无界面层 19 项与桌面层 23 项在 Linux 和 Windows 上全部通过，覆盖“脚本化 provider 结果”一节列出的场景。
  - 真实 Claude Sonnet 5.5（thinking 开）在 Linux 上一次跑通主链：
    - 用户只给出缺一列的反馈、不提能力工具，第 3 条计入的反馈后改进作业自动开始；
    - 诊断合 schema，提案在快照里产出一个技能候选；
    - 门控的回放集含反馈任务，反馈检查与确定性检查分开记录，候选在两者上都更好（100% 对 67%、100% 对 0%），以 quality-up 采用；
    - 新 OS 进程里的下一次同类任务自动加载并调用该技能，账本可证，反馈指出的那一列出现了，`firstUse` 有记录；
    - 每个任务、反馈轮与作业阶段都有费用，改进费用单列。
- 本记录不证明：
  - 改进流程的成功率或稳定性（修复后只跑了一次）；
  - 反馈检查的判断正确（评审模型判，没人工复核）；
  - 第二个作业的候选能被采用；
  - 函数模块、策略、插件经改进作业进门控；
  - Windows 真实模型、macOS、安装包；
  - 实际账单金额。
- 是否满足退出门槛：
  - 第 1–3 项满足：真实模型第 2 次运行的 R02–R05，以及脚本化的 H 项；
  - 第 4 项满足：Linux 通过，Windows 手动运行第 3 次通过；
  - 第 5 项满足：真实模型主链跑通，工作留在 nexgent-app，验收记录经用户认可（2026-10-13）。
