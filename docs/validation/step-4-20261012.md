## 步骤

- 步骤编号与名称：4，能力变化进入真实运行
- 退出门槛（与 `accept-step4` 摘要里的 `exitCriteria` 相同）：
  1. 跨任务、跨进程实际调用：任务 A 开发并使用的组件经门控采用后，新 OS 进程里的任务 B 自动加载并调用它，账本可证；
  2. 自动回滚：注入一次退化后，宿主自动退回上一版本，之后的任务用回旧版本，账本与采用历史可证；
  3. 被拒候选留档：门控判为变差的候选保留组件、回放结果、费用与拒绝原因，原版本照常可用；
  4. `accept-step4` 无界面层与桌面层在 Linux 本地通过（脚本化 provider）；验收前 Windows 手动运行一次；
  5. 真实模型一次（Linux，thinking 开）主链跑通；验收记录 `docs/validation/step-4-<日期>.md` 经用户认可；工作留在 `nexgent-app`。
- 验收脚本：`scripts/accept-step4.mjs`，共 44 项：
  - 无界面层 H01–H19：H19 重跑步骤 3 的 H01–H23；
  - 桌面层 D01–D18：D01–D14 是步骤 2、3 的桌面项，原样回归；
  - 真实模型层 R01–R07：R07 为 Windows 可选，不进门槛；
  - 另记中期检查点 4 项，不进退出码。
- 判定：都是纯函数，在 `scripts/accept-common/step4-judges.mjs`、`step4-desktop-judges.mjs`、`step4-real-judges.mjs`。每个判定都有反例测试（`packages/test-support/tests/accept-step4*.spec.ts`）：H 与 D 用改坏的观测，R 用手写的观测再改坏。

脚本模拟了什么：脚本化的 Claude Messages API 服务端，经 `@nexgent/sdk` 驱动，分三个场景。

- **步骤 4 场景**（H01–H05、H07、H10、H13、H14、H17、H18）：
  - 基线任务；
  - 任务 A 起草、试用、调用函数模块和技能，草稿区拒绝文件工具；
  - 并行会话看不到试用组件；
  - 只有成功调用过的组件能提交；
  - 能力包内容寻址、写成后不可改；
  - 新 OS 进程里的任务 B 自动加载已采用版本并调用组件；
  - 篡改能力包后加载被拒、自动回滚；
  - 上下文策略不能碰审批、费用、沙箱、门控字段；
  - 插件试用与采用各审批一次；
  - 成员没有能力工具；
  - 账本完整，导出物里没有测试密钥。
- **门控场景**（H06、H08、H09、H11、H12、H14 的采用部分、H15、H16），在独立项目里实跑门控进程：
  - 历史不足时等待；
  - 历史足够后同一应用里 `capabilities.trial` 直接起门控（本轮去掉了先前“重启应用再试”的绕行，H15 增加这一条）；
  - 好候选被采用，坏候选被拒绝并留档；
  - 改坏已采用的模块后，3 个任务内按 component-errors 回滚；
  - 试验额度用尽结论为 unknown、不采用；
  - 打平时由评审模型决定，插件停在等待审批；
  - 强杀门控进程后，重启时标为中断，不重跑。
- **H19**：重跑步骤 3 的无界面场景与判定，23/23。

桌面层：先跑步骤 2、3 的桌面场景（D01–D14），再跑能力版本场景（D15–D18：右栏版本、候选状态与拒绝原因、插件审批框、手动回滚后版本与采用历史一致）。

## 失败与缺测

- 失败的用例与原因：正式通过的第 6 次没有失败项。前 5 次的失败与修复见上表；脚本化层在本轮没有失败。
- 没有测到的部分：
  - 真实模型只完整跑通一次；门控在 3 次完整门控里采用 1 次、拒绝 2 次（都在 #98 之前）。#98 之后只跑了一次门控，采用率没有统计。
  - 任务 A 的要求点名了能力工具。只说“做成可复用的”时，模型不会主动用能力工具（第 1 次运行）。
  - R05 的退化是注入的：脚本把一份坏副本作为一次采用写入，不是模型自己写坏的。
  - 只测了函数模块；技能、上下文策略、插件在真实模型下没有进门控。
  - R07（Windows 真实模型）、macOS、安装包没有测；桌面层没有接真实模型。
  - 回滚规则在真实模型下只触发了 component-errors（连续报错）；按检查通过率回滚的那条在真实模型下没有触发。
- 已知但未修的问题：
  - 插件候选在门控回放时会执行插件代码：用户已决定保持现状（选 A，2026-10-12），不列为待定风险。
  - 费用只按 token 估算，价目表写在验收脚本里（`step2-real.mjs` 的 PRICE），不是账单。

## 结论边界

- 本记录证明：
  - 脚本化 provider 下，`accept-step4` 的无界面层 19 项与桌面层 18 项在 Linux 和 Windows 上全部通过，覆盖“脚本化 provider 结果”一节列出的三个场景与桌面层。
  - 真实 Claude Sonnet 5.5（thinking 开）在 Linux 上一次跑通主链：
    - 任务 A 开发并使用一个函数模块，提交为候选；
    - 门控在回放集上两侧各跑 2 次，以费用更低采用；
    - 新 OS 进程里的任务 B 自动加载并调用它，账本可证；
    - 注入退化后，宿主在 3 个任务内自动回滚，之后的任务回到原版本；
    - 每步都有费用，试验费用单列。
- 本记录不证明：
  - 能力版本让任务更准：所有回放两侧检查都通过，采用的理由只是更省；
  - 门控的采用率或稳定性（修复后只跑了一次）；
  - 模型在没有提示时会主动沉淀能力；
  - 真实模型下技能、策略、插件的门控；
  - Windows 真实模型、macOS、安装包；
  - 实际账单金额。
- 是否满足退出门槛：
  - 第 1、2 项满足：真实模型第 6 次运行，以及脚本化的 H07、H09；
  - 第 3 项满足：脚本化的 H08，真实模型第 4、5 次的被拒候选也留了档；
  - 第 4 项满足；
  - 第 5 项的“真实模型主链跑通、工作留在 nexgent-app”满足，验收记录等待用户认可。
