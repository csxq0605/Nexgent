| 模型（thinking 开 / 关） | 任务 | 调用数 | 已知 tokens（输入 / 输出） | 未知结果数 | 费用 | 结果 | 摘要文件 |

- 本机运行说明：`NEXGENT_API_KEY=<key> node packages/llm/scripts/smoke.mjs`（一次带工具调用的请求，打印用量）；完整任务：`NEXGENT_API_KEY=<key> node apps/cli/bin/nexgent.mjs run --project <dir> --task "..."`，会话在 `<dir>/.nexgent/sessions/`，账本在 `<dir>/.nexgent/ledgers/`。
- 运行环境：Linux 本地（Linux 6.18、Node v22.22.0、pnpm 10.28.0），端点 `https://api.anthropic.com`，密钥来自 `NEXGENT_API_KEY`，项目配置为 `nexgent run` 新建的默认值（`thinking: off`、`effort: medium`、`workspace-write`）。
- unknown 的来源：两次真实运行中输入、输出、缓存读 token 全部已知，没有 `status: unknown` 的请求，`unknownUsageCount` 为 0。`reasoningTokens` 每次都是 `unknown`，这是设计如此：Messages API 不单独报告思考 token（且本次 thinking 关）。脚本化运行中 `unknownUsageCount` 为 5 是因为被杀进程的那次请求没有 `llm.request.end`，其余请求用量来自脚本。
- 用量口径：`inputTokens` 只是未命中缓存的输入，不含缓存读与缓存写。`packages/llm/src/usage.ts` 丢弃了 `cache_creation_input_tokens`（契约里没有对应字段），所以完整任务第 1 次请求显示输入 4 token，而实际提示约 2.35k token 都写入了缓存；CLI 结尾的 `tokens in 10 / out 385` 因此明显偏低。
- 费用：账本不记费用，且缺缓存写入 token，无法从账本准确算出费用，本记录不填数字。

## 失败与缺测

- 失败的用例与原因：无。
- 没有测到的部分：真实 Claude Platform 下的 thinking 开、`between_tools` 映射、服务端回退、拒答处理、`resume` 续聊与中断恢复（真实模型只跑了 `smoke.mjs` 与一次 `nexgent run`）；Windows 上的真实模型运行；审批提示的端到端交互（验收脚本在非 TTY 下全部按拒绝处理）；`apps/cli/bin/nexgent.ps1` 启动器未执行；macOS。
- 已知但未修的问题：Windows 进程树终止用 `taskkill /T`，没有 Job Object，已脱离进程树的后代进程杀不掉；`perProject` 费用上限只定格式未执行；`pause_turn` 按 `stop` 处理，不自动续跑；缓存写入 token 不进账本（见上，用量与费用偏低）；`nexgent run --help` 仍写着默认模型 `mimo-v2.6-pro`（`apps/cli/src/args.ts:220`），实际默认是 `claude-sonnet-5-5`。

## 结论边界

- 本记录证明：在脚本化 provider 下，`nexgent run` 能完成写文件任务并持久化会话与账本；进程被强杀后新进程能恢复会话并续跑；以上在 Linux 与 Windows CI 上都成立。在真实 Claude Sonnet 5.5（thinking 关）下，provider 能流式解析工具调用并报告已知用量，`nexgent run` 能在 Linux 上以 4 次请求完成一次真实写文件任务，会话与账本完整。
- 本记录不证明：真实模型在 thinking 开、长任务、中断恢复和 Windows 上的行为；费用（缓存写入未记录）；一次运行之外的稳定性与时延分布。
- 是否满足退出门槛：是——`accept-step1` 两平台通过，真实模型一次通过。
