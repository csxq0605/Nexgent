# DSH Main 实测（2026-10-06）

本轮从普通 `Nexgent(..., kernel="dsh")` 入口执行，使用真实 `mimo-v2.6-pro`、默认 Main 包、固定宿主 evaluator 和既有学习驱动器。没有注入模型、策略、评价器或候选。官方 DSH 源码固定在 `46a7f68b0922371ce7144b668b90e377d8e799f4`，通过官方 Python SDK、`sdk-minimal` profile 和 MCP 接入；运行载体为显式选择的开发 node carrier。

MiMo thinking 关闭，不能据此评价开启推理模式的最强表现。宿主审核仍是同模型复核；脚本另有不提供给模型的确定性 oracle。以下是开发证据，任务主动要求可复用工具，不能证明自主发现能力缺口、泛化 RSI 或递归收益。

## 失败和修复

保留了所有原生尝试：缺失 PyWin32 `.pth` 初始化、一次 SDK 冷启动超时、连接重置的未知模型结果、宽泛参数被序列化成字符串、核验耗尽判断调用额度，以及缺少工具源码导致审核器无法判断通用性。连接重置留下一个未知计费调用，不按零消耗处理，也不从同一日志重发。

第一次连续验证的来源任务在重复错误 `run_python.payload` 后耗尽 12 次模型预算，未交付。参数说明修正后的下一次历史任务数值正确，但因为审核器看不到工具源码而拒绝可复用要求。随后补齐宿主读取的不可变源码证据，不给 evaluator 执行候选代码的权限，也不放宽门槛。

两个普通任务通过后，验证脚本写入要求复用的反馈。最初两次规划合计 2 次模型调用、46446 已知 tokens，选择 `no_change`。随后补充任务内能力的说明、作用域和拟议持久化用途；一次规划误把完整摘要拼成定义 ID，被拒绝，没有修补模型选择。规划输入改为只提供宿主签发的 `source_ref`，摘要留在宿主核验账本。

后续真实配对暴露了三个不同问题，旧记录均保留：

- 父、候选都已完成独立复算，却在最后一轮继续请求工具，没有有效评价。宿主审核最后一轮改为只请求结论，缺少核验和继续请求工具仍不能通过。
- 一次 selection 全部通过，但发布校验误把内容寻址包第一次的来源说明当作最新生成记录的权限。现在从当前不可变生成记录、实际 `improve` 收据重放补丁，核对完整代码与父子版本；不覆盖第一次来源说明，不减少 selection/guard 要求。
- 下一次候选实际调用工具、发布正确结果并复算，却因“说明文字加 JSON”的原生收尾被纯 JSON 解析拒绝。DSH 完成现在依据本轮成功的宿主发布收据；最终文字中的引用没有权限，缺失工件或 schema 拒绝仍不能交付。

验证脚本共重复写入六次相同复用反馈，期间有人工诊断和框架修复。这是开发调试，不是六次独立用户请求或无人工干预的自主改进。
