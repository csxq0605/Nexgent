# Nexgent：无状态底座与任务专一型多智能体系统

日期：2026-09-23。状态：**目标架构决策，不是当前实现能力声明**。本决策修正以固定三角色包、特定 benchmark 或科研 demo 推导产品形态的做法。现有运行与进化能力、负结果仍以 [RSI readiness 审计](../research/rsi-readiness-audit-20260923.md) 为准。

## 1. 定位

Nexgent 的产品是一个**任务类型无关的多智能体自设计与自改进系统**。用户通过 Main 提出目标；系统可以为这项任务形成专一的角色、协作关系、技能、工具组合、交接合同与停止规则，组成一个可执行、可恢复、可修订的任务系统。面对另一类任务，同一个底座可以形成不同的团队和流程。科学发现、OpenFOAM、编程和 benchmark 都只是接入环境；任何一个场景的阶段、角色或评分方式均不进入通用 Kernel。

本机 Manyselves 的 `docs/PROJECT_POSITIONING.md` 提供重要参照：一套业务无关的 Kernel/Compiler/Runtime，由文件定义组织不同 Agent 团队。Nexgent 在此基础上增加一个关键能力：**团队与 Capability 定义不只能由人预先编写，智能体也能依据任务与反馈提出、实现、检验并版本化地改进它们。** 这不是复制 Manyselves 的领域示例或把 Nexgent 缩减为工作流编辑器。

## 2. “无状态”的准确含义

无状态指通用 Kernel 不拥有可变任务或领域状态。其核心语义应是确定性转换：

```text
ResolvedProgram + CurrentState + Event -> NewState + Effects
```

Compiler 解析版本化定义并检查引用、类型、权限与控制流；Kernel 只决定合法状态转移和待执行效果；Runtime 执行模型、工具、交互和工件操作，并把权威 Episode、Conversation、Artifact、Memory、版本档案及事件保存到外部 Store。**无状态不等于无记忆、无恢复或每个任务从零开始。** 记忆与改进成果是显式输入和版本化数据，不能藏在 Kernel 的进程全局变量或特定领域状态机里。

## 3. 一个任务怎样产生自己的“Manyselves”

```text
用户目标／环境与可用能力
  -> 任务理解与能力缺口判断
  -> 多智能体提出或选择任务专一的 AgentProgram
       角色、消息／工件关系、工作流或代码、技能、工具绑定、合同
  -> 通用 Compiler 准入，生成 ResolvedProgram
  -> 通用 Runtime 执行、交流、观察、修订、交付
  -> 任务反馈和执行轨迹
  -> 同一能力体系提出改进版本，开发检查，档案保留或采用
  -> 后续任务按适用条件选择并实际使用新版本
```

`AgentProgram` 是行为版本，不规定四个文件、固定角色数、固定 DAG 或必须使用某种语言。它可表达直接单智能体执行、临时组队、并行分支、辩论、委派、工具实验、有界反馈循环及阶段性交接。图适合显式依赖；受控代码与技能可以表达图不便表达的算法。Agent 可复用已验证的 Capability，也可开发新技能或组织方案；任务的实际限制来自可用模型、工具、权限、环境和资源，而不是人为只允许一次模型调用或一次文件替换。

任务内可重新规划，但正在执行的节点保持其已准入版本和输入身份；新定义编译后只能用于未开始的子图或后续 Episode。跨任务进化以新版本及实际复用为准。若修改了改进过程，必须让新版本实际产生后代，才能研究递归效用。

## 4. 稳定边界与可进化边界

| 通用且稳定 | 可由智能体设计、改进和复用 |
| --- | --- |
| 定义加载、编译、纯状态转换、调度与恢复语义 | 角色身份、职责、数量和组织方式 |
| 授权、凭据隔离、资源计账、工件身份和事件完整性 | 通信边、分支、合并、停止和任务内修订策略 |
| 模型／工具／交互端口及其准入合同 | 技能协议、受控代码、工具组合与领域方法 |
| 独立评价接口与隐藏结果隔离 | 记忆组织、检索、改进策略和候选搜索方法 |

稳定边界保证候选可执行、可审计、可比较，不规定候选只能发明哪种智能体。能力注册允许新增可执行技能和合法组合；外部工具与权限仍受宿主授权。领域插件只提供环境、工具、输入输出及评价适配，不拥有第二套 Kernel。

## 5. 探索与检验不能互相压制

开发阶段应允许多候选、多步修复、不同图拓扑和新增技能，在公开任务与真实环境中看系统是否**能完成任务、发现缺口、实现能力、改进并复用**。预算须可配置并完整记账；微小调用上限只能用于明确标记的 smoke，不是通用能力边界。失败候选、成本与退化保留在档案。

确认阶段才冻结任务、模型、总资源、版本和评价规则，与固定编排、单智能体、仅记忆等控制比较。相同调用次数只是一个控制条件，不自动等于相同纠错机会或实际算力。一个 demo 跑通只支持该环境的执行结论；跨任务适用性和 RSI 效用需要新任务与真实版本复用。统计合同不能代替系统首先具备可探索的能力空间。

## 6. 当前实现距离目标的主要缺口

现有 `AgentPackage`/`ExecutablePlan` 能编译并运行工作流，O/S PackagePatch v3 能提出多组件候选，真实模型已执行过一次改变图结构的 O 候选。这些是可复用底座，**不是任务专一团队自动形成的证明**。默认基线仍是预设三角色；普通任务不会自然触发团队设计、能力缺口识别、技能开发和后续采用。进化工作主要通过独立实验脚本与显式策略启动；M 与 O/S 尚不能原子联合发布，真实 R 改进效用也未建立。

下一架构验收应先证明：同一通用入口对不同类型的真实任务形成不同团队或技能组合；在一个能力缺口上产生可执行新能力；独立检查后于新任务复用，并记录角色、消息／工件、工具、版本和实际效果。之后再运行多任务 benchmark 与正式对照。科学发现和 OpenFOAM 只作为其中的环境实例。
