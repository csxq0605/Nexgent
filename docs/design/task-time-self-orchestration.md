# Nexgent 任务时自编排架构：可生成、可执行、可修订的智能体图

日期：2026-09-23。状态：**目标架构与实现合同；任务时 pending 图修订、新角色、有类型消息和受控技能子包已有代码路径，但真实模型尚未完成自主技能委派、反馈驱动的第二版图及跨任务收益。** 产品边界见[无状态底座与任务专一团队](stateless-kernel-and-self-designed-teams.md)，底层合同见[ExecutablePlan v1](executable-plan-v1.md)。

## 1. 问题与设计取舍

Nexgent 的核心能力不是从一张预制 DAG 里选择下一节点，而是让多智能体在任务过程中**提出团队及其执行图、运行节点、根据结果增删或改写未执行的节点和边、开发可复用技能，并在后续任务继承有用版本**。计划图是执行状态的一个版本，不是任务类型或产品的固定模板。简单任务可以只用一个节点；复杂任务可以展开并行探索、相互质疑、验证、修复和汇总。

参考一手方法的可迁移机制：[LLMCompiler](https://arxiv.org/abs/2312.04511)区分规划、就绪任务派发和并行执行；[GPTSwarm](https://proceedings.mlr.press/v235/zhuge24a.html)将节点提示及智能体间连边作为优化对象；[AFlow](https://arxiv.org/html/2410.10762)搜索代码表示的工作流并用执行反馈更新搜索；[ADAS](https://arxiv.org/html/2408.08435)扩大到可编程的智能体设计空间；[AutoSci](https://arxiv.org/html/2605.31468)以算子图和技能／模板演化处理其科研场景。Nexgent 借用**编排机制**，不继承它们的特定任务流程、固定模型角色或结果声明。

## 2. 三层模型

```text
可进化 AgentProgram       角色／技能／通信与规划策略／改进策略的版本
        │ 提出 GraphProposal 或 ProgramPatch
        ▼
Compiler + Plan Admission  类型、引用、权限、依赖、预算、版本边界
        │ 产出不可变 PlanRevision
        ▼
Execution Kernel/Runtime  就绪调度、交互、节点执行、反馈、恢复、工件
        │ 持久事件与结果
        └───────────────────> AgentProgram 的下一次规划或改进
```

通用 Kernel 的状态转换不含科研、CFD、编程题或报告字段。Runtime 从 Store 读取状态；Program 承担选择问题分解、角色数量、路由策略和工具方法。Compiler 负责把模型提出的结构变成可运行、可重放的版本，**不能由宿主偷偷填入固定的 proposer/reviewer/adjudicator 链**。Planner、critic 或 architect 也是 Program 中可更换的角色／技能，可从最小种子开始成长，不是一个永远不变的外部超级智能体。

## 3. 可执行图和交流

每个 `PlanRevision` 是有向依赖图 `G=(V,E)`。节点是一次有身份的工作请求：模型角色、技能、工具、子任务、局部控制或交互；边分为**控制依赖**与**数据／消息依赖**。控制边决定何时可运行；数据边指定哪个上游工件或消息进入哪个下游输入端口。节点只能读取任务输入、显式订阅的团队消息、准入的记忆和绑定的工件，不能默认获得整个隐式聊天历史。

`AgentMessage` 是带发送者、接收者／主题、schema、来源节点及可见性范围的工件；对话流是这样的消息序列，不是共享的无类型字符串。请求／回应、辩论、投票和同行复核都可以由角色及边组合表达，不在 Kernel 写死为必须经过的阶段。角色可能短暂存在于一个节点，也可能持有同一任务的会话；两者都须在图和收据中可辨认。当前纵切允许在 `artifact_edges` 上声明 `{topic,payload_schema}`；Compiler 把合同摘要写入端口身份，Runtime 在接收节点准入前验证发送值并生成带节点地址的确定性消息。发送者结果和接收者请求均进入既有收据，暂停恢复测试已证明消息重建且发送者不重放。尚无独立消息流／持久会话语义。

一个计划版本内的普通依赖图保持无环，以便计算就绪集和安全并行。**反馈循环不是画一条无限回边**：验证节点输出新观察后，Program 可以提交下一版图，或显式执行有界 loop/subworkflow。每版图可审计，已发出的模型／工具调用不会因改图而消失。

## 4. 智能体怎样自行编排

任务输入不应先被宿主归类成「科研五阶段」或「固定三角色」。启动 Program 只提供编排能力与可用端口；**任务专用的角色、节点、连接、并行程度、检查点和停止条件都应由 Program 根据目标及可用资源提出**。当前 `self_orchestration_seed.py` 的固定 `architect` 是启动脚手架，而非最终不可改变的组织。若后续任务仍只能执行它的单次规划提示，即使生成了 DAG，也不算可自设计的 AgentProgram。下一步须让经过评价的规划／协作策略版本取代这个种子，并在运行中自主触发修订。

节点代表可实际执行的一份工作，不只是流程图标签：模型询问、技能、工具、子任务、合并、工件读取或发布各有输入端口、输出收据、费用与失败状态。满足依赖的节点可并行调度；角色通过有类型的消息或工件边交接。子任务可以拥有自己的图。每版图保持 DAG，反馈循环通过新版本的 pending 子图或有界循环表示。这样既允许一节点直接完成简单任务，也允许复杂任务自己形成探索、质疑、实验和验证结构。

编排本身也是能力对象：除了任务内 `GraphProposal`，版本档案应保存可复用的规划策略、角色定义、技能协议与协作模板。后续任务先检索适用版本，再允许新提案分叉、组合或淘汰它们；独立评价决定是否晋升。不得用一个全局固定 supervisor 把「自编排」偷换成「由宿主编排其他智能体」。

Program 可以在任务开始或执行中的检查点产出下列提案；它也可以决定维持当前图或直接交付：

```text
GraphProposal {
  base_plan_ref, base_program_digest, reason_evidence_refs,
  pending_scope[],
  add_or_replace_nodes[], remove_nodes[],
  add_or_remove_control_edges[], add_or_remove_data_edges[],
  join_and_stop_rules[], expected_outputs[],
  estimated_work, hypothesis?, falsifier?
}
```

这些字段表达所需语义，不规定模型必须一次生成整份大 JSON。当前实现接受完整 `revised_workflow`，也接受按顺序执行的 `add/remove/replace_node`、`add/remove_control_edge`、`add/remove_artifact_edge` 操作，并可替换 `outputs`、下一版的 `revision_rules`，或追加 `task_roles`。模型可为任务声明新的角色身份与提示；宿主以内容摘要冻结其身份，后续图版本可继续增加角色，已完成节点不能被新角色定义改写。当前任务角色只能执行 `ask`，工具仍走独立的 Episode lease。编译错误会成为结构化反馈，同一角色可按版本化规则进行有界修复；修复模型调用进入独立 RPC 账本，不能悄悄把无效提案当成成功。Compiler 应：

1. 绑定 `base_plan_ref` 和 Program 版本，解析角色、技能、工具与工件引用；检查图结构、类型、可达交付和节点唯一性。
2. 检查外部权限与剩余根资源；允许 Program 在根预算内调整节点份额，不用固定每个角色一次调用或固定三个节点。预算不足时返回可修复的结构化诊断，不把宿主设置造成的失败误称为模型能力失败。
3. 仅修改未准入节点和这些节点拥有的入边；运行中及终态节点、实际输入、收据与费用保持原身份。新增节点可消费已完成节点的明确输出。
4. 原子保存提案、编译结果与来源，发布新的计划版本；若中断，可从同一提案和账本重算身份，不重新调用模型。

若提案需要**新角色、新技能或代码**，Program 同时提交 `ProgramPatch`。宿主先构建一个新的不可变 AgentProgram 版本并检查权限、接口及最小执行能力；新版本只进入未开始的工作或一个子 Episode。不能把运行中节点的提示或代码热改。任务内采用不等于跨任务晋升；后者仍需独立任务验证。已安装工具之外的新外部能力须走独立授权／安装端口，不能由图补丁凭空获得权限。

## 5. 任务执行状态机

```text
task admitted
  -> Program 提议初始图或直接执行
  -> Compiler 准入 PlanRevision
  -> Scheduler 选择所有依赖满足且资源可准入的节点
  -> Runtime 并行执行并保存 node attempts / messages / artifacts
  -> 检查结果与任务合同
       ├─ 可交付：发布结果与局限
       ├─ 可修复：Program 提议 pending 子图／Program 新版；再次编译
       ├─ 信息缺失：WAITING，保留同一 Run
       └─ 资源耗尽／环境不可用：可核查地停止
```

节点反馈有来源：工具返回、schema 校验、公开环境检查、用户纠正或 benchmark 公开开发信号。隐藏评价不得返回给任务中规划者。局部反馈使本任务调整图；只有反复出现或可迁移的能力缺口才启动跨任务版本提案。节点／边／角色的贡献分析是待检验假设，不能仅凭最后得分把功劳归给新加的 reviewer。

## 6. 长期自改进与搜索

版本档案保存 `AgentProgram`、图版本、技能、记忆、提出它们的 Episode、真实激活轨迹、开发结果、成本与失败。搜索可以从多个历史版本分叉，而不只在当前冠军上做一次 replace。改进 Program 可生成角色／边／技能／路由／预算策略的联合变化，也可改写自己的诊断与搜索方式；真正的 R 改进必须由新 R 产生后代并检验。

探索预算与确认预算分离。开发阶段需要足够的候选、修复和真实任务执行机会，允许不同拓扑与调用数并记录总成本；小预算只作为 smoke。确认阶段冻结模型、任务分布、版本、权限和资源，比较固定图、同资源单智能体、仅记忆、完整进化系统。控制实验解释机制，但**不能倒过来把所有候选限制成对照图的形状**。

## 7. 当前代码差距与首个可验收纵切

原始 `workflows.py` 可编译／执行依赖图，`PlanRevision` 可替换 pending 子图，`TaskService` 会核验角色、技能、工具与恢复账本；但修订原先只能指向**同一包内预登记的 workflow**。本分支新增 `proposal_path`：完成节点可以返回图提案；Compiler 检查基线版本、pending 边界和整个 DAG；运行器执行新节点，并以内容摘要保存已解析的生成图供恢复。已有确定性端到端测试验证规划节点增加并行角色、暂停恢复与已完成调用不重放。默认普通任务入口仍不是这条自编排路径；PackagePatch v3 的跨任务 O/S 候选也尚未与任务时图提案形成自动晋升闭环。

第一个纵切只聚焦架构主体：普通任务中的规划节点提出一份新增、删除或重连节点的图提案；Compiler 编译后由同一 Episode 执行新 pending 子图；两种不同目标导致不同真实调用图；模型、工具、消息与成果均留下收据；中断恢复不重放已完成调用。随后接入任务内新角色／技能的 ProgramPatch 与子 Episode，最后验证改进版本在新任务的复用。不得用“图 JSON 通过校验”或 demo 求解器运行代替这些验收。

当前纵切支持**从已有 manifest 中选用角色／技能／工具，或在任务图里创建新的 `ask` 角色，并动态决定节点与边**。任务角色和提示由内容摘要冻结，委派、暂停恢复及后续 pending 图修订均沿用这个身份。新增的 `develop_skill` 路径可在任务中编译受控代码技能为不可变子包，并通过委派实际执行，见[任务中创建能力](task-time-skill-invention.md)。任务图还能用有类型消息边传递节点间结果；这不等于持久会话。外部工具仍不能由图补丁凭空安装。编译错误修复和 checker 结果触发第二版 pending 图（旧节点不再执行）都有确定性端到端证据，尚未有真实模型完成这两类修订的证据。失败路由及多项节点级限制仍需执行语义。下一步需要真实模型至少在两类任务上设计不同的调用图，让实际任务反馈触发第二版图，再做技能独立评价与新任务复用。这些是尚未完成的验收，不由确定性测试替代。
